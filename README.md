# collector-bot

Закрытый Telegram-бот для внутренней проверки должников и оценки перспектив
взыскания.

Оператор вводит то, что известно о должнике → система опрашивает подключённые
легальные источники → сопоставляет и нормализует результаты → формирует карточку
→ считает объяснимый **Recovery Score 0–100** с указанием факторов и уверенности
данных.

`collector-bot` — имя репозитория. Название продукта задаётся переменной
`APP_NAME` и нигде не захардкожено.

## Что это

Внутренний инструмент. Не публичный сервис и не «пробив».

Работает только с:

- данными заказчика;
- данными, которые оператор сам вводит;
- официальными государственными источниками;
- открытыми публичными данными;
- легальными коммерческими API, к которым у владельца системы есть законный
  доступ.

Ключевой принцип всей системы:

> **Отсутствие доступа к источнику — это не отсутствие данных.**

Если ЕФРСБ не подключён, отчёт скажет «не проверено: источник не подключён», а
не «банкротство не обнаружено». Эта разница проведена сквозь весь код: через
`ProviderStatus`, через движок скоринга и через рендер отчёта.

Интерфейсов два. В Telegram уходит карточка: вердикт, долг, пошлина, балл и
строка «не проверено» — то есть ответ, а не простыня. Сам отчёт живёт на
веб-странице по временной ссылке, и оттуда же он печатается, сохраняется в PDF
и скачивается текстом (см. «[Веб-отчёт и выгрузка](#веб-отчёт-и-выгрузка)»).
Архитектура рассчитана на то, чтобы позже добавить REST API, интеграцию с
системой заказчика, 1С, XLSX/batch-импорт и периодическую перепроверку, не
переписывая бизнес-логику.

## Архитектура

```
Telegram (aiogram 3)
    ↓
BatchService — массовая проверка выгрузки
    ↓
SearchService
    ├── InternalDebtorProvider
    │       ├── CSV (data/*.csv)
    │       ├── внутренняя БД (импорт)
    │       └── 1С — future
    ├── FSSP                   NewDB: fssp_person
    ├── Fedresurs (ЕФРСБ)      вендор или NewDB: bankrot_person
    ├── FNS (ЕГРЮЛ / ЕГРИП)    вендор или NewDB: egrul_ip
    ├── Pledge (залоги)        NewDB: pledge_person, pledge_vin
    ├── Court (арбитраж)       NewDB: arbitr_person
    └── Vehicle / Property / Inheritance — future
    ↓
IdentityMatcher        сопоставление личности, match_confidence 0.0–1.0
    ↓
Aggregator             единая модель DebtorReport
    ↓
RecoveryScoreEngine    детерминированный скоринг + объяснение + confidence
    ↓
VerdictEngine          подавать / приказ / проверить / не подавать + пошлина
    ↓
Очередь взыскания      отсортированный список + выгрузка в CSV
```

Слои разделены жёстко:

| Слой | Каталог | Отвечает за |
|---|---|---|
| domain | `app/domain/` | модели, нормализация, правила скоринга. Без I/O |
| providers | `app/providers/` | источники данных и HTTP. Не знают о Telegram |
| services | `app/services/` | оркестрация, сопоставление, агрегация, отчёты |
| db | `app/db/` | схема и репозитории |
| bot | `app/bot/` | только сбор ввода и рендер. Без бизнес-логики |

`app/container.py` — единственная точка сборки зависимостей.

### Контракт провайдера

Провайдер **никогда не выбрасывает исключение наружу**. Любой сбой — таймаут,
401, 429, 5xx, битый JSON, неузнанная схема, баг внутри провайдера — становится
`ProviderResult` с честным статусом:

```python
class ProviderStatus(StrEnum):
    SUCCESS        = "success"          # ответил, есть записи
    NO_RESULTS     = "no_results"       # ответил, записей нет
    NOT_CONFIGURED = "not_configured"   # не подключён — НЕ отсутствие данных
    UNAVAILABLE    = "unavailable"      # временно недоступен
    ERROR          = "error"            # ошибка обращения
```

Поэтому падение одного источника ухудшает один раздел отчёта, а не весь запуск.

## Важное замечание про 1С

**Прямой интеграции с 1С сейчас нет — и это осознанное решение, а не пробел.**

Причина: нет доступа к реальной системе заказчика и её схеме. Неизвестно, какая
конфигурация используется, где она размещена, есть ли OData или HTTP-сервисы,
как называются справочники и поля, какие права будут выданы. Адаптер, написанный
по догадкам, выглядел бы готовым и не работал бы нигде.

Сейчас MVP работает через:

```
ручной ввод + импорт CSV
```

В будущем:

```
InternalDebtorProvider   ← SearchService видит только этот интерфейс
        ↓
OneCODataProvider        ← добавляется сюда, ничего выше не меняется
```

`app/providers/internal/onec_future.py` — задокументированный placeholder.
Он не используется в runtime, не зарегистрирован в реестре провайдеров, и его
конструктор осознанно выбрасывает `NotImplementedError` (это покрыто тестом).

### Что понадобится получить у заказчика для подключения 1С

1. Конфигурация 1С и её версия (УТ, ERP, УНФ, самописная, …).
2. Где размещена: локальный сервер, облако, аренда, файловая база.
3. Опубликован ли OData (`/odata/standard.odata/`) и доступен ли он по сети.
4. Есть ли HTTP-сервисы и можно ли добавить новые.
5. Допустим ли прямой доступ к СУБД (обычно нет — и не нужен).
6. Имена справочников и документов, где лежат должники, договоры и задолженность.
7. Состав полей каждого объекта: ФИО, дата рождения, телефон, номер договора,
   номер заявки, сумма долга, адрес, транспорт.
8. Учётная запись с правами только на чтение нужных объектов.
9. Сетевой доступ: VPN, белый список IP, сертификаты.
10. Ожидаемые объёмы и допустимая нагрузка (частота и размер выгрузок).
11. Регламент: пакетная выгрузка по расписанию или запрос по требованию.

Пока этого нет, промежуточный вариант без доработок на стороне 1С — регулярная
выгрузка CSV из 1С и загрузка её через `/import`. Формат — ниже.

## Массовая проверка

Главный сценарий. У компании сотни должников, и вопрос не «что известно про
Иванова», а «на кого из восьмисот тратить госпошлину».

```
/import   → загрузить выгрузку
/batch    → смета → подтверждение → прогон → очередь
```

**Смета до запуска.** Прогон тратит платные запросы, поэтому оператор сначала
видит, сколько должников, сколько уже есть в кэше и сколько обращений к
источникам это будет. Запуск — только по кнопке.

**Прогресс правится на месте.** Одно сообщение с полосой, а не восемьсот новых.

**Результат — очередь, а не отчёт.** Сводка по вердиктам, списки по каждому и
выгрузка в CSV (UTF-8 с BOM и точка с запятой — чтобы Excel открыл кириллицу и
разложил по столбцам; телефоны маскированы).

### Вердикт вместо абстрактного числа

Recovery Score отвечает «насколько долг выглядит взыскиваемым». Оператору нужен
другой ответ — что делать с конкретным должником. Правила проверяются строго по
порядку:

| Условие | Вердикт |
|---|---|
| Активное банкротство | **Не подавать** — требование в реестр кредиторов |
| Нет даты рождения или ИНН | **Проверить руками** — совпадение по одному ФИО не подтверждается |
| Ключевой источник не ответил | **Проверить руками** — решение на неполных данных принимать рано |
| В выгрузке нет суммы долга | **Проверить руками** — цену иска считать не из чего |
| Пошлина несоразмерна долгу | **Не подавать** — процесс не окупается |
| Низкая перспектива по совокупности | **Проверить руками** |
| Долг ≤ 500 000 ₽ | **Судебный приказ** — пошлина вдвое ниже |
| Долг > 500 000 ₽ | **Подавать иск** |

Порядок здесь и есть содержание: «мы не знаем» — это «проверить», а не «не
подавать».

Госпошлина считается по п. 1 ст. 333.19 НК РФ в редакции ФЗ от 08.08.2024
№ 259-ФЗ (для дел, возбуждённых после 08.09.2024); судебный приказ — 50 % от
исковой ставки. Таблица вынесена в `app/domain/fees.py`: при изменении редакции
НК правится один список.

Прогон показывает и обратную величину — **сколько не будет потрачено на пошлины
по безнадёжным должникам**. Ради этого числа всё и затевалось.

## Demo-режим

Проект **полностью работает без внешних API-ключей**. Это не заглушка, а тот же
самый код: те же сервисы, то же сопоставление, тот же скоринг, тот же рендер.
Подменяются только сетевые адаптеры.

```bash
make demo
# или
APP_MODE=demo .venv/bin/python -m app.main demo
```

Прогон выполняет три вымышленных должника, покрывающих весь диапазон оценки:

| Должник | Внешний след | Score | Категория |
|---|---|---|---|
| Тестов Андрей Сергеевич | ИП действует, ФССП и ЕФРСБ чисто | **75 / 100** | ВЫСОКАЯ |
| Примеров Алексей Олегович | 2 активных ИП, роль в ЮЛ | **50 / 100** | СРЕДНЯЯ |
| Демов Максим Игоревич | активное банкротство, 6 производств | **0 / 100** | НИЗКАЯ |

Затем показывается поиск по договору `EV-20481`.

Все персонажи вымышлены. Демо-провайдеры детерминированы: один и тот же запрос
всегда даёт один и тот же результат. Каждый отчёт помечен баннером
`⚠️ ДЕМО-РЕЖИМ`.

Демо-прогон — это и smoke-тест: если он печатает три отчёта с тремя разными
категориями, пайплайн собран правильно.

## Telegram: BotFather и allowlist

1. Откройте [@BotFather](https://t.me/BotFather) → `/newbot` → получите токен.
2. Узнайте свой числовой Telegram ID (например, через
   [@userinfobot](https://t.me/userinfobot)).
3. Заполните `.env`:

```env
TELEGRAM_BOT_TOKEN=123456789:AA...
ALLOWED_TELEGRAM_USER_IDS=123456789,987654321
```

4. Запустите:

```bash
make run
# или
.venv/bin/python -m app.main
```

**Бот закрытый.** `AllowlistMiddleware` стоит перед всеми роутерами: пользователь
вне allowlist получает `Доступ запрещён.` и не доходит ни до одного handler'а —
поиск не запускается, `search_request` не создаётся, ни один внешний API не
вызывается. Логируется только факт отказа и user id, без содержимого запроса.

Пустой `ALLOWED_TELEGRAM_USER_IDS` не пускает никого: закрытый инструмент должен
отказывать по умолчанию, а не открываться.

### Доступ по одобрению

До этого режима состояний было ровно два: список ID в `.env`, который правится на
сервере с перезапуском бота, — и `*`, открывающий бота всем, кто его найдёт.
Между ними не было ничего, а нужно было именно среднее.

```env
OWNER_TELEGRAM_USER_IDS=123456789
```

Заданный владелец включает режим. Дальше:

*   посторонний пишет боту → читает «доступ по одобрению, запрос отправлен» и
    **не доходит ни до одного handler'а**: ни поиска, ни `search_request`, ни
    одного платного запроса. Заявка создаётся в middleware;
*   владельцу приходит карточка — имя, `@username`, числовой ID — с кнопками
    **✅ Разрешить** / **🚫 Отклонить**;
*   решение уходит в таблицу `access_requests` (миграция `0006`) и переживает
    перезапуск: иначе падение процесса возвращало бы отобранный доступ;
*   одобренному бот пишет сам — «доступ открыт, нажмите /start»;
*   отклонённый может подать новую заявку **не чаще раза в сутки**. Отсчёт идёт
    от более позднего из двух — подачи и решения: владелец, разобравший заявку
    через три дня, иначе получил бы новую тем же вечером;
*   `/access` — список допущенных, ждущих и отклонённых, **только владельцу**.
    Там же кнопка **🚪 Отозвать** у каждого одобренного. Команда не попадает в
    общее меню Telegram: она публикуется через `BotCommandScopeChat` в чат
    владельца, потому что «кто ещё пользуется ботом» — не то, что обязан знать
    каждый допущенный сотрудник.

Что режим **не** меняет:

*   `ALLOWED_TELEGRAM_USER_IDS=*` сильнее и работает как работал — пущены все,
    заявок не создаётся вовсе, одобрять нечего;
*   без `OWNER_TELEGRAM_USER_IDS` поведение прежнее: посторонний получает
    `Доступ запрещён.`, строка в базе не создаётся;
*   владелец допущен всегда, даже если его нет в `ALLOWED_TELEGRAM_USER_IDS` —
    иначе одобрять заявки было бы некому;
*   доступ, выданный через `.env`, кнопкой не отзывается, и `/access` говорит об
    этом прямо, а не оставляет владельца искать несуществующую кнопку;
*   убрать владельца из `.env` — значит закрыть бота и для одобренных им: строка
    от прежней конфигурации не пускает в бота, у которого больше нет владельца.

Заявка и каждое решение пишутся в `audit_events` (`access.requested`,
`access.approved`, `access.rejected`, `access.revoked`). Тесты —
`tests/test_access.py`.

### Главное меню

```
📊 Проверить всю базу                     ← главный сценарий
👤 Физлицо          🚘 Госномер      🔢 VIN
🚗 Автомобиль       📍 Адрес         🪪 Паспорт
📄 Договор / заявка 📥 Импорт CSV    🕘 История
ℹ️ Откуда данные    ❓ Как это работает
```

Это инлайн-меню: оно живёт под конкретным сообщением и относится к нему.

### Нижняя клавиатура

Постоянная клавиатура под полем ввода — то, что видно всегда, не листая чат:

```
📊 Проверить всю базу
🔍 Проверить одного   🕘 История
ℹ️ Откуда данные      ❓ Как это работает
```

`resize_keyboard=True`, `is_persistent=True`, `one_time_keyboard` не выставляется:
свёрнутая или одноразовая клавиатура ничем не лучше её отсутствия. Пять кнопок, а
не десять пунктов инлайн-меню, — она занимает место на экране всегда, поэтому в
ней только ежедневное. Остальное (импорт, госномер, VIN, адрес, паспорт, договор)
осталось за «🔍 Проверить одного», которая открывает то же инлайн-меню.

Telegram присылает нажатие обычным текстовым сообщением: признака «это кнопка» в
апдейте нет. Отсюда два правила, оба закреплены тестами
(`tests/test_bot_keyboard.py`).

*   **Роутер кнопок подключается первым** (`app/bot/handlers/buttons.py`).
    Хендлер состояния забирает себе весь текст, дошедший до его роутера, — с
    любым другим порядком «🕘 История» на шаге ввода ФИО разобралась бы как
    фамилия.
*   **Совпадение точное, вместе со значком.** Нажатие присылает подпись байт в
    байт, а значок в начале с клавиатуры не набирается, — этим нажатие и
    отличается от ввода. Свободный ввод (номер договора, адрес, ФИО) доезжает до
    своего сценария нетронутым. Поэтому подпись кнопки — это ключ обработчика:
    переименование ломает кнопки у всех, кто не нажимал `/start` после релиза.

Состояние диалога сбрасывают только кнопки, начинающие новый сценарий: прогон,
проверка одного, история. «ℹ️ Откуда данные» и «❓ Как это работает» — чтение, и
после них человек возвращается ровно на тот шаг, где стоял.

Клавиатуру ставит `/start`, и только он: она не «показывается на сообщение», а
устанавливается для чата и живёт там, пока её не заменят или не снимут явно.
`ReplyKeyboardRemove` в коде нет нигде — это проверяется тестом. Обратная
сторона: у того, кто уже нажимал `/start` когда-то, кнопки появятся только после
следующего `/start`.

### Приветствие

`/start` отвечает баннером с подписью в три шага: нажми сюда, введи это, получи
вот это. Картинка лежит в `app/assets/welcome.jpg` — внутри пакета, а не в
корневом `assets/`: так её забирают и wheel (`packages = ["app"]`), и образ
(`COPY app ./app`), без правок сборки. Если файла нет или Telegram отверг
загрузку, `/start` отвечает тем же текстом без картинки: украшение не имеет права
выключать главную команду бота.

В подписи стоит и оговорка про «не проверено»: она относится к главному
инварианту проекта и потому живёт на первом экране, а не в справке, которую
откроет один человек из десяти.

## Импорт CSV

`/import` → отправить файл документом. Только для пользователей из allowlist.

### Формат

```csv
debtor_id,fio,birth_date,phone,contract_number,claim_number,debt_amount,address,vehicle_plate,vin,created_at
DEM-001,Тестов Андрей Сергеевич,12.03.1985,+7 (999) 123-45-01,EV-20481,ZA-1001,38400,"Москва, ул. Вымышленная, д. 1",А123ВС77,XW8ZZZ61ZKG011111,2026-01-15
DEM-002,Примеров Алексей Олегович,24.07.1979,89991234502,EV-20482,ZA-1002,154 200,"МО, г. Придуманск",О777ОО50,WVWZZZ1KZAW222222,2026-02-03
```

Все поля кроме идентифицирующих — необязательные. **Минимально достаточно `fio`
или `contract_number`.**

Поддерживается:

- разделители `,` `;` и табуляция (определяются автоматически);
- кодировки UTF-8 (в том числе с BOM) и Windows-1251;
- распространённые алиасы колонок: `id`, `фио`, `телефон`, `договор`, `долг`, …;
- суммы вида `38400`, `38 400`, `38 400,50`, `38400.50 руб.`;
- даты `ДД.ММ.ГГГГ`, `ДД-ММ-ГГГГ`, `ГГГГ-ММ-ДД`, `ДДММГГГГ`.

### Устойчивость

Одна плохая строка **не прерывает импорт**. Битые необязательные поля дают
предупреждение, а строка сохраняется без них. Строка без `fio` и без
`contract_number` отклоняется — сопоставить её не с чем.

```
Импорт завершён.

Всего строк: 482
Импортировано: 471
Пропущено: 11
Ошибки: 0
```

### Дедупликация

Детерминированная:

- есть `debtor_id` → upsert по нему;
- иначе → upsert по нормализованной комбинации `fio + birth_date + contract_number`.

Повторный импорт той же выгрузки **обновляет** записи, а не размножает их. Более
бедная выгрузка не затирает поля, заполненные предыдущей.

Демо-файлы: `data/demo_debtors.csv` (чистый) и `data/demo_debtors_messy.csv`
(с пустыми строками, дубликатом и битыми значениями — для проверки устойчивости).

Загрузка из командной строки:

```bash
make seed                                   # data/demo_debtors.csv
.venv/bin/python scripts/seed_demo.py path/to/export.csv
```

## Веб-отчёт и выгрузка

Таблицу производств в сообщении Telegram не сверстать, поэтому отчёт открывается
страницей. В чат уходит карточка и кнопка.

**Что на странице.** Первый экран отвечает на вопрос владельца за пять секунд:
вердикт, наш долг, госпошлина, Recovery Score и строка «Источники: ответили N из
M». Если хоть один источник промолчал, там же стоит «вердикт посчитан по
неполным данным» и перечень молчавших — вердикт не объявляется так, будто данные
полные. Ниже разделы: наши данные, ФССП, банкротство, залоги, суды, бизнес,
источники, Recovery Score. У каждого раздела в заголовке стоит состояние его
источника.

**Шесть состояний источника.** Ответил и нашёл / ответил и не нашёл / не
подключён / не хватило данных для запроса / временно недоступен / ошибка
обращения. Формулировки живут в одном месте —
`app/services/reporting.py::unanswered_line` и `source_state`, — и текстовый
отчёт, страница, карточка в чате и «ограничения оценки» берут их оттуда. Второй
набор слов неизбежно разъедется с первым, и тогда «не проверено» где-нибудь да
прочитается как «чисто».

**Выгрузка** — по тому же токену, что и страница, отдельного открытого адреса у
файлов нет:

| Адрес | Что отдаёт |
|---|---|
| `/r/<token>` | страница отчёта |
| `/r/<token>/print` | та же страница на печать: браузер сам открывает диалог, оттуда же «Сохранить в PDF» |
| `/r/<token>/report.txt` | текстовый отчёт — ровно тот же `render_report`, что уходит в чат |
| `/q/<token>` | очередь взыскания |
| `/q/<token>/print` | очередь на печать |
| `/q/<token>/queue.csv` | очередь таблицей (UTF-8 с BOM, Excel открывает как есть) |

PDF делает браузер по печатному стилю, а не генератор на сервере. Так на бумагу
уходит ровно то, что человек видел; PDF не расходится со страницей при каждой
правке вёрстки; в образ не приезжает ни WeasyPrint с cairo и pango, ни
headless-браузер; и файл с персональными данными нигде не оседает на диске.
Печатный стиль задаёт A4 с полями, повторяет шапку таблицы на каждом листе, не
рвёт строки и не оставляет заголовок висеть в конце страницы, раскрывает
свёрнутые блоки и убирает интерфейсное. Состояния источника на бумаге держатся
на знаке (`✓ — ○ ? ! ✗`), штриховке и форме рамки, а не на цвете: распечатку
подшивают к делу, и на чёрно-белом принтере «не проверено» обязано оставаться
отличимым от «проверено, записей нет».

Одно замечание про печать: браузер по умолчанию дописывает в свой колонтитул
адрес страницы, а в нём токен доступа. Страница печати об этом предупреждает и
несёт собственный колонтитул с датой формирования, так что галочку
«Колонтитулы» в диалоге печати можно снимать без потерь.

**Ссылка.** Токен на 256 бит, срок жизни ограничен (`SHARE_LINK_TTL_HOURS`, у
очереди свой и короче — `SHARE_QUEUE_TTL_HOURS`, за ней вся выгрузка целиком).
Страница открывается без пароля — так её можно переслать юристу, — и ровно
поэтому она закрыта от индексации, не кэшируется, не отдаёт `Referer` и ничего
не грузит со сторонних доменов (ни шрифтов, ни аналитики; CSP это фиксирует).
Ушедшую не туда ссылку гасит команда `/revoke`. Адрес у каждого оператора свой,
даже когда отчёт один и тот же и второй запрос ушёл в кэш: одна ссылка на всех
означала бы, что второй сотрудник получает выданную первому и погасить её своим
`/revoke` не может — а команда при этом отвечает «отзывать нечего». Чужие
ссылки на тот же отчёт `/revoke` не трогает и о них прямо предупреждает: после
отзыва человек обязан знать, открывается ли отчёт где-то ещё. Выдача и каждое
открытие попадают в `/audit` — по идентификатору ссылки, без токена.

**Развёртывание.** `WEB_PUBLIC_URL` обязан начинаться с `https://`, иначе бот не
стартует (для локальной отладки — `WEB_ALLOW_INSECURE=true`): токен едет в пути
URL, и по http его видит любой узел на маршруте. Приложение слушает `127.0.0.1`,
наружу страницу публикует TLS-терминатор. В его конфиге уберите `$request_uri`
из `log_format` или вырезайте `/r/<token>` — иначе токены осядут в access.log
прокси и во всех его ротациях. Пустой `WEB_PUBLIC_URL` — ссылки не
отправляются, и бот честно уходит на текстовый отчёт в чат.

### ФССП — через агрегатор NewDB

Прямой сервис ФССП (`api-ip.fssp.gov.ru`) выведен из эксплуатации и отвечает
`HTTP 410 Gone`. Исполнительные производства берутся из
[NewDB](https://newdb.net/docs/); ключ запрашивается на `access@newdb.net`.

```
POST https://api.newdb.net/v2
X-API-KEY: <token>

{"params": {"method": "fssp_person", "country": "ru",
            "lastname": "...", "firstname": "...", "secondname": "...",
            "dob": "YYYY-MM-DD", "regioncode": 77},
 "requestId": "<uuid>"}
```

Метод асинхронный. Конверт содержит `state`:
`queued` / `in_progress` / `restart` — ждать дальше, `complete` / `failed` —
терминальные. Опрос выполняется повторным POST на тот же `/v2` с тем же
`requestId` (так предписывает спецификация; заодно токен не попадает в query
string, а значит и в логи прокси).

Параметры обязательны на стороне источника. Поэтому:

* нет ФИО или **нет даты рождения** → провайдер возвращает `insufficient_query`,
  а отчёт пишет «не проверено: недостаточно данных», а не «ничего не найдено»;
* отчество отсутствует → ключ `secondname` **не отправляется вовсе**. Пустую
  строку источник отбивает (`secondname must be non-empty`), и запрос за
  должника без отчества не дошёл бы до ФССП вообще.

`regioncode`: Москва — 77, Московская область — 50, `100` — все регионы ФССП.
«Москва + МО» выполняет два запроса и объединяет результат, дедуплицируя
производства по номеру. Регион без известного кода расширяет поиск до `100`,
а не подставляет произвольный.

**Важная особенность, ради которой стоит читать этот абзац.** Отклонённый или
отсутствующий ключ NewDB возвращает не `401`, а **`HTTP 200` с
`state: "failed"`**. При наивном разборе это выглядит как пустой результат —
то есть чистый раздел ФССП по должнику, которого никто не проверял. Поэтому
любой терминальный `failed` отображается в статус ошибки
(`unauthorized` / `payment_required` / `bad_request`), а конверт `complete` без
секции `results.fssp_person.result.data` — в `unexpected_schema`. `NO_RESULTS`
возвращается только когда источник реально ответил и `data` пустой.

Это проверено на живом эндпоинте, а не вычитано: запрос без ключа отвечает
`HTTP 200`, `"state": "failed"` и текстом про `X-API-KEY`. В том же ответе
стоит **`"cost": 1`**. Похоже, что отклонённый вызов всё равно тарифицируется;
первым же оплаченным запросом это стоит проверить по балансу, потому что на
прогоне в сотни должников ошибка конфигурации иначе оплачивается молча.

Нормализация записи `data[]`: номер производства очищается от «от <дата>»,
из `Debtor` извлекаются ФИО и дата рождения, из `SubjectAndDebtAmount` —
предмет взыскания и сумма (приоритет у остатка долга — это то, что реально
конкурирует с нашим требованием), непустой `CompletionDateOrReason` означает
оконченное производство.

### Остальные методы NewDB — конверт в коде, строки в карте

Один ключ NewDB отвечает не только за ФССП. Тем же ключом подключаются:

| Метод | Что даёт | Чем адресуется | Куда попадает |
|---|---|---|---|
| `bankrot_person` | банкротство физлица | `innfiz` | ЕФРСБ, `FEDRESURS_BACKEND=newdb` |
| `egrul_ip` | ЕГРИП **и роли в юрлицах** | `innfiz` | ФНС, `FNS_PROVIDER=newdb` |
| `pledge_person` | залоги по человеку | ФИО + дата рождения | Залоги |
| `pledge_vin` | залог конкретной машины | `vin` | Залоги |
| `arbitr_person` | арбитражные дела | `innfiz` | Суды (арбитраж) |

Имя метода в таблице — рабочее, а не то, которым озаглавлена страница
документации: банкротство описано на странице `fedresurs_bankrot`, но живой API
принимает только `bankrot_person`.

**Три метода из пяти ищут только по ИНН.** ФИО с датой рождения они не
принимают — отвечают `Отсутствует обязательный параметр: innfiz`. Практическое
следствие: у должника без ИНН банкротство, статус ИП и арбитраж остаются
непроверенными, и провайдеры так и отвечают — `insufficient_query`, «нужен
ИНН», без единого платного вызова. По ФИО работают только ФССП и залоги.

`innfiz` — это ИНН физлица, двенадцать цифр. Поле `inn` в том же API означает
ИНН **юрлица** и валидируется как десятизначное, так что перепутать их значит
получить отказ на каждом запросе. Десятизначный ИНН эти три метода поэтому не
получают вовсе: провайдер отвечает «нужен ИНН физлица (12 цифр)» вместо того,
чтобы купить гарантированный отказ.

Дата рождения зовётся у разных методов по-разному: ФССП — `dob`,
`pledge_person` — `datebirth` (так на его странице во всех четырёх местах).
Живым запросом это не проверено; если сервис всё-таки ждёт `dob`, залоги по
человеку начнут отвечать отказом — это первое, на что смотреть в сыром ответе.

Контракт запроса снят с живого эндпоинта: неавторизованный `POST /v2`
проверяет параметры **до** ключа, поэтому обязательные поля читаются прямо из
отказов, не тратя ни одного оплаченного вызова. Схемы ответов так не увидеть —
для них нужен ключ.

Здесь проведена граница, которая важнее, чем кажется.

**В коде — то, что проверено.** Конверт NewDB один на все методы: `POST /v2`,
`method` внутри `params`, жизненный цикл `queued` → `complete` / `failed`,
опрос повторным POST с тем же `requestId`, строки в
`results.<method>.result.data`. Он вычитан из спецификации и живёт в
`app/providers/newdb.py`. Там же — правило, ради которого всё это написано:
терминальный `failed` (в том числе отклонённый ключ, который приходит как
**HTTP 200**) становится ошибкой, а не пустым результатом.

**В конфигурации — то, что принадлежит деплою.** Строки `fssp_person` разобраны
захардкоженными ключами: этот метод был вычитан с живого ответа первым, и его
разбор так и остался в коде. Схемы строк остальных методов тоже сверены с
живыми ответами (05.09.2026), но живут в карте — тем же механизмом, что уже
используется для вендоров ЕФРСБ и ФНС. Причина не в недоверии к схеме, а в том,
что контракт у каждого деплоя свой: карту правят файлом, а метод без записи в
ней остаётся «не подключено» вместо того, чтобы гадать.

```env
NEWDB_API_KEY=...
NEWDB_FIELD_MAP=./config/field_maps/my_newdb.json
FEDRESURS_BACKEND=newdb
FNS_PROVIDER=newdb
```

Карта — один JSON, ключами которого служат имена методов:

```json
{
  "pledge_person": {
    "records_path": "fnp",
    "fields": {
      "registration_number": "reference_number",
      "registered_at": "json_extra.registrationTime",
      "pledgor_name": "pledgor",
      "pledgee_name": "pledgee",
      "vin": "pledge_subject_ids_raw",
      "status": "message_type"
    },
    "value_maps": { "status": { "возникновение залога": "действует" } },
    "extra_params": { "country": "ru" }
  }
}
```

* `records_path` — вложенный массив, в который метод заворачивает записи,
  считая **от одной строки** `results.<method>.result.data` (конверт снимает
  сам клиент). У половины методов строка `data[]` — это контейнер на субъекта:
  уведомления лежат в `fnp`, дела о банкротстве — в `bankruptcy`. Ключа нет →
  строка сама и есть запись;
* `fields` — путь к полю внутри одной записи; индексы списков допустимы
  (`judges.0.court`);
* `value_maps` — нормализация словаря вендора (например, статусов);
* `extra_params` — то, что домешивается в запрос и **перекрывает** параметры,
  которые собрал бы адаптер: запасной выход для контракта, где параметр зовётся
  иначе.

Готовая карта — `config/field_maps/example_newdb.json`.

**Откуда в ней пути.** С живых ответов. 5 сентября 2026 года появился ключ, и
каждый метод был вызван по-настоящему; захваченные тела лежат в
`tests/data/newdb_live_*.json`, а тесты `tests/test_newdb_live_answers.py`
гоняют по ним ту самую карту из репозитория — от провайдера до текста отчёта.
Фикстуры нарезаны из захваченных ответов скриптом
(`scripts/make_live_fixtures.py`), а не набраны руками: заменены только
персональные данные, значение на значение той же формы.

До этого пути были сняты с документации NewDB из веб-архива (снимок 7 февраля
2026: <http://web.archive.org/web/20260207111510/https://newdb.net/docs/>).
Живой сервис разошёлся с этим снимком, и не в мелочах:

* `arbitr_person` заворачивает дела в **обёртку на запрос** (`cases[]` внутри
  строки `data`), а архивные пути отсчитывались от самого дела. Из-за этого
  метод отвечал «недоступен» у каждого должника, у которого дела есть, — и
  проходил только у тех, у кого их нет;
* `egrul_ip` возвращает не только ИП, но и роли в юрлицах (см. ниже);
* «данные не найдены» у `bankrot_person` и `pledge_*` — это не пустой `data[]`,
  как обещает документация, а контейнер с пустыми массивами внутри;
* ссылки Федресурса приходят абсолютными, а не относительными;
* в ответе о банкротстве обнаружились СНИЛС, место рождения и адрес проживания
  должника, которых документация не показывала вовсе.

**Что осталось архивным.** Прежде всего строка уведомления ФНП: у обоих живых
ответов массив `fnp` пришёл пустым, и все восемь путей внутри него подтвердить
было нечем. Полный список непроверенного — в шапке самой карты, в разделе
«STILL ARCHIVE ONLY». Отдельные поля, которых источник не отдаёт (ИНН
залогодателя, дата прекращения уведомления), перечислены в комментариях рядом
со своим методом прямо в файле.

Прогон одного должника с `STORE_RAW_RESPONSES=true` перед выпуском восьмисот
по-прежнему полезен — контракт вашего деплоя может отличаться. Учтите, что в
базу ляжет ответ вендора целиком: ФИО, ИНН, номера дел, адреса из карточек.
СНИЛС, место рождения и адрес проживания вырезаются всегда, независимо от
флагов (`app/utils/masking.py`, `SENSITIVE_RAW_KEYS`).

Метода нет в карте → метод не запрашивается, источник остаётся
`NOT_CONFIGURED`, отчёт пишет «не проверено». Карта не читается → бот **не
стартует**: иначе описанные ею методы молча остались бы «не подключено», и
оператор прочитал бы это как правду об источниках, а не о своём файле. Карта
читается, но её пути мимо → записи, в которых не нашлось ни одного поля, дают
`unexpected_schema`, а не `NO_RESULTS`: «не разобрано» и «чисто» — разные
ответы, и файл с чужими путями не должен выдавать второй.

**Одной неразобранной записи достаточно**, чтобы источник целиком стал «не
проверено». Раньше падал только ответ, в котором не разобралось совсем ничего,
а частичная потеря уходила в лог: из двух уведомлений в отчёт попадало одно, и
оператору неоткуда было узнать, что второе выпало — короткий список выглядит
ровно как полный. Потерять при этом уже разобранные строки — цена сознательная:
«не проверено» видно, а тихо укоротившийся список — нет. Карта полей это
артефакт деплоя, и наполовину верную карту чинят до прогона в восемьсот
должников, ради чего и делается первый прогон по одному с
`STORE_RAW_RESPONSES=true`.

То же и с самим вложенным массивом: `"fnp": []` — это ответ («уведомлений
нет»), а `"fnp": null`, `"fnp": 0` или `"fnp": "нет данных"` — это не ответ, а
строка другой формы, и она тоже даёт `unexpected_schema`.

И то же — с содержимым массива. `{"fnp": ["УВ-1", "УВ-2"]}` — реестр прислал
два уведомления строками вместо объектов; массив по типу в порядке, а записей
в нём ноль. Считается разница между длиной массива и числом прочитанных из него
записей, иначе такой ответ выходил бы как «залогов не найдено» с плюсом к
оценке за два найденных уведомления.

Счёт потерь — правило общее, а не свойство карты полей. Ему подчиняются:

* методы с картой (`app/providers/newdb.py`);
* **ФССП**, ключи которой захардкожены, потому что читались с живого ответа:
  строка не-объект и строка без номера производства — это потери, а не пустой
  реестр. Источник самый вероятно включённый, и «производств не найдено» у него
  стоит +5 к взыскаемости;
* vendor-agnostic адаптеры ЕФРСБ и ФНС (`app/providers/vendor_http.py`);
* строка-контейнер, у которой не прочиталось **ни одного** `row_fields`: записи
  в ней есть, а чьи они — неизвестно. Живьём личность лежит в блоке `commmon`
  (опечатка вендора, три «m»); переименуй он его — все пути промахнутся, и код
  проставил бы на дела ИНН запроса, то есть в ответе о двух субъектах отдал бы
  дела второго первому. Пустой ответ этим не задет: там и записей нет.

Обрезка длинного списка — не потеря, а неполнота, и о ней говорит сам ответ:
ФССП отдаёт первые 100 производств, арбитраж — первые 50 дел, и оба помечают
такой ответ `is_partial` (см. ниже).

**И третий ответ: «нашёл больше, чем прислал».** Живые вызовы показали, что
между «проверено, чисто» и «не проверено» есть ещё один случай, и до сих пор
его негде было сказать:

* ФНП нашла по ФИО тринадцать уведомлений (`fnp_urls`) и не пропустила ни
  одного через фильтр по дате рождения (`fnp` пуст);
* арбитраж отдаёт по десять дел за раз (`pagination.limit`), а сколько нашёл —
  пишет отдельно, в `total_count`.

В обоих случаях записей приходит меньше, чем нашёл источник, и ни ноль
неразобранного, ни статус `NO_RESULTS` об этом не сообщают. Такой ответ теперь
помечается `is_partial`, отчёт печатает, чего именно не хватает (для ФНП — со
ссылками на уведомления, чтобы взыскателю было куда пойти руками), в списке
источников он выглядит как «⚠ ... — ответ неполный», а скоринг снимает
положительный фактор: «залогов не найдено» и «исков не найдено» означают «мы
посмотрели и ничего не увидели», а тут посмотрели не всё. Штрафа при этом тоже
нет — неизвестность не факт.

Той же логике подчиняется отсев по отождествлению: если источник прислал
записи, а сопоставить с должником не удалось ни одну, отчёт пишет об этом прямо
(«требуется ручная проверка»), а не «не обнаружено». Исключение одно — ФССП: она
ищет по ФИО и штатно возвращает однофамильцев, и молчать о чистой ФССП из-за
чужого производства значило бы наказывать должника за тёзку.

Кроме `records_path`, `fields`, `value_maps` и `extra_params` запись метода
понимает ещё два ключа:

- `row_fields` — пути, отсчитанные **от самой строки `data`**, а не от записи
  внутри неё. Нужны там, где строка это контейнер на субъекта: `bankrot_person`
  держит ФИО и ИНН должника в `data[].commmon` рядом с массивом дел. Пока их
  никто не читал, адаптер проставлял на каждое дело тот ИНН, по которому шёл
  поиск, — для ответа об одном человеке это верно, а для ответа о двух отдаёт
  дела второго первому.
- `options` — то, что адаптеру нужно знать, а путём не выражается. Сейчас там
  один ключ: `arbitr_person.participant_name_key` — как называется поле с
  именем внутри элемента списка участников.

Каждый включённый метод — платный вызов на должника. На прогоне в восемьсот
строк это восемьсот вызовов на метод, так что включайте то, что будете читать.

### Залоги: зачем это в инструменте про взыскание

Заложенная вещь — не наше обеспечение, а чужое: залогодержатель
удовлетворяется раньше обычного кредитора. Найденная в реестре единственная
машина должника превращает видимый актив в чужой залог, и это меняет решение,
а не просто добавляет строку в отчёт.

Обратное стоит намного меньше и так и написано. Ответ `pledge_*` несёт две
ветки — `fnp` (реестр уведомлений ФНП) и `fedresurs` (лизинг и иные
обременения), — а одна запись карты полей описывает один набор строк, поэтому
читается только первая. Пустой ответ означает «в реестре уведомлений ФНП
действующих залогов не найдено», и ни отчёт, ни скоринг не переводят это в
«имущество не обременено»: ипотеки нет в ФНП вовсе, а одного действующего
договора лизинга хватило бы, чтобы такой вывод стал ложью.

ФИО залогодателя ФНП печатает в порядке «ИМЯ ОТЧЕСТВО ФАМИЛИЯ». Сопоставление
имён (`app/domain/identity.py`, `compare_names`) сравнивает мультимножества
слов и порядок игнорирует — позиционное сравнение читало такую запись как
чужого человека и прятало найденный залог. Поиск по VIN идентификаторов
залогодателя не возвращает вовсе, поэтому точный VIN из запроса сам работает
идентификатором: см. `_vin_from_query_matches` в `app/services/identity.py`.

### Арбитраж: что именно проверяется

`arbitr_person` — это **kad.arbitr.ru**, то есть дела, где физлицо участвует
как ИП. Суды общей юрисдикции, где судится большая часть потребительского
долга, туда не входят. Поэтому пустой ответ здесь означает «арбитражных дел
нет», а не «в суд на него никто не подавал», — и раздел отчёта так и написан.
Метод ищет по ИНН: без ИНН провайдер отвечает «недостаточно данных», а не
ищет по одному ФИО. Чужое арбитражное дело — плохое основание снять должника
с иска.

Отдельного поля роли у КАД нет: истцы и ответчики приходят двумя списками, и
роль определяется тем, в каком из них нашёлся должник. Решает она немало —
только живой иск **к** должнику попадает в конкуренты за его имущество и в
минусы скоринга. Поэтому имя участника сравнивается тем же `compare_names`, что
и везде: половина участников в примерах документации записана сокращённо
(«Бычков Д.Ю.»), и точное равенство строк промахивалось по ним всем, выдавая
роль «иной участник». Итог промаха был хуже суммы частей: дело печаталось в
отчёте, а скоринг рядом сообщал, что исков к должнику не найдено.

Роль назначает **доказательство**, а не «что угодно, кроме противоречия».
Проверка «уровень совпадения не NONE» пропускала и нечитаемую строку («Данные
скрыты» в списке ответчиков), и однофамильца с чужим отчеством — и оба делали
должника ответчиком по чужому иску. Теперь роль дают только положительные
уровни (`is_name_evidence`), а неопределённая роль перестала быть бесплатной:
действующее дело с ролью «иная» снимает плюс «исков к должнику не найдено» —
печатать дело и тут же отрицать его существование нельзя.
### Наследственные дела: единственный источник, отвечающий «ответчика больше нет»

Если должник умер, иск к нему суд не примет: производство прекращается, а
требование предъявляется наследникам или к наследственному имуществу в пределах
его стоимости. Не узнать об этом — значит год судиться с покойным и потерять и
пошлину, и срок. Открытое дело вдобавок называет нотариуса, который
единственный знает круг наследников: это следующий практический шаг, а не
справка.

Источник открытый и **бесплатный** — в отличие от всего остального в этом
списке. Поэтому он не входит в смету массового прогона (`planned_calls` == 0) и
не прячется за настройкой «в массовой проверке». `INHERITANCE_ENABLED`
существует по другой причине: `notariat.ru` отвечает только с российских
адресов, и на машине без российского IP источник обязан говорить «не
подключено», а не «дел не найдено».

Технически это два запроса: страница `/ru-ru/help/probate-cases/` за cookie и
токеном из `<meta name="csrf-token">`, затем `POST /api/probate-cases` с телом
`{"name": "<ФИО>", "args": {}}`, заголовками `X-CSRFToken` и `Referer` и
браузерным `User-Agent`. Токен живёт минуты, поэтому берётся перед каждой
проверкой и не кэшируется. Ретрай у источника свой и короткий: это чужой сайт,
а не API по договору.

**Главное свойство — реестр ищет ТОЛЬКО по ФИО и возвращает всех однофамильцев
разом.** Живьём «Иванов Иван Иванович» — `count: 1730`, и все 1730 записей
приходят одним ответом; дата рождения в запросе их число не меняет, а в самих
записях поле `BirthDate` часто `null`. Отсюда всё поведение:

* отбор по дате рождения делается **на нашей стороне** — сервис этого не умеет;
* совпавшая дата рождения даёт подтверждённое совпадение (0.60 за ФИО + 0.30 за
  дату = 0.90) и −35 в оценку, а вердикт становится «проверить руками» с
  пояснением про наследников — не «не подавать»: долг не исчезает;
* запись без даты рождения подтверждена быть не может по построению и **не даёт
  никакого фактора** — ни плюса, ни минуса: −35 за смерть однофамильца обнулили
  бы балл живого должника;
* когда однофамильцев немного, несколько записей показываются возможными
  совпадениями; когда их сотни — отчёт печатает число, объясняет, что различить
  их нечем, и даёт ссылку на ручную проверку. «Показать первые двадцать и
  промолчать про остальные» здесь запрещено;
* запись, чья дата смерти раньше даты рождения должника, отбрасывается: умереть
  до собственного рождения нельзя, и это единственный различитель, работающий
  при пустом `BirthDate`.

Положительного фактора у источника нет вовсе, ни при каком ответе. Дело
заводится **по заявлению наследника**, поэтому пустой реестр не доказывает даже
слабо, что должник жив, и отчёт говорит это прямо.

Даты разбираются локальным парсером: `DeathDate` приходит как `19760330`
(ГГГГММДД), а общий `parse_date` читает восьмизначную строку как ДДММГГГГ и на
этом источнике молча вернул бы `None`. Чинить общий парсер нельзя — для
остальных источников ДДММГГГГ верно, а `01021990` неразрешимо неоднозначен.

Сырое тело ответа не сохраняется никогда, даже при `STORE_RAW_RESPONSES=true`:
это ФИО, адреса, номера актов о смерти и телефоны тысячи посторонних людей, а
`SENSITIVE_RAW_KEYS` таких ключей не знает. В модель переносятся только ФИО,
даты, номер дела, нотариус, палата и округ.

### ИНН по паспорту — мост к трём источникам

Три метода из пяти ищут только по ИНН физлица. У взыскателя ИНН должника чаще
всего нет — а паспорт есть, он в договоре займа. Метод NewDB `passport_fns`
меняет одно на другое:

```
POST /v2  {"params": {"method": "passport_fns", "country": "ru",
                      "seria": "4015", "number": "350278",
                      "lastname": "...", "firstname": "...", "secondname": "...",
                      "dob": "YYYY-MM-DD"}}
```

```env
INN_BRIDGE_ENABLED=true      # по умолчанию false
```

**Ответ приходит в `results.company`, а не в `results.passport_fns`.** Это
единственный известный метод NewDB, у которого секция названа не именем метода;
читать по имени — значит получить `unexpected_schema` на каждом успешном
ответе. Ради этого у `NewDBClient.call` появился именованный параметр
`result_section`; остальные методы его не передают и читаются как раньше.

Что это меняет в отчёте. Раньше банкротство, статус ИП и арбитраж у должника без
ИНН писали «не проверено: нужен ИНН физлица» и на этом заканчивали. Теперь та же
строка получает продолжение, и оно разное:

* `ФНС не нашла ИНН по паспорту.` — ФНС ответила, ИНН по этим данным нет;
* `Получить ИНН по паспорту не удалось (…) — это не значит, что записей нет.` —
  мост не отработал;
* `Получение ИНН по паспорту не подключено.` — выключен флаг или нет ключа.

Разница между первым и вторым — это `NO_RESULTS` против `UNAVAILABLE`, тот самый
главный инвариант в миниатюре. Ради него мост и сделан отдельным провайдером: он
пишется в `search_results`, и объяснение переживает кэш вместе со строкой «не
проверено».

**Цена.** Один дополнительный платный вызов на должника. Флаг выключен по
умолчанию, смета `/batch` печатает мост отдельной строкой, а не растворяет его в
общем числе, и `providers_per_debtor` от него не меняется. Сегодня в массовом
прогоне мост всегда даёт ноль вызовов: паспортов в выгрузке нет — у `Debtor` нет
такой колонки. Смета говорит об этом прямо, потому что молчаливый ноль читался бы
как «бесплатно и работает», а значит он обратное: три источника по этим должникам
не будут проверены вовсе.

**Приватность.** Паспорт — чувствительнее всего, что бот обрабатывает:

* `raw_response` моста не сохраняется **никогда**, даже при
  `STORE_RAW_RESPONSES=true`: вендор возвращает присланные `params` эхом;
* текст вендорской ошибки проходит через `scrub_passport` **до** записи в
  `error_message` — эта колонка пишется мимо обоих флагов приватности;
* при `STORE_SENSITIVE_IDENTIFIERS=false` паспорт не попадает в `subject_json`;
  сохраняется только полученный ИНН — от него зависит корректность повторного
  показа отчёта;
* сам ИНН в текст отчёта не печатается ни в каком виде, включая маскированный;
* серия, номер и весь блок паспортных полей добавлены в редактор логов, который
  теперь чистит и вложенные словари.

В одиночном поиске паспорт спрашивается **последним шагом флоу физлица** и
только при включённом флаге — так он не попадает даже в состояние диалога.
Отдельный поиск по паспорту (`menu:passport`) остаётся тем, чем был: он строит
субъект без ФИО и даты рождения, мост на таком отказывает, не сделав ни одного
обращения, и обещание «не передаётся во внешние источники» на том экране
по-прежнему правда.

**Чего мост не делает.** Он не источник фактов: записей не приносит, в
`PROVIDER_CONFIDENCE_WEIGHTS` не входит, уверенность отчёта не повышает. Он
делает возможной проверку тех, кто в покрытие уже входит.

**Что не проверено и требует первого живого ответа.** Ключа NewDB у проекта нет,
живой ответ `passport_fns` никем не видан. Две вещи проверить в первую очередь:

* **длина `innfiz`.** Собственные примеры вендора противоречат друг другу:
  `fiz_02` возвращает `"7703245603"` (десять цифр), `fiz_04` —
  `"272116001938"` (двенадцать). Десятизначное — это ИНН юрлица, и три источника
  валидируют `innfiz` как двенадцать, поэтому десятизначный ответ мост
  **отвергает** (`unexpected_inn_length`), а не отдаёт дальше;
* **обязательность `secondname`.** Без отчества вызов всё равно делается — иначе
  заблокированы все, у кого его нет, — но пустой ответ помечается примечанием
  «отчество не указано», а не выдаётся за окончательное «ИНН нет».

Несколько разных `innfiz` в ответе — отказ (`ambiguous_identity`), ИНН не
берётся: чужой ИНН подошьёт должнику чужое банкротство и чужие дела, а это хуже
ненахождения.

Соседние методы того же семейства сознательно не подключены. `complex_by_passport`
— это другая форма конверта (секции по именам подметодов плюс блок `steps`, без
чтения которого частичный отказ прочитается как пустой источник) и **один
скалярный** `regioncode`, тогда как ФССП сейчас опрашивается отдельным запросом
на каждый регион: экономия одного вызова сузила бы покрытие с «Москва + область»
до одного региона. `passport_mvd` — это факт для отчёта и второй платный вызов, и
документация сама себе противоречит в имени поля (`status` против `doc_status`).

### ЕФРСБ и ФНС — vendor-agnostic адаптеры

Эти данные доступны через разных лицензированных API-вендоров, у каждого своя
схема ответа. Вместо того чтобы выдумать одну схему и захардкодить её, адаптеры
читают **field map** — небольшой JSON, описывающий, где в ответе лежат записи и
какие поля им соответствуют.

```env
FEDRESURS_BACKEND=generic_json
FEDRESURS_BASE_URL=https://api.вашвендор.ru
FEDRESURS_SEARCH_PATH=/v1/bankruptcy/search
FEDRESURS_API_KEY=...
FEDRESURS_AUTH_STYLE=bearer          # bearer | header | query | basic | none
FEDRESURS_FIELD_MAP=./config/field_maps/my_vendor.json
```

Примеры карт: `config/field_maps/example_fedresurs.json`,
`config/field_maps/example_fns.json`. Это **примеры структуры, а не описание
реального API** — пути нужно заменить на те, что указаны в документации вашего
вендора.

Без field map провайдер остаётся `NOT_CONFIGURED`: разобрать ответ нечем, а
делать вид, что источник подключён, нельзя.

Доступен встроенный демо-бэкенд: `FEDRESURS_BACKEND=demo`, `FNS_PROVIDER=demo`.

## Recovery Score

Детерминированный движок. Никакой LLM, никакой случайности: один и тот же отчёт
всегда даёт один и тот же результат, и каждый балл объясним.

Базовая оценка — 50, далее применяются факторы:

**Плюсы**

```
+10  действующее подтверждённое ИП
 +5  активная роль в ЮЛ            (суммарный бонус за бизнес ≤ +20)
+15  подтверждённое имущество
 +8  подтверждённый транспорт
+10  ЕФРСБ проверен, банкротства нет
 +5  ФССП проверена, активных производств нет
 +3  реестр залогов проверен, действующих залогов нет
 +3  арбитраж проверен, исков к должнику нет
```

**Минусы**

```
-35  активное банкротство
-35  дело о банкротстве есть, состояние процедуры источник не сообщил
-10  завершённое банкротство в анамнезе
 -5  1–2 активных исполнительных производства
-15  3–5
-25  более 5
 -5  подтверждённая сумма взысканий от 100 000 ₽
-10  от 500 000 ₽
-15  от 1 000 000 ₽
 -3  за каждую прекращённую бизнес-связь (не более -9)
 -8  за каждый действующий залог (не более -16)
-10  за каждый действующий арбитражный иск к должнику (не более -20)
```

Строчка про непрочитанное состояние стоит рядом с активным банкротством и
стоит столько же — намеренно. `bankrot_person` не отдаёт на уровне дела ни
процедуры, ни дат начала и окончания: состояние берётся из одной текстовой
строки, и незнакомая формулировка оставляет запись «неизвестной». (Даты и суть
процедуры в ответе есть — в `publications[]`, — но в непарсимом виде: «2475822
от 20.02.2018» это номер сообщения и дата одной строкой, и к конкретному делу
эти сообщения не привязаны.) Разница между активным и
завершённым — это скидка в 25 баллов, и выдавать её за молчание источника
нельзя. Цена ошибки несимметрична: недооценённая живая процедура — это поданный
иск и потраченная пошлина, а переоценённая завершённая — низкая перспектива,
которая по правилам вердикта уходит человеку на проверку. Фактор назван
отдельно (`bankruptcy_state_unknown`) и в отчёте печатается как «состояние
процедуры не определено», потому что «идёт процедура» — утверждение, которого
мы делать не можем.

То же правило и на залогах, только мягче: уведомление ФНП с непрочитанным типом
сообщения отменяет плюс «действующих залогов не найдено» — этот плюс значит «мы
посмотрели и ничего, что могло бы действовать, не увидели», а запись нашлась. Но
и штрафа за него нет: состояния как поля у ФНП нет вообще, и домысливать
«залог действует» не на чем.

Результат ограничивается диапазоном 0–100:

```
0–34     НИЗКАЯ
35–69    СРЕДНЯЯ
70–100   ВЫСОКАЯ
```

### Уверенность данных — отдельное число

`score` отвечает на вопрос «насколько долг выглядит взыскиваемым», а
`score_confidence` — на вопрос «какую часть картины мы вообще увидели». Это
разные вопросы, и хороший score, построенный на одном доступном источнике, —
не надёжный score.

Покрытие взвешено по источникам, которые двигают score: внутренние данные
0.15, ФССП 0.30, ЕФРСБ 0.25, ФНС 0.15, залоги 0.10, арбитраж 0.05. Источник,
который не может изменить число, не может и сделать его надёжнее.

Залоги и арбитраж попали в эту таблицу вместе со своими факторами — и это
сознательно понижает уверенность там, где их не подключили. Отчёт, посчитанный
без них, действительно видит меньше, и «Ограничения оценки» теперь прямо
называют, чего именно он не видел.

Confidence понижается дополнительно, если:

- поиск выполнен без даты рождения и ИНН (×0.7);
- часть записей сопоставлена лишь как «возможные совпадения» (×0.9).

Источник со статусом `NOT_CONFIGURED`, `UNAVAILABLE` или `ERROR` **не даёт ни
бонуса, ни штрафа** — он не проверен, и отчёт прямо перечисляет такие пробелы в
разделе «Ограничения оценки».

Отчёт не даёт юридических указаний. Он пишет «Предварительная перспектива
взыскания: СРЕДНЯЯ», перечисляет плюсы и риски и завершается фразой
«Оценка является аналитической и не заменяет юридическую проверку».

## Сопоставление личности

Самая ответственная часть системы.

Одинаковое ФИО из разных источников — **это ещё не один человек**. Действовать по
чужим исполнительным производствам одинаково неправильно и дорого, поэтому
совпадение по имени само по себе никогда не даёт подтверждённый статус.

Каждой внешней записи присваивается `match_confidence` в диапазоне 0.0–1.0:

| Сигнал | Вклад |
|---|---|
| полное совпадение ФИО | 0.60 |
| совпадают только фамилия и имя | 0.45 |
| фамилия совпадает, имя и отчество — по инициалам | 0.30 |
| ФИО не сопоставлено, либо строку не удалось прочитать как имя | 0.25 |
| ФИО прочитано и не совпало | 0.00 (но см. «пол» ниже) |
| совпадает дата рождения | +0.30 |
| **дата рождения не совпадает** | **→ 0.05, запись отбрасывается** |
| совпадает ИНН | +0.30 |
| ИНН не совпадает | −0.35 |
| совпадает телефон (внутренние данные) | +0.20 |
| нет уточняющих идентификаторов | −0.05 |
| распространённая фамилия без уточнений | −0.05 |

```
≥ 0.85   Подтверждённое совпадение
≥ 0.55   Возможное совпадение
<  0.55  Слабое совпадение — показывается, но в скоринге не участвует
```

Записи, найденные по точному внутреннему идентификатору (номер договора,
`debtor_id`, VIN), получают порог 0.95: сам идентификатор и есть доказательство.

**Форма записи имени — не свойство человека.** Сравнение (`compare_names` в
`app/domain/identity.py`) сравнивает мультимножества слов, поэтому не зависит
от порядка: ФНП печатает «ИМЯ ОТЧЕСТВО ФАМИЛИЯ», Федресурс — наоборот. Оно же
понимает сокращения — «Бычков Д.Ю.», «ИП Иванов И.И.», которыми записана
половина участников арбитражных дел, — но отдаёт их отдельным, самым слабым
уровнем: фамилия с инициалами доказывает меньше, чем имя, и без даты рождения
или ИНН до «возможного совпадения» не дотягивается.

Строгость при этом не в форме, а в содержании: сравнивается **то же** множество
слов, а не пересечение. Однофамилец («Тестов Пётр Сергеевич»), тёзка по имени и
отчеству («Андрей Сергеевич Петров»), чужие инициалы («Тестов П.С.») и чужое
отчество («Леликов Андрей Петрович» при нашем Андрее Сергеевиче) совпадением не
считаются.

**«Не совпало» и «не прочитано» — разные ответы, и стоят они по-разному.**
Реестры дописывают к ФИО что угодно: «Тестов Андрей Сергеевич, 15.03.1980
г.р.», «ТЕСТОВ АНДРЕЙ СЕРГЕЕВИЧ (ИНН 770…)», «Тестов Андрей Сергеевич ИП»,
«Алиев Рашид Мамед оглы», «Иванова (Петрова) Мария». Приписки убираются до
сравнения, скобки читаются в обоих вариантах, а хвост, который прочитать не
удалось, считается **отсутствием доказательства**, а не противоречием. Иначе
получалась ловушка: несовпадение ФИО стоит 0.00, а его отсутствие 0.25, и
дописать в карту полей путь к имени можно было только себе в убыток —
заполненное поле прятало запись надёжнее пустого.

Оттуда же **пол**: если сильный идентификатор (дата рождения или ИНН) сошёлся и
ничто не противоречит, имя не опускает запись ниже 0.25. `egrul_ip` отдаёт одно
и то же поле `name_short` у всех секций реестра, а что стоит в нём у секций,
которых живьём никто не видел, неизвестно; «имя не совпало» там означает не
«это другой человек», а «источник назвал здесь не то, что мы сравниваем» — и
0.00 + 0.30 за ИНН выбрасывало найденную по ИНН запись из отчёта, после чего
скоринг платил бонус за то, что её не нашли. С полом выходит ровно 0.55 — порог
«возможного совпадения»: запись видна и подписана как требующая проверки, но
подтверждённой не становится. Противоречие полом не лечится: разошедшийся ИНН
или дата рождения по-прежнему топят запись.

## Docker

```bash
make docker-build     # docker compose build
make docker-up        # docker compose up -d
make docker-down
```

Образ многостадийный, работает из-под непривилегированного пользователя,
применяет миграции при старте. SQLite и загруженные выгрузки живут в томе
`bot-data`. Секреты берутся из `.env` и не попадают в образ.

С PostgreSQL:

```bash
docker compose --profile postgres up -d
```

и в `.env`:

```env
DATABASE_URL=postgresql+asyncpg://collector:collector@postgres:5432/collector_bot
```

(для PostgreSQL поставьте extra: `pip install -e '.[postgres]'`).

**Локальный запуск на SQLite не требует Docker вообще** — достаточно
`make install && make demo`.

## Тесты, линт, типы

```bash
make test         # 507 тестов
make lint         # ruff check + ruff format --check
make typecheck    # mypy --strict, включая тесты
make check        # всё вместе
```

Покрыто, в частности:

- **скоринг** — банкротство роняет score; много производств роняет; действующая
  бизнес-связь поднимает; **недоступный провайдер не считается отсутствием
  записей**; score всегда в 0–100; результат детерминирован;
- **сопоставление** — ФИО + дата рождения; то же ФИО с другой датой рождения;
  только ФИО; отсутствующая дата рождения; распространённые фамилии; название
  ЮЛ не сопоставляется с человеком;
- **провайдеры** (через `respx`, фикстуры повторяют реальную схему NewDB) —
  успех, пустой результат, polling `queued → in_progress → complete`, исчерпание
  бюджета опроса, `state: failed` при отклонённом токене и при нулевом балансе,
  401/403, 402, 429 с ретраем, 5xx, битый JSON, неузнанная схема, `complete`
  без секции результата, баг внутри провайдера;
- **живые ответы NewDB** (`tests/test_newdb_live_answers.py`) — захваченные
  05.09.2026 тела прогоняются через ту самую карту из репозитория и до текста
  отчёта: дело о банкротстве не теряется из-за девичьей фамилии, чужая дата
  рождения по-прежнему дисквалифицирует, СНИЛС не доезжает до базы, роли в ЮЛ
  из `egrul_ip` не печатаются как «прекращено», одна регистрация ИП не
  считается дважды, обёртка арбитража разбирается, десять дел из сорока не
  выдаются за все, тринадцать несопоставленных уведомлений ФНП не читаются как
  чистый реестр — и при этом по-настоящему пустой реестр остаётся пустым;
- **агрегация** — ошибка ФНС не уничтожает результат ФССП; неподключённый
  источник не рендерится как «чисто»; отчёт не выдаёт юридических указаний;
- **безопасность Telegram** — неавторизованный пользователь не доходит до
  handler'а и не создаёт запись поиска; пустой allowlist не пускает никого;
- **маскирование** — телефон, паспорт, ИНН, VIN и токены не попадают целиком в
  историю, аудит и логи;
- **CSV** — валидный импорт, битая строка, отсутствующие необязательные поля,
  дубликаты, некорректная сумма, кодировки, лимиты;
- **end-to-end сценарии бота** — реальные `aiogram`-апдейты через реальный
  диспетчер: `/start`, полный поиск физлица, поиск по договору, отказ
  неавторизованному, история, кэш, `/import`, `/status`;
- **старт приложения** — отказ без токена, отказ с пустым allowlist, сборка
  контейнера зависимостей и отсутствие расхождений между моделями и миграцией;
- **госпошлина** — все границы ступеней ст. 333.19 НК РФ, потолок, монотонность
  на стыках, округление до полного рубля, половина ставки для приказа;
- **вердикт** — каждое правило и приоритет между ними: банкротство перекрывает
  хороший score, нехватка данных даёт «проверить», а не «не подавать»;
- **массовая проверка** — смета, переиспользование кэша, ограничение сверху,
  порядок очереди по числовому ключу (деньги хранятся текстом), битая строка не
  роняет прогон, прогресс, экспорт в CSV и маскирование телефонов.

## Безопасность и приватность

- Секреты только через `.env`; `.env` в `.gitignore`, в репозитории лежит
  `.env.example`.
- `STORE_RAW_RESPONSES=false` и `STORE_SENSITIVE_IDENTIFIERS=false` по умолчанию.
- Из сырых ответов вендора СНИЛС, место рождения и адрес проживания вырезаются
  **всегда**, независимо от обоих флагов. Живой ответ о банкротстве привозит их
  в блоке `commmon`; ни один путь карты полей на них не указывает, домену они не
  нужны, а совет «прогоните первого должника с `STORE_RAW_RESPONSES=true`»
  означал бы «запишите чужой СНИЛС себе в базу». Список ключей —
  `SENSITIVE_RAW_KEYS` в `app/utils/masking.py`; на месте вырезанного остаётся
  `_redacted_fields`, потому что `"snils": null` читалось бы как «вендор ничего
  не прислал».
- Дата рождения должника из ответа о банкротстве используется только для
  сопоставления личности: в отчёт она не печатается и в логи не пишется.
- В историю пишется маскированный запрос и односторонний хэш, не сам запрос.
- Паспорт при выключенном флаге не сохраняется целиком. В логах — `45** ******`.
  Сообщение оператора с номером удаляется из чата. Наружу он уходит ровно в
  одном случае — при явно включённом `INN_BRIDGE_ENABLED`, в ФНС через агрегатор,
  чтобы получить ИНН; см. [ИНН по паспорту](#инн-по-паспорту--мост-к-трём-источникам).
  Отдельный поиск по паспорту (`menu:passport`) наружу не ходит никогда: он
  строит субъект без ФИО и даты рождения, и мост на таком отказывает без единого
  обращения.
- Телефон хранится маскированным (`+7 (999) ***-**-67`) плюс хэш для поиска;
  полный номер — только при явно включённом флаге.
- Логи проходят через процессор-редактор, который вычищает токены, ключи,
  пароли, телефоны и паспорта, даже если что-то просочилось немаскированным.
- `/audit` показывает журнал действий: кто, что и когда — без содержимого
  запросов. Выдача ссылки на отчёт и каждое её открытие тоже туда попадают —
  по идентификатору ссылки, никогда по токену: аудит не должен сам стать
  хранилищем ключей доступа.
- Ссылка на отчёт отзывается командой `/revoke`; отозванная и просроченная
  отдают одинаковый 404, как и несуществующая. Отзывается своё: адрес у каждого
  оператора свой, а про живые чужие ссылки на те же отчёты бот говорит в ответе.
- Ретеншен, удаляя историю проверок, удаляет и ссылки на неё: иначе связка
  «оператор → какой отчёт он смотрел» переживала бы сам отчёт.
- ИНН на странице отчёта показывается целиком — это реквизит иска, и оператору
  он нужен для подготовки документов. Во всём остальном (история, аудит, логи)
  работает `mask_inn`. Адрес проживания на странице спрятан под «показать
  адрес»: в вердикте и в оценке он не участвует, а страница пересылается.
  В таблице очереди ФИО сокращены до `Иванов И. И.` — за одной ссылкой там
  восемьсот человек.
- `HISTORY_RETENTION_DAYS` (90 по умолчанию) чистит историю проверок; вместе с
  ней раз в сутки удаляются просроченные ссылки. `0` отключает чистку — это
  осознанное решение, а не значение по умолчанию.

## Переменные окружения

Полный список с комментариями — в `.env.example`. Минимум для запуска бота:

```env
APP_MODE=demo
APP_NAME=Collector Bot

TELEGRAM_BOT_TOKEN=          # от @BotFather — обязательно
ALLOWED_TELEGRAM_USER_IDS=   # числовые ID через запятую — обязательно
OWNER_TELEGRAM_USER_IDS=     # владельцы: включает доступ по одобрению

DATABASE_URL=sqlite+aiosqlite:///./collector_bot.db
INTERNAL_CSV_PATH=./data/demo_debtors.csv

# Веб-отчёт. Пустой WEB_PUBLIC_URL — ссылки не отправляются, отчёт уходит
# текстом в чат. Адрес обязан быть https, иначе бот не стартует.
WEB_ENABLED=true
WEB_HOST=127.0.0.1
WEB_PORT=8080
WEB_PUBLIC_URL=
SHARE_LINK_TTL_HOURS=72
SHARE_QUEUE_TTL_HOURS=12
HISTORY_RETENTION_DAYS=90
```

Для подключения реальных источников (`APP_MODE=live`) дополнительно.

Всё через один ключ NewDB — самый короткий путь:

```env
NEWDB_API_KEY=
NEWDB_BASE_URL=https://api.newdb.net
# Схемы строк методов, кроме fssp_person. Метода нет в файле — метод не
# запрашивается. Файл не читается — бот не стартует.
NEWDB_FIELD_MAP=./config/field_maps/my_newdb.json

FEDRESURS_BACKEND=newdb
FNS_PROVIDER=newdb
# FNS_PROVIDER=newdb — только когда в карте появится egrul_ip; сейчас ФНС
# останется «не подключено», и это честнее, чем пустой ответ.

# Получение ИНН физлица по паспорту (passport_fns). Один дополнительный платный
# вызов на должника; серия и номер уходят во внешний источник. Без него
# банкротство, статус ИП и арбитраж не проверяются вовсе.
INN_BRIDGE_ENABLED=false

# Реестр наследственных дел ФНП. Ключа не требует и денег не стоит: в смету
# прогона не входит. Флаг про доступность, а не про деньги — notariat.ru
# отвечает только с российских адресов, и выключенный источник говорит
# «не подключено», а не «дел не найдено».
INHERITANCE_ENABLED=false
INHERITANCE_BASE_URL=https://notariat.ru
```

Либо ЕФРСБ и ФНС от отдельных лицензированных вендоров:

```env
FEDRESURS_BACKEND=generic_json
FEDRESURS_BASE_URL=
FEDRESURS_SEARCH_PATH=
FEDRESURS_API_KEY=
FEDRESURS_FIELD_MAP=

FNS_PROVIDER=generic_json
FNS_BASE_URL=
FNS_SEARCH_PATH=
FNS_API_KEY=
FNS_FIELD_MAP=
```

Залоги и арбитраж идут только через NewDB и включаются наличием своих методов
(`pledge_person`, `pledge_vin`, `arbitr_person`) в `NEWDB_FIELD_MAP`. Там же
описан `egrul_ip`, который отдаёт и регистрации ИП, и роли в юрлицах —
руководителя и учредителя. Чего он не отдаёт в этих строках, так это самой
компании: ИНН и название юрлица лежат в другой ветке того же ответа, а одна
запись карты читает один набор строк, поэтому в отчёте роль названа по
человеку — «руководитель ЮЛ: Иванов И.И.», без имени общества.

## Границы проекта

Проект **не реализует и не будет реализовывать**:

- базы утечек и покупку слитых данных;
- нелегальный «пробив»;
- обход авторизации и капчи;
- scraping закрытых кабинетов;
- получение банковских счетов и остатков;
- скрытое определение местоположения;
- Telegram userbot / Telethon-интеграции с чужими «пробивными» ботами;
- автоматическое определение имущества по ФИО без законного provider'а;
- выдумывание схемы ответа вендора: метод, строки которого не описаны, не
  запрашивается вовсе.

Sherlock и Void рассматриваются исключительно как UX-референс.

Если источник нельзя подключить стабильно и законно — он возвращает
`NOT_CONFIGURED` или `UNAVAILABLE`. Отсутствие доступа не выдаётся за отсутствие
данных.

## Roadmap

Сделано: массовая проверка выгрузки, вердикт с расчётом госпошлины, очередь
взыскания и выгрузка в CSV, остальные методы NewDB — банкротство, статус ИП,
залоги (по человеку и по VIN) и арбитраж — поверх общего конверта, с залогами
и арбитражем как отдельными источниками в отчёте и в скоринге, плюс мост
«паспорт → ИНН» (`passport_fns`), без которого три из этих источников у должника
без ИНН не проверялись вовсе.

Дальше, в порядке ценности для задачи:

1. **Увидеть живьём строку уведомления ФНП.** Схемы строк сверены с живыми
   ответами 05.09.2026, и это закрыло почти весь долг: `datebirth` у
   `pledge_person` подтверждён, строка `egrul_ip` описана, обёртка
   `arbitr_person` исправлена. Осталась одна дыра, и она в самом ценном для
   взыскания месте: массив `fnp` живьём приходил пустым оба раза, поэтому все
   восемь путей внутри уведомления — по-прежнему архивная гипотеза. Нужен один
   должник, у которого залог в реестре ФНП точно есть. Там же стоит проверить
   ветку `fedresurs[]` (лизинг), которую карта пока не читает вовсе.
2. **Проверить реестр наследственных дел на проде.** Источник подключён
   (`app/providers/inheritance.py`, `INHERITANCE_ENABLED`), схема снята с
   живого ответа, тесты идут на фикстурах. Живьём с машины разработчика он
   недоступен — notariat.ru отвечает только с российских адресов, — поэтому
   первый настоящий прогон делается на прод-сервере. Проверить надо ровно два
   места: держится ли форма страницы с `csrf-token` и не изменился ли формат
   `DeathDate` (`ГГГГММДД` строкой).
1. **Сверить карту строк NewDB с живым ответом.** Конверт вычитан из
   спецификации и покрыт тестами; схемы строк методов, кроме `fssp_person`,
   сняты с архивной документации (снимок 07.02.2026) и против реального ответа
   не проверялись. Первый прогон с ключом на одном должнике и
   `STORE_RAW_RESPONSES=true` подтверждает или опровергает их разом. Отдельно
   ждут проверки два места, где документация уже могла устареть: имя параметра
   даты рождения у `pledge_person` (`datebirth` против `dob`) и содержимое
   строки `egrul_ip`, для которого карты пока нет вовсе. Тем же прогоном
   проверяются два открытых вопроса по `passport_fns`: длина `innfiz` (примеры
   вендора расходятся — десять цифр против двенадцати) и обязательность
   `secondname`.
2. **Паспортная колонка в выгрузке.** Пока её нет, мост в массовом прогоне даёт
   ноль вызовов, и смета говорит об этом прямо. Отдельный этап со своей ценой:
   сотни паспортов в покое в SQLite и схема `passport`/`passport_masked`/
   `passport_hash` по образцу телефона.
3. ~~**Наследственные дела** — реестр ФНП.~~ Сделано: источник подключён и
   даёт вердикт «проверить руками» с пояснением, что требование предъявляется
   наследникам. Осталось проверить его живьём на прод-сервере — см. п. 2.
4. **Telegram Mini App** — очередь на восемьсот строк с сортировкой и
   фильтрами; в сообщениях такое не показать. Заодно закрывает запрос
   «телега + веб-интерфейс» одним куском.
5. **Периодическая перепроверка** — расписание поверх существующего кэша:
   банкротство, производства и залоги появляются со временем.
6. **XLSX-импорт** — рядом с CSV-парсером, тот же `ImportService`.
7. **1С** — `OneCODataProvider` вместо/рядом с CSV, после получения доступа.
8. **PostgreSQL в проде** — миграции и репозитории уже совместимы.
