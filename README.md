# collector-bot

Закрытый Telegram-бот для внутренней проверки должников и оценки перспектив
взыскания.

Оператор вводит то, что известно о должнике → система опрашивает подключённые
легальные источники → сопоставляет и нормализует результаты → формирует карточку
→ считает объяснимый **Recovery Score 0–100** с указанием факторов и уверенности
данных.

`collector-bot` — имя репозитория. Название продукта задаётся переменной
`APP_NAME` и нигде не захардкожено.

## Что это

Внутренний инструмент. Не публичный сервис и не «пробив».

Работает только с:

- данными заказчика;
- данными, которые оператор сам вводит;
- официальными государственными источниками;
- открытыми публичными данными;
- легальными коммерческими API, к которым у владельца системы есть законный
  доступ.

Ключевой принцип всей системы:

> **Отсутствие доступа к источнику — это не отсутствие данных.**

Если ЕФРСБ не подключён, отчёт скажет «не проверено: источник не подключён», а
не «банкротство не обнаружено». Эта разница проведена сквозь весь код: через
`ProviderStatus`, через движок скоринга и через рендер отчёта.

Первый интерфейс — Telegram. Архитектура рассчитана на то, чтобы позже добавить
Web UI, REST API, интеграцию с системой заказчика, 1С, XLSX/batch-импорт и
периодическую перепроверку, не переписывая бизнес-логику.

## Архитектура

```
Telegram (aiogram 3)
    ↓
BatchService — массовая проверка выгрузки
    ↓
SearchService
    ├── InternalDebtorProvider
    │       ├── CSV (data/*.csv)
    │       ├── внутренняя БД (импорт)
    │       └── 1С — future
    ├── FSSP
    ├── Fedresurs (ЕФРСБ)
    ├── FNS (ЕГРЮЛ / ЕГРИП)
    └── Court / Vehicle / Property / Pledge / Inheritance — future
    ↓
IdentityMatcher        сопоставление личности, match_confidence 0.0–1.0
    ↓
Aggregator             единая модель DebtorReport
    ↓
RecoveryScoreEngine    детерминированный скоринг + объяснение + confidence
    ↓
VerdictEngine          подавать / приказ / проверить / не подавать + пошлина
    ↓
Очередь взыскания      отсортированный список + выгрузка в CSV
```

Слои разделены жёстко:

| Слой | Каталог | Отвечает за |
|---|---|---|
| domain | `app/domain/` | модели, нормализация, правила скоринга. Без I/O |
| providers | `app/providers/` | источники данных и HTTP. Не знают о Telegram |
| services | `app/services/` | оркестрация, сопоставление, агрегация, отчёты |
| db | `app/db/` | схема и репозитории |
| bot | `app/bot/` | только сбор ввода и рендер. Без бизнес-логики |

`app/container.py` — единственная точка сборки зависимостей.

### Контракт провайдера

Провайдер **никогда не выбрасывает исключение наружу**. Любой сбой — таймаут,
401, 429, 5xx, битый JSON, неузнанная схема, баг внутри провайдера — становится
`ProviderResult` с честным статусом:

```python
class ProviderStatus(StrEnum):
    SUCCESS        = "success"          # ответил, есть записи
    NO_RESULTS     = "no_results"       # ответил, записей нет
    NOT_CONFIGURED = "not_configured"   # не подключён — НЕ отсутствие данных
    UNAVAILABLE    = "unavailable"      # временно недоступен
    ERROR          = "error"            # ошибка обращения
```

Поэтому падение одного источника ухудшает один раздел отчёта, а не весь запуск.

## Важное замечание про 1С

**Прямой интеграции с 1С сейчас нет — и это осознанное решение, а не пробел.**

Причина: нет доступа к реальной системе заказчика и её схеме. Неизвестно, какая
конфигурация используется, где она размещена, есть ли OData или HTTP-сервисы,
как называются справочники и поля, какие права будут выданы. Адаптер, написанный
по догадкам, выглядел бы готовым и не работал бы нигде.

Сейчас MVP работает через:

```
ручной ввод + импорт CSV
```

В будущем:

```
InternalDebtorProvider   ← SearchService видит только этот интерфейс
        ↓
OneCODataProvider        ← добавляется сюда, ничего выше не меняется
```

`app/providers/internal/onec_future.py` — задокументированный placeholder.
Он не используется в runtime, не зарегистрирован в реестре провайдеров, и его
конструктор осознанно выбрасывает `NotImplementedError` (это покрыто тестом).

### Что понадобится получить у заказчика для подключения 1С

1. Конфигурация 1С и её версия (УТ, ERP, УНФ, самописная, …).
2. Где размещена: локальный сервер, облако, аренда, файловая база.
3. Опубликован ли OData (`/odata/standard.odata/`) и доступен ли он по сети.
4. Есть ли HTTP-сервисы и можно ли добавить новые.
5. Допустим ли прямой доступ к СУБД (обычно нет — и не нужен).
6. Имена справочников и документов, где лежат должники, договоры и задолженность.
7. Состав полей каждого объекта: ФИО, дата рождения, телефон, номер договора,
   номер заявки, сумма долга, адрес, транспорт.
8. Учётная запись с правами только на чтение нужных объектов.
9. Сетевой доступ: VPN, белый список IP, сертификаты.
10. Ожидаемые объёмы и допустимая нагрузка (частота и размер выгрузок).
11. Регламент: пакетная выгрузка по расписанию или запрос по требованию.

Пока этого нет, промежуточный вариант без доработок на стороне 1С — регулярная
выгрузка CSV из 1С и загрузка её через `/import`. Формат — ниже.

## Массовая проверка

Главный сценарий. У компании сотни должников, и вопрос не «что известно про
Иванова», а «на кого из восьмисот тратить госпошлину».

```
/import   → загрузить выгрузку
/batch    → смета → подтверждение → прогон → очередь
```

**Смета до запуска.** Прогон тратит платные запросы, поэтому оператор сначала
видит, сколько должников, сколько уже есть в кэше и сколько обращений к
источникам это будет. Запуск — только по кнопке.

**Прогресс правится на месте.** Одно сообщение с полосой, а не восемьсот новых.

**Результат — очередь, а не отчёт.** Сводка по вердиктам, списки по каждому и
выгрузка в CSV (UTF-8 с BOM и точка с запятой — чтобы Excel открыл кириллицу и
разложил по столбцам; телефоны маскированы).

### Вердикт вместо абстрактного числа

Recovery Score отвечает «насколько долг выглядит взыскиваемым». Оператору нужен
другой ответ — что делать с конкретным должником. Правила проверяются строго по
порядку:

| Условие | Вердикт |
|---|---|
| Активное банкротство | **Не подавать** — требование в реестр кредиторов |
| Нет даты рождения или ИНН | **Проверить руками** — совпадение по одному ФИО не подтверждается |
| Ключевой источник не ответил | **Проверить руками** — решение на неполных данных принимать рано |
| В выгрузке нет суммы долга | **Проверить руками** — цену иска считать не из чего |
| Пошлина несоразмерна долгу | **Не подавать** — процесс не окупается |
| Низкая перспектива по совокупности | **Проверить руками** |
| Долг ≤ 500 000 ₽ | **Судебный приказ** — пошлина вдвое ниже |
| Долг > 500 000 ₽ | **Подавать иск** |

Порядок здесь и есть содержание: «мы не знаем» — это «проверить», а не «не
подавать».

Госпошлина считается по п. 1 ст. 333.19 НК РФ в редакции ФЗ от 08.08.2024
№ 259-ФЗ (для дел, возбуждённых после 08.09.2024); судебный приказ — 50 % от
исковой ставки. Таблица вынесена в `app/domain/fees.py`: при изменении редакции
НК правится один список.

Прогон показывает и обратную величину — **сколько не будет потрачено на пошлины
по безнадёжным должникам**. Ради этого числа всё и затевалось.

## Demo-режим

Проект **полностью работает без внешних API-ключей**. Это не заглушка, а тот же
самый код: те же сервисы, то же сопоставление, тот же скоринг, тот же рендер.
Подменяются только сетевые адаптеры.

```bash
make demo
# или
APP_MODE=demo .venv/bin/python -m app.main demo
```

Прогон выполняет три вымышленных должника, покрывающих весь диапазон оценки:

| Должник | Внешний след | Score | Категория |
|---|---|---|---|
| Тестов Андрей Сергеевич | ИП действует, ФССП и ЕФРСБ чисто | **75 / 100** | ВЫСОКАЯ |
| Примеров Алексей Олегович | 2 активных ИП, роль в ЮЛ | **50 / 100** | СРЕДНЯЯ |
| Демов Максим Игоревич | активное банкротство, 6 производств | **0 / 100** | НИЗКАЯ |

Затем показывается поиск по договору `EV-20481`.

Все персонажи вымышлены. Демо-провайдеры детерминированы: один и тот же запрос
всегда даёт один и тот же результат. Каждый отчёт помечен баннером
`⚠️ ДЕМО-РЕЖИМ`.

Демо-прогон — это и smoke-тест: если он печатает три отчёта с тремя разными
категориями, пайплайн собран правильно.

## Telegram: BotFather и allowlist

1. Откройте [@BotFather](https://t.me/BotFather) → `/newbot` → получите токен.
2. Узнайте свой числовой Telegram ID (например, через
   [@userinfobot](https://t.me/userinfobot)).
3. Заполните `.env`:

```env
TELEGRAM_BOT_TOKEN=123456789:AA...
ALLOWED_TELEGRAM_USER_IDS=123456789,987654321
```

4. Запустите:

```bash
make run
# или
.venv/bin/python -m app.main
```

**Бот закрытый.** `AllowlistMiddleware` стоит перед всеми роутерами: пользователь
вне allowlist получает `Доступ запрещён.` и не доходит ни до одного handler'а —
поиск не запускается, `search_request` не создаётся, ни один внешний API не
вызывается. Логируется только факт отказа и user id, без содержимого запроса.

Пустой `ALLOWED_TELEGRAM_USER_IDS` не пускает никого: закрытый инструмент должен
отказывать по умолчанию, а не открываться.

## Импорт CSV

`/import` → отправить файл документом. Только для пользователей из allowlist.

### Формат

```csv
debtor_id,fio,birth_date,phone,contract_number,claim_number,debt_amount,address,vehicle_plate,vin,created_at
DEM-001,Тестов Андрей Сергеевич,12.03.1985,+7 (999) 123-45-01,EV-20481,ZA-1001,38400,"Москва, ул. Вымышленная, д. 1",А123ВС77,XW8ZZZ61ZKG011111,2026-01-15
DEM-002,Примеров Алексей Олегович,24.07.1979,89991234502,EV-20482,ZA-1002,154 200,"МО, г. Придуманск",О777ОО50,WVWZZZ1KZAW222222,2026-02-03
```

Все поля кроме идентифицирующих — необязательные. **Минимально достаточно `fio`
или `contract_number`.**

Поддерживается:

- разделители `,` `;` и табуляция (определяются автоматически);
- кодировки UTF-8 (в том числе с BOM) и Windows-1251;
- распространённые алиасы колонок: `id`, `фио`, `телефон`, `договор`, `долг`, …;
- суммы вида `38400`, `38 400`, `38 400,50`, `38400.50 руб.`;
- даты `ДД.ММ.ГГГГ`, `ДД-ММ-ГГГГ`, `ГГГГ-ММ-ДД`, `ДДММГГГГ`.

### Устойчивость

Одна плохая строка **не прерывает импорт**. Битые необязательные поля дают
предупреждение, а строка сохраняется без них. Строка без `fio` и без
`contract_number` отклоняется — сопоставить её не с чем.

```
Импорт завершён.

Всего строк: 482
Импортировано: 471
Пропущено: 11
Ошибки: 0
```

### Дедупликация

Детерминированная:

- есть `debtor_id` → upsert по нему;
- иначе → upsert по нормализованной комбинации `fio + birth_date + contract_number`.

Повторный импорт той же выгрузки **обновляет** записи, а не размножает их. Более
бедная выгрузка не затирает поля, заполненные предыдущей.

Демо-файлы: `data/demo_debtors.csv` (чистый) и `data/demo_debtors_messy.csv`
(с пустыми строками, дубликатом и битыми значениями — для проверки устойчивости).

Загрузка из командной строки:

```bash
make seed                                   # data/demo_debtors.csv
.venv/bin/python scripts/seed_demo.py path/to/export.csv
```

## Источники данных

| Источник | Состояние | Что нужно |
|---|---|---|
| Внутренние данные (CSV + БД) | **работает** | ничего |
| Demo-провайдеры | **работает** | ничего (`APP_MODE=demo`) |
| ФССП (через NewDB) | **реализовано, нужен ключ** | `NEWDB_API_KEY` |
| ЕФРСБ / Федресурс | **реализовано, нужен вендор** | базовый URL, ключ, field map |
| ФНС (ЕГРЮЛ/ЕГРИП) | **реализовано, нужен вендор** | базовый URL, ключ, field map |
| Суды | future | нет проверенной легальной интеграции |
| Недвижимость (ЕГРН) | future | нужен законный доступ |
| Транспорт по госномеру/VIN | future | нет законного provider'а |
| Залоги | future | — |
| Наследственные дела | future | — |
| 1С | future | см. раздел про 1С |

Источники со статусом future присутствуют в реестре и всегда возвращают
`NOT_CONFIGURED`. Они видны в отчёте как `○ Суды — не подключено`, потому что
названный пробел полезнее скрытого: оператор видит, что score посчитан без
судебных данных, а не считает, что там чисто.

### ФССП — через агрегатор NewDB

Прямой сервис ФССП (`api-ip.fssp.gov.ru`) выведен из эксплуатации и отвечает
`HTTP 410 Gone`. Исполнительные производства берутся из
[NewDB](https://newdb.net/docs/); ключ запрашивается на `access@newdb.net`.

```
POST https://api.newdb.net/v2
X-API-KEY: <token>

{"params": {"method": "fssp_person", "country": "ru",
            "lastname": "...", "firstname": "...", "secondname": "...",
            "dob": "YYYY-MM-DD", "regioncode": 77},
 "requestId": "<uuid>"}
```

Метод асинхронный. Конверт содержит `state`:
`queued` / `in_progress` / `restart` — ждать дальше, `complete` / `failed` —
терминальные. Опрос выполняется повторным POST на тот же `/v2` с тем же
`requestId` (так предписывает спецификация; заодно токен не попадает в query
string, а значит и в логи прокси).

Все семь параметров обязательны на стороне источника. Поэтому:

* нет ФИО или **нет даты рождения** → провайдер возвращает `insufficient_query`,
  а отчёт пишет «не проверено: недостаточно данных», а не «ничего не найдено»;
* отчество отсутствует → отправляется пустая строка (ключ обязателен).

`regioncode`: Москва — 77, Московская область — 50, `100` — все регионы ФССП.
«Москва + МО» выполняет два запроса и объединяет результат, дедуплицируя
производства по номеру. Регион без известного кода расширяет поиск до `100`,
а не подставляет произвольный.

**Важная особенность, ради которой стоит читать этот абзац.** Отклонённый или
отсутствующий ключ NewDB возвращает не `401`, а **`HTTP 200` с
`state: "failed"`**. При наивном разборе это выглядит как пустой результат —
то есть чистый раздел ФССП по должнику, которого никто не проверял. Поэтому
любой терминальный `failed` отображается в статус ошибки
(`unauthorized` / `payment_required` / `bad_request`), а конверт `complete` без
секции `results.fssp_person.result.data` — в `unexpected_schema`. `NO_RESULTS`
возвращается только когда источник реально ответил и `data` пустой.

Нормализация записи `data[]`: номер производства очищается от «от <дата>»,
из `Debtor` извлекаются ФИО и дата рождения, из `SubjectAndDebtAmount` —
предмет взыскания и сумма (приоритет у остатка долга — это то, что реально
конкурирует с нашим требованием), непустой `CompletionDateOrReason` означает
оконченное производство.

### ЕФРСБ и ФНС — vendor-agnostic адаптеры

Эти данные доступны через разных лицензированных API-вендоров, у каждого своя
схема ответа. Вместо того чтобы выдумать одну схему и захардкодить её, адаптеры
читают **field map** — небольшой JSON, описывающий, где в ответе лежат записи и
какие поля им соответствуют.

```env
FEDRESURS_BACKEND=generic_json
FEDRESURS_BASE_URL=https://api.вашвендор.ru
FEDRESURS_SEARCH_PATH=/v1/bankruptcy/search
FEDRESURS_API_KEY=...
FEDRESURS_AUTH_STYLE=bearer          # bearer | header | query | basic | none
FEDRESURS_FIELD_MAP=./config/field_maps/my_vendor.json
```

Примеры карт: `config/field_maps/example_fedresurs.json`,
`config/field_maps/example_fns.json`. Это **примеры структуры, а не описание
реального API** — пути нужно заменить на те, что указаны в документации вашего
вендора.

Без field map провайдер остаётся `NOT_CONFIGURED`: разобрать ответ нечем, а
делать вид, что источник подключён, нельзя.

Доступен встроенный демо-бэкенд: `FEDRESURS_BACKEND=demo`, `FNS_PROVIDER=demo`.

## Recovery Score

Детерминированный движок. Никакой LLM, никакой случайности: один и тот же отчёт
всегда даёт один и тот же результат, и каждый балл объясним.

Базовая оценка — 50, далее применяются факторы:

**Плюсы**

```
+10  действующее подтверждённое ИП
 +5  активная роль в ЮЛ            (суммарный бонус за бизнес ≤ +20)
+15  подтверждённое имущество
 +8  подтверждённый транспорт
+10  ЕФРСБ проверен, банкротства нет
 +5  ФССП проверена, активных производств нет
```

**Минусы**

```
-35  активное банкротство
-10  завершённое банкротство в анамнезе
 -5  1–2 активных исполнительных производства
-15  3–5
-25  более 5
 -5  подтверждённая сумма взысканий от 100 000 ₽
-10  от 500 000 ₽
-15  от 1 000 000 ₽
 -3  за каждую прекращённую бизнес-связь (не более -9)
```

Результат ограничивается диапазоном 0–100:

```
0–34     НИЗКАЯ
35–69    СРЕДНЯЯ
70–100   ВЫСОКАЯ
```

### Уверенность данных — отдельное число

`score` отвечает на вопрос «насколько долг выглядит взыскиваемым», а
`score_confidence` — на вопрос «какую часть картины мы вообще увидели». Это
разные вопросы, и хороший score, построенный на одном доступном источнике, —
не надёжный score.

Confidence считается как взвешенное покрытие ответивших источников и
понижается, если:

- поиск выполнен без даты рождения и ИНН (×0.7);
- часть записей сопоставлена лишь как «возможные совпадения» (×0.9).

Источник со статусом `NOT_CONFIGURED`, `UNAVAILABLE` или `ERROR` **не даёт ни
бонуса, ни штрафа** — он не проверен, и отчёт прямо перечисляет такие пробелы в
разделе «Ограничения оценки».

Отчёт не даёт юридических указаний. Он пишет «Предварительная перспектива
взыскания: СРЕДНЯЯ», перечисляет плюсы и риски и завершается фразой
«Оценка является аналитической и не заменяет юридическую проверку».

## Сопоставление личности

Самая ответственная часть системы.

Одинаковое ФИО из разных источников — **это ещё не один человек**. Действовать по
чужим исполнительным производствам одинаково неправильно и дорого, поэтому
совпадение по имени само по себе никогда не даёт подтверждённый статус.

Каждой внешней записи присваивается `match_confidence` в диапазоне 0.0–1.0:

| Сигнал | Вклад |
|---|---|
| полное совпадение ФИО | 0.60 |
| совпадают только фамилия и имя | 0.45 |
| ФИО не сопоставлено | 0.25 |
| совпадает дата рождения | +0.30 |
| **дата рождения не совпадает** | **→ 0.05, запись отбрасывается** |
| совпадает ИНН | +0.30 |
| ИНН не совпадает | −0.35 |
| совпадает телефон (внутренние данные) | +0.20 |
| нет уточняющих идентификаторов | −0.05 |
| распространённая фамилия без уточнений | −0.05 |

```
≥ 0.85   Подтверждённое совпадение
≥ 0.55   Возможное совпадение
<  0.55  Слабое совпадение — показывается, но в скоринге не участвует
```

Записи, найденные по точному внутреннему идентификатору (номер договора,
`debtor_id`, VIN), получают порог 0.95: сам идентификатор и есть доказательство.

## Docker

```bash
make docker-build     # docker compose build
make docker-up        # docker compose up -d
make docker-down
```

Образ многостадийный, работает из-под непривилегированного пользователя,
применяет миграции при старте. SQLite и загруженные выгрузки живут в томе
`bot-data`. Секреты берутся из `.env` и не попадают в образ.

С PostgreSQL:

```bash
docker compose --profile postgres up -d
```

и в `.env`:

```env
DATABASE_URL=postgresql+asyncpg://collector:collector@postgres:5432/collector_bot
```

(для PostgreSQL поставьте extra: `pip install -e '.[postgres]'`).

**Локальный запуск на SQLite не требует Docker вообще** — достаточно
`make install && make demo`.

## Тесты, линт, типы

```bash
make test         # 279 тестов
make lint         # ruff check + ruff format --check
make typecheck    # mypy --strict, включая тесты
make check        # всё вместе
```

Покрыто, в частности:

- **скоринг** — банкротство роняет score; много производств роняет; действующая
  бизнес-связь поднимает; **недоступный провайдер не считается отсутствием
  записей**; score всегда в 0–100; результат детерминирован;
- **сопоставление** — ФИО + дата рождения; то же ФИО с другой датой рождения;
  только ФИО; отсутствующая дата рождения; распространённые фамилии; название
  ЮЛ не сопоставляется с человеком;
- **провайдеры** (через `respx`, фикстуры повторяют реальную схему NewDB) —
  успех, пустой результат, polling `queued → in_progress → complete`, исчерпание
  бюджета опроса, `state: failed` при отклонённом токене и при нулевом балансе,
  401/403, 402, 429 с ретраем, 5xx, битый JSON, неузнанная схема, `complete`
  без секции результата, баг внутри провайдера;
- **агрегация** — ошибка ФНС не уничтожает результат ФССП; неподключённый
  источник не рендерится как «чисто»; отчёт не выдаёт юридических указаний;
- **безопасность Telegram** — неавторизованный пользователь не доходит до
  handler'а и не создаёт запись поиска; пустой allowlist не пускает никого;
- **маскирование** — телефон, паспорт, ИНН, VIN и токены не попадают целиком в
  историю, аудит и логи;
- **CSV** — валидный импорт, битая строка, отсутствующие необязательные поля,
  дубликаты, некорректная сумма, кодировки, лимиты;
- **end-to-end сценарии бота** — реальные `aiogram`-апдейты через реальный
  диспетчер: `/start`, полный поиск физлица, поиск по договору, отказ
  неавторизованному, история, кэш, `/import`, `/status`;
- **старт приложения** — отказ без токена, отказ с пустым allowlist, сборка
  контейнера зависимостей и отсутствие расхождений между моделями и миграцией;
- **госпошлина** — все границы ступеней ст. 333.19 НК РФ, потолок, монотонность
  на стыках, округление до полного рубля, половина ставки для приказа;
- **вердикт** — каждое правило и приоритет между ними: банкротство перекрывает
  хороший score, нехватка данных даёт «проверить», а не «не подавать»;
- **массовая проверка** — смета, переиспользование кэша, ограничение сверху,
  порядок очереди по числовому ключу (деньги хранятся текстом), битая строка не
  роняет прогон, прогресс, экспорт в CSV и маскирование телефонов.

## Безопасность и приватность

- Секреты только через `.env`; `.env` в `.gitignore`, в репозитории лежит
  `.env.example`.
- `STORE_RAW_RESPONSES=false` и `STORE_SENSITIVE_IDENTIFIERS=false` по умолчанию.
- В историю пишется маскированный запрос и односторонний хэш, не сам запрос.
- Паспорт используется только для сопоставления с внутренней базой, никогда не
  уходит во внешние источники, и при выключенном флаге не сохраняется целиком.
  В логах — `45** ******`. Сообщение оператора с номером удаляется из чата.
- Телефон хранится маскированным (`+7 (999) ***-**-67`) плюс хэш для поиска;
  полный номер — только при явно включённом флаге.
- Логи проходят через процессор-редактор, который вычищает токены, ключи,
  пароли, телефоны и паспорта, даже если что-то просочилось немаскированным.
- `/audit` показывает журнал действий: кто, что и когда — без содержимого
  запросов.

## Границы проекта

Проект **не реализует и не будет реализовывать**:

- базы утечек и покупку слитых данных;
- нелегальный «пробив»;
- обход авторизации и капчи;
- scraping закрытых кабинетов;
- получение банковских счетов и остатков;
- скрытое определение местоположения;
- Telegram userbot / Telethon-интеграции с чужими «пробивными» ботами;
- автоматическое определение имущества по ФИО без законного provider'а.

Sherlock и Void рассматриваются исключительно как UX-референс.

Если источник нельзя подключить стабильно и законно — он возвращает
`NOT_CONFIGURED` или `UNAVAILABLE`. Отсутствие доступа не выдаётся за отсутствие
данных.

## Roadmap

Сделано: массовая проверка выгрузки, вердикт с расчётом госпошлины, очередь
взыскания и выгрузка в CSV.

Дальше, в порядке ценности для задачи:

1. **Досдать методы NewDB** — банкротство (`bankrot_person`), залоги и залог
   авто по VIN (`pledge_person`, `pledge_vin`), статус ИП (`egrul_ip`),
   арбитраж (`arbitr_person`). Один ключ уже подключён, адаптер написан:
   это добавление методов, а не новая интеграция.
2. **Наследственные дела** — реестр ФНП. Для старых долгов это фактор №1
   «не подавайте»: иск к умершему ничтожен, требование идёт наследникам.
3. **Telegram Mini App** — очередь на восемьсот строк с сортировкой и
   фильтрами; в сообщениях такое не показать. Заодно закрывает запрос
   «телега + веб-интерфейс» одним куском.
4. **Периодическая перепроверка** — расписание поверх существующего кэша:
   банкротство и производства появляются со временем.
5. **XLSX-импорт** — рядом с CSV-парсером, тот же `ImportService`.
6. **1С** — `OneCODataProvider` вместо/рядом с CSV, после получения доступа.
7. **PostgreSQL в проде** — миграции и репозитории уже совместимы.
