# ТЗ на подключение источников

Документ для стороннего разработчика, который пришёл в collector-bot впервые и
берётся за источники данных: он написан так, чтобы подключение можно было
довести до конца, ни разу не спросив автора.

Всё ниже проверено по коду ветки `main` (`df5b6f8`) и прогонами на проде
08.09.2026. Гейты на этом коммите зелёные. Проверять их надо **по коду
возврата**, а не по хвосту вывода:

```bash
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/mypy
.venv/bin/pytest
```

То же одной командой — `make check`.

Разведка по вендорам — кто ищет банкротство без ИНН, у кого есть собственный
официальный API, кто мимикрирует под Росреестр и почему по БКИ ответ
окончательный — идёт отдельным документом `docs/VENDORS.md`; проверка ещё не
закончена, и в репозитории его пока нет. Здесь она не дублируется: в этом
документе только то, что делается руками в этом репозитории.

**С чего начать.** Прочитать «Карту работ» ниже — она отвечает на вопрос, что уже

## 1. Мост «паспорт → ИНН»: починен и работает

### 1.1. Зачем мост нужен

Три источника отчёта ищут физлицо **только** по `innfiz` — двенадцатизначному
ИНН физлица. ФИО с датой рождения они не принимают: живой сервис отвечает
`Отсутствует обязательный параметр: innfiz`.

| Раздел отчёта | Провайдер | Метод NewDB | Гейт |
|---|---|---|---|
| Банкротство (ЕФРСБ) | `app/providers/fedresurs.py` | `bankrot_person` | `missing_input_for` → `MissingInput.INN` (стр. 207) |
| Статус ИП и роли в ЮЛ (ФНС) | `app/providers/fns.py` | `egrul_ip` | то же (стр. 193) |
| Арбитраж (kad.arbitr.ru) | `app/providers/court.py` | `arbitr_person` | то же (стр. 91) |

Все три написаны одной строкой:
`return () if individual_inn(subject) else (MissingInput.INN,)`, и в `_fetch` без
ИНН возвращают `insufficient_query`, не делая ни одного обращения. Четвёртый,
косвенно: `arbitr_legal` (арбитраж компаний должника) питается ответом
`egrul_ip` — нет ИНН физлица, нет списка компаний, нет и этой цепочки.

`individual_inn` (`app/providers/newdb.py:796`) отдаёт ИНН, только если в нём
ровно 12 цифр. Десятизначный — идентификатор юрлица; `innfiz` валидируется как
двенадцать, и десятизначное значение купило бы отклонённый, но всё равно
оплаченный вызов (`cost: 1` на живом эндпоинте) сразу у трёх источников.

Масштаб на этом развёртывании: **ИНН нет ни у одного из 2052 должников**, и
взяться ему неоткуда — СНИЛС в выгрузке тоже нет ни у кого. Без моста три раздела
отчёта по всей базе — «не проверено», навсегда. С мостом они проверяются у
**1300** должников: полных паспортов в базе 1304, и четверым из них не хватает
даты рождения. Мост не увеличивает покрытие отчёта: он делает возможной проверку
тех, кто в покрытие уже входит.

### 1.2. Почему это законный путь

Мост зовёт метод NewDB `passport_fns`, за которым стоит сервис ФНС, выдающий ИНН
физического лица по ФИО, дате рождения и серии-номеру паспорта. Это официальная
государственная функция: сведения выдаёт держатель реестра в ответ на корректно
составленный запрос, и получаемое — один идентификатор, тот самый, которым по
закону оперируют реестры банкротства, ЕГРИП и картотека арбитражных дел.

Инженерное следствие, о котором стоит помнить при смене источника: экран
«Откуда данные» говорит оператору «не пользуется базами утечек и „пробивом“»
(`app/bot/sources.py:141`). Это отгруженное пользователю утверждение, и если
происхождение данных изменится, строку надо править вместе с источником —
иначе бот начнёт говорить о себе неправду.

### 1.3. Секция ответа выбирается по факту, а не по документации

Это первое из двух мест, где чужая документация стоила молчаливой поломки;
второе — подстановка `{phone}` в путь источника (3.2). Знать надо про оба: обе
поломки выглядели как отсутствие данных у других, а были нашими.

Документация вендора говорит, что `passport_fns` отвечает в `results.company`.
Живой конверт с прода от 08.09.2026 содержит
`results.passport_fns.result.data[0].innfiz`, а секции `company` в нём нет вовсе:
метод отвечает по своему имени, как все остальные. Код верил документации, читал
`company`, ничего там не находил и поднимал `unexpected_schema` **на каждом
успешном ответе** — вместе с уже полученным ИНН, лежавшим в том же конверте
рядом.

Дефект был тихим и потому дорогим. Без ИНН молчат сразу три источника —
банкротство, статус ИП и арбитраж, — и в отчёте они честно писали «нужен ИНН
физлица». То есть своя поломка выглядела как нехватка данных у заказчика и
прожила бы до первой ручной сверки.

Починено в `_section_of` (`app/providers/newdb.py:360`): берётся та секция,
которая в ответе **есть** — сперва названная вызывающим (`RESULT_SECTION`,
`app/providers/identity_bridge.py:74-76`), потом одноимённая методу. Обе формы
рабочие, и возврат вендорского поведения обратно ничего не сломает. Конверт, в
котором нет ни одной известной секции, — по-прежнему `unexpected_schema`, а не
молчаливый успех: терпимость к двум формам не должна стать терпимостью к любой.
Проверено живым вызовом: ИНН получен.

Закреплено `tests/test_identity_bridge.py::test_both_shapes_of_the_answer_are_read`
(`:178`, параметризован обеими секциями) и
`::test_an_answer_in_no_known_section_is_still_a_schema_error` (`:210`).

Вывод дороже самого дефекта: **форму ответа нового источника проверяют живым
вызовом, а не страницей документации.** Тест, написанный по документации,
сторожит документацию, а не вендора: прежний `T-2` требовал ровно обратного тому,
что делает живое API, и был бы прав — если бы документация была верна.

### 1.4. Что уже включено и как это проверить

Правок `.env` здесь больше не требуется: всё включено, выгрузка переимпортирована.
Ниже — состояние и способ убедиться в нём своими глазами, а не по этому документу.

**Мост.** `PassportInnProvider.is_configured` = `newdb_configured and
inn_bridge_enabled` (`app/providers/identity_bridge.py:146`). Состояние печатается
в лог при старте: `providers.ready ... inn_bridge=True`
(`app/providers/registry.py:224-228`). На проде там `True` — `NEWDB_API_KEY` и
`INN_BRIDGE_ENABLED=true` стоят.

Больше это состояние нигде не видно: `/status` перечисляет источники по
`container.registry.external` (`app/bot/handlers/admin.py:79`), а мост в
`external` не входит намеренно (см. 1.7, пункт 2) — значит, кроме лога старта,
спросить не у кого.

**Хранение паспорта.** `STORE_SENSITIVE_IDENTIFIERS=true` на проде. Прочитайте
1.5 прежде, чем здесь что-нибудь менять: флаг глобальный, меняет не только
паспорт, и отката у него нет. Что флаг доехал, видно из бота: `/status` печатает
строку «хранение полных идентификаторов: включено» (`app/bot/handlers/admin.py:72`,
слова даёт `_flag` на `:24-25` — «включено» или «выключено», третьего нет).

Флаг разворачивает не базу, а импорт: полный номер пишется единственным местом —
`ImportService._to_model`, `passport=row.passport if store_raw else None`
(`app/services/import_service.py:356`). Маска (`passport_masked`) пишется всегда и
необратима (`mask_passport`, `app/utils/masking.py:63`), развернуть её нельзя ни
при каком флаге. Поэтому выгрузку и пришлось прислать заново — тем же файлом,
командой `/import` в боте (owner-only, `app/bot/router.py:68`). Повторный импорт
обновляет, а не множит: ключ дедупликации при наличии `debtor_id` —
`stable_hash("id", debtor_id)` (`app/providers/internal/csv_schema.py:349`),
`DebtorRepository.upsert` перезаписывает только непустыми значениями
(`app/db/repository.py:114`). Файл обязан быть **тем же**: другая выгрузка без
`debtor_id` даст новые строки вместо обновления старых.

Настройки читаются один раз при сборке контейнера приложения (`app/container.py`,
`get_settings` под `lru_cache`), правка `.env` без рестарта не действует. Миграции
накатываются самим приложением на старте (`app/main.py`, `_upgrade_schema`),
отдельной команды не нужно.

```bash
docker compose -f docker-compose.prod.yml up -d --force-recreate bot
```

**Проверка по базе.** В образе `python:3.12-slim` нет CLI `sqlite3`, поэтому через
модуль. Путь базы задан прод-компоузом: `DATABASE_URL` по умолчанию
`sqlite+aiosqlite:////app/var/collector_bot.db`. Флаг `-T` обязателен: без него
`exec` требует терминал и падает на heredoc, не выполнив ни строки.

```bash
docker compose -f docker-compose.prod.yml exec -T bot python - <<'PY'
import sqlite3
db = sqlite3.connect("/app/var/collector_bot.db")
print(db.execute("""
    SELECT count(*)               AS должников,
           count(passport)        AS полных_паспортов,
           count(passport_masked) AS масок,
           count(inn)             AS инн,
           count(birth_date)      AS дат_рождения
    FROM debtors""").fetchone())
print("готовы к мосту (верхняя граница):", db.execute("""
    SELECT count(*) FROM debtors
    WHERE passport IS NOT NULL
      AND inn IS NULL
      AND birth_date IS NOT NULL
      AND fio IS NOT NULL AND instr(trim(fio), ' ') > 0""").fetchone()[0])
PY
```

**Это замер с сервера, а не свойство кода.** В репозитории базы нет
(`find . -name '*.db'` даёт только кэш mypy), воспроизвести цифры локально нечем.
До поднятия флага было `(2052, 0, 1304, 0, 2036)` — ноль полных паспортов при 1304
масках. После переимпорта полных паспортов **1304**, к мосту готовы **1300**.
Колонка `inn` осталась нулевой и останется: добытый ИНН живёт в
`search_requests.subject_json` (1.5), а в `debtors` не пишется. **Повторите замер
сами, прежде чем называть владельцу любые числа.**

Второй запрос — верхняя граница, а не точное число. Точное условие даёт
`PassportInnProvider.will_query` (`identity_bridge.py:118`): `is_configured`
**и** `is_needed` (ИНН не двенадцатизначный) **и** `missing_bridge_input(subject)
is None` (паспорт, ФИО, дата рождения). ФИО при этом должно разбираться
`parse_fio` — два-три слова (четвёртое допускается только как частица отчества из
`NAME_PARTICLES`), буквы, дефис и апостроф; SQL этого не проверяет.

Расхождение цифр в репозитории, чтобы вы на него не наткнулись позже: 1474
паспорта названы в двух местах — докстринг
`migrations/versions/0013_debtor_passport.py` и комментарий над колонкой
«паспорт» в `app/providers/internal/csv_schema.py:142`; масок в базе 1304, и эта
цифра уже стоит в `docs/STATE.md:213` и `tests/test_review_fixes.py`. Числа про
разное — строки выгрузки против должников после дедупликации, — поэтому верить
надо запросу выше, а правки нужны обеим устаревшим цифрам, не одной.

**Кэш.** Проверка того же субъекта, сделанная в последние `CACHE_TTL_HOURS` (24 по
умолчанию), вернётся из кэша, и мост не сработает. Ключ кэша считается **по
вопросу оператора**, до обогащения (`build_query_hash`,
`app/services/search.py:760`) — это сделано намеренно, чтобы тот же вопрос через
час не оплачивал мост заново. Чтобы проверить мост на живом должнике сразу —
кнопка «Спросить заново» (`force_refresh`).

### 1.5. Чем `STORE_SENSITIVE_IDENTIFIERS` является для владельца

Флаг поднят на проде — значит всё перечисленное ниже уже произошло, а не ждёт
решения. Это не настройка моста. Это один глобальный флаг приватности
(`app/config.py:198`), и он меняет пять вещей сразу:

* `debtors.passport` — полные серия и номер паспорта 1304 человек, **бессрочно**
  (`import_service.py:356`). Ретеншен (`app/services/retention.py:34`,
  `purge_once`) чистит `search_requests`, `share_links` и `query_cards`; таблицу
  `debtors` он не трогает вовсе — сроков хранения у выгрузки нет.
* `debtors.phone` — полные телефоны, тем же `_to_model`
  (`import_service.py:352`).
* `search_requests.subject_json` — паспорт перестаёт вырезаться из сохранённого
  запроса (`redact_subject`, `app/services/search.py:791`). Здесь срок есть:
  `HISTORY_RETENTION_DAYS`, 90 суток по умолчанию.
* **Выгрузка очереди в CSV** — `queue_to_csv(items, include_phone=...)`
  (`app/services/export.py:41`, вызов — `app/bot/handlers/batch.py:614`). Файл
  уходит документом в чат, и с поднятым флагом он несёт полные телефоны, а из
  подписи пропадает оговорка «Телефоны маскированы» (`batch.py:622`). Это
  единственное последствие, которое покидает сервер.
* **Подсказка в карточке запроса** — `PASSPORT_HINT_STORED` вместо
  `PASSPORT_HINT` (`app/bot/card_view.py:294`, `:299`, ветка на `:608`):
  оператору прямо сказано, что присланный номер сохранится в базе. Единственное
  место, где включённый флаг виден оператору; убирать его нельзя — это и есть его
  информированность.

Что флаг **не** отменяет и что трогать не надо ни при каких условиях:

* `raw_response` моста не сохраняется никогда, независимо от
  `STORE_RAW_RESPONSES` (`identity_bridge.py:268`): вендор возвращает присланные
  `params` эхом, то есть серию и номер;
* текст вендорской ошибки проходит через `scrub_passport` **до** записи в
  `error_message` (`app/providers/newdb.py:105`) — эта колонка пишется мимо обоих
  флагов приватности, и вендор охотно цитирует параметры в отказе;
* `redact_sensitive_json` вырезает `snils`, `passport`, `birth_place` и прочее из
  сохраняемых тел безусловно (`app/utils/masking.py:132`);
* у таблицы `query_cards` колонок `passport` и `phone` нет вовсе
  (`app/db/models.py:316`).

Отдельный от паспорта факт хранения: **добытый ИНН остаётся в базе при любом
флаге**. `redact_subject` (`search.py:791`) вырезает паспорт и телефон, но `inn`
оставляет в обоих режимах — то есть после включения моста в
`search_requests.subject_json` появляется ИНН, полученный от ФНС, и живёт там
`HISTORY_RETENTION_DAYS`. В перечне обрабатываемых персданных он должен быть
назван наравне с паспортом.

**Отката у решения нет.** Снятие флага останавливает только новые записи: кода,
чистящего `debtors.passport` и `debtors.phone`, в проекте не существует —
ретеншен работает по `search_requests`, `share_links` и `query_cards`. Вычищать
придётся руками, `UPDATE debtors SET passport = NULL, phone = NULL`, и знать это
надо до включения, а не после.

Организационно это решение о персональных данных, а не настройка по умолчанию, и
принимает его владелец. Код от него отказывается сам: умолчание `false`, и
никакой сценарий его не поднимает. Минимум, что должно быть сделано **до**
включения: шифрование тома `bot-data` (или диска целиком), ограниченный доступ к
хосту, резервные копии в том же режиме защиты, что и сама база, и запись в
перечне обрабатываемых персданных о том, что паспорт обрабатывается ради
получения ИНН и ни для чего больше. Разработчик, включающий флаг без явного
письменного распоряжения владельца, принимает это решение за него.

### 1.6. Как убедиться, что мост не тратит деньги впустую

Два гейта, оба в `app/providers/identity_bridge.py`:

* **`is_configured`** (стр. 146) — ключ **и** явно поднятый флаг.
  `BaseProvider.fetch` (`app/providers/base.py:155`) при `False` возвращает
  `NOT_CONFIGURED`, не заходя в `_fetch`: ноль обращений, ноль списаний. Платный
  вызов, добавляющийся сам собой, — ровно то, чего смета не покажет.
* **`missing_bridge_input`** (стр. 184) — единственная лестница `_bridge_gap`
  (стр. 203): паспорт → ФИО → дата рождения. Зовётся дважды: в `_fetch` до
  всякого HTTP и в `will_query` (стр. 118). Текст и машинное поле берутся из
  одной лестницы (`missing_bridge_fields`, стр. 197), поэтому разъехаться не
  могут.

`will_query` — «дойдёт ли дело до платного вызова» — единственный источник истины
о платности, и переписывать его условия рядом с ним запрещено. Зовут его двое:

* смета прогона: `BatchService._scan` (`app/services/batch.py:429`) →
  `BatchEstimate.bridge_calls` →
  `requests = to_query * providers_per_debtor + bridge_calls` (`batch.py:188`);
* кнопка «а если бы паспорт был»: `passport_would_help`
  (`app/bot/report_actions.py:143`, вызов `will_query` на `:153`) подставляет
  паспорт-заглушку и спрашивает сам мост. Флаг вида `resolves_inn_by_passport`
  уже пробовали — его никто не проставлял, и кнопка не появлялась вовсе.

Третье место спрашивает у моста другое и делает это намеренно: карточка покрытия
`coverage._providers` (`app/services/coverage.py:40-52`) зовёт `is_needed`, а не
`will_query`, и убирает мост только тогда, когда ИНН физлица уже известен, —
иначе оператору продавали бы платный вызов за уже имеющийся ответ. Заменить там
`is_needed` на `will_query` значит убрать мост из карточки у всех, у кого паспорта
ещё нет, то есть стереть строку «что даст паспорт» ровно там, где паспорт —
единственный доступный ход.

И `SearchService._resolve_inn` (`app/services/search.py:312-313`):
`if bridge is None or not bridge.is_needed(subject): return subject, None` —
вызова нет и строки в отчёте нет вовсе, потому что объяснять нечего.

#### Дефект, который надо закрыть — флаг уже включён

**Смета покажет ноль вызовов моста, а прогон их сделает.** Проверено измерением:

* `_subject_for` (`app/services/batch.py:809-819`) не заполняет `passport` —
  смета считает `will_query` на субъекте без паспорта, и он всегда `False`;
* в самом прогоне паспорт доезжает другим путём:
  `SearchService.search_detailed` (`app/services/search.py:130`) сперва
  спрашивает внутреннюю базу, `_enrich_from_internal` (`search.py:610`)
  подставляет `record.passport` из `debtors.passport`, и мост срабатывает.

Замер (импорт одной строки с паспортом при `STORE_SENSITIVE_IDENTIFIERS=true`,
`external=[]`, HTTP замокан):

```text
STORED passport: 4015350278 | masked: 40** ******
BATCH SUBJECT passport: None
ESTIMATE bridge_calls: 0 | enabled: True
HTTP CALLS DURING RUN: 1
BRIDGE RESULT: success
```

Зонд, которым это измерено, лежит в рабочем дереве —
`tests/test_zz_probe_bridge.py`, помечен временным в первой же строке докстринга.
Он **не мусор и не эталон**: это способ перезамерить утверждения выше. Перезамерьте
им и удалите файл в той же правке, которой закроете дефект.

Точная граница недоучёта: мост срабатывает в прогоне не у всех, у кого есть
паспорт. `_enrich_from_internal` возвращает субъект нетронутым при неточном
попадании во внутреннюю базу (`if not exact or not records: return subject`,
`app/services/search.py:633-634`), а точным считается совпадение по `debtor_id`,
телефону, номеру договора или заявки. Телефона в выгрузке нет ни у кого и не
будет (раздел 2), поэтому реальное занижение — **не больше 1300 вызовов**, то
есть 2 600 ₽ по тарифу из раздела 5, не показанных оператору до нажатия. Для
проекта, где смета есть то, что оператор подтверждает **до** списания, это брак,
а не мелочь.

Чинится в `_subject_for` строкой `passport=row.passport`: тогда смета и прогон
считают одно и то же, и вместо контр-строки «ИНН неизвестен у N» появится «ИНН по
паспорту (ФНС): N вызовов — по одному на должника»
(`app/bot/handlers/batch.py:215`).

Вместе с этим устареют два текста, обещающие обратное, — их надо править в той же
правке: докстринг `BatchService._scan` (`batch.py:388-393`) и README, раздел «ИНН
по паспорту — мост к трём источникам» (`README.md:1038`, утверждение на `:1078`).
Оба говорят «у `Debtor` нет паспортной колонки»; колонка есть с миграции `0013`
(`app/db/models.py:55`).

Про рубли: `PROVIDER_REQUEST_COST` по умолчанию `0`, и это значит «цена не
задана», а не «бесплатно» — смета честно говорит, что рублёвую сумму назвать
нечем (`BatchEstimate.cost` возвращает `None`). Тариф известен и записан в разделе
5; чтобы владелица видела сумму до списания, его надо внести.

### 1.7. Границы: что нельзя трогать

1. **Состояния источника называет только `app/services/reporting.py`.** У моста
   своя ветка `_bridge_source_line` (стр. 1072) — общая напечатала бы
   «✓ … — 0 зап.» ровно там, где мост только что сделал всю проверку возможной.
   Пять исходов, пять разных строк: «ИНН получен, банкротство, ИП и арбитраж
   проверены по нему» / «проверено, ИНН по этим данным не найден» (плюс
   «; отчество не указано — совпадение в ФНС могло не найтись по этой причине»,
   если ФИО из двух слов) / «не подключено» / «недоступно (код)» / «Паспорт не
   указан — ФНС ищет ИНН только по серии и номеру». У трёх источников, которым не
   хватило ИНН, причину дописывает `_bridge_note` (стр. 1188): «ФНС не нашла ИНН
   по паспорту.» — это `NO_RESULTS`; «Получить ИНН по паспорту не удалось (код) —
   это не значит, что записей нет.» — это `UNAVAILABLE`; «Получение ИНН по
   паспорту не подключено.» — это выключенный флаг. Заводить второй набор слов
   нельзя ни при каких условиях: за различение уже заплачено вызовом, и терять его
   в тексте — значит выбросить купленное.
2. **Мост — не источник фактов.** Он вне `configured_names`
   (`app/providers/registry.py:113`) и вне `PROVIDER_CONFIDENCE_WEIGHTS`
   (`app/domain/scoring.py:147`), записей не приносит, уверенность отчёта не
   повышает. Перенести его в `external` — значит запустить его
   `asyncio.gather`-ом параллельно с теми тремя, кого он кормит.
3. **В строке моста сам ИНН не печатается ни в каком виде, включая
   маскированный** (`_bridge_source_line`, стр. 1072). Причина не приватность, а
   согласованность двух показов: восстановленный из кэша `ProviderResult`
   значения не несёт, и «получен 77\*\*\*\*\*\*\*\*03» на первом показе против
   «получен» на втором — то самое расхождение, которое чинит обогащение субъекта
   в `_load_cached`. Это правило про строку источника, а не про продукт целиком:
   заголовок отчёта `👤 {subject.display_name}` и подпись запроса в истории
   `describe_subject` (`app/services/search.py:827`) печатают `mask_inn`
   законно — первый чтобы поиск по одному ИНН не назывался «—», вторая чтобы к
   такой строке истории можно было вернуться. Вырезать их, приняв правило за
   общее, нельзя.
4. **Секция ответа не угадывается по имени и не берётся из документации.**
   Живой `passport_fns` отвечает в `results.passport_fns`, документация вендора
   обещает `results.company`; читаются обе, и выбирает между ними `_section_of`
   по факту наличия (`app/providers/newdb.py:360`, подробно — 1.3). Свести это
   обратно к одной секции нельзя ни в ту, ни в другую сторону: чтение
   единственной названной формы уже стоило `unexpected_schema` на каждом успешном
   ответе. Именованный параметр `NewDBClient.call(..., result_section=...)`
   (`app/providers/newdb.py:153`) остаётся подсказкой, а не приговором.
5. **Двенадцать цифр — не перестраховка.** Собственные примеры вендора
   противоречат друг другу (`fiz_02` отдаёт десятизначное, `fiz_04` —
   двенадцатизначное). Приняв десятизначное, вы купите отклонённый и всё равно
   оплаченный вызов у трёх источников. Несколько разных ИНН в ответе —
   `ambiguous_identity`, а не «взять первый»: чужой ИНН подошьёт должнику чужое
   банкротство, и инверсия хуже ненахождения.
6. **`secondname` не отправляется пустым**
   (`app/providers/newdb.py:759-763`): сервис отвергает пустое значение, а не
   отсутствие ключа. Отказываться от вызова без
   отчества тоже нельзя — это заблокировало бы всех, у кого его нет; вместо этого
   к пустому ответу приписывается оговорка.
7. **В текстах для оператора нет ни «NewDB», ни `passport_fns`, ни
   `INN_BRIDGE_ENABLED`.** «ФНС» — можно и нужно: это тот, кто отвечает, и
   оператору это говорит о качестве ответа.

## 2. Вход по номеру телефона: чего нет и что из этого следует

### 2.1. Телефона нет ни в выгрузке, ни в 1С

Первая редакция этого документа была построена на предположении, что телефон в 1С
есть и его достаточно выгрузить колонкой. Предположение опровергнуто владелицей
дословно: **«телефона нет в 1с»**. Не «не выгружен» и не «выгружен не так» — нет
вообще, в самой таблице. Просить колонку не у кого: её нечем наполнить.

Замер на проде 08.09.2026 говорит то же самое с другой стороны — телефон есть у
**0 из 2052** должников. Полный ряд по полям, которым меряется всё остальное в
этом документе:

| Поле | Заполнено | Из скольких |
|---|---|---|
| ФИО | 2052 | 2052 |
| Дата рождения | 2036 | 2052 |
| Госномер | 2008 | 2052 |
| Адрес | 2033 | 2052 |
| Паспорт (полный) | 1304 | 2052 |
| ИНН | 0 | 2052 |
| СНИЛС | 0 | 2052 |
| Телефон | 0 | 2052 |

СНИЛС стоит нулём по причине более сильной, чем у остальных: колонки под него в
схеме нет вовсе (`grep -n snils app/db/models.py` — ноль совпадений), и заводить
её незачем (8.2).

То же записано в `docs/STATE.md:215`: «Телефона в выгрузке нет ни у кого и не
будет — это часть таблицы 1С». Так же считает и код: докстринг `_resolve_name`
(`app/bot/handlers/query_card.py:379-386`) объясняет, почему имя добывается на
стороне, а не поиском по номеру.

### 2.2. Значит, вход по голому номеру возможен только через внешний источник

По номеру телефона не ищет ни один реестр, с которым работает бот: ФССП — по ФИО,
дате рождения и региону; ЕФРСБ, ЕГРИП и картотека арбитража — по ИНН; ЕГРН — по
адресу или кадастровому номеру; реестр уведомлений ФНП — по ФИО с датой рождения
или по VIN. Внутри искать тоже нечем: `find_by_phone` написан и работает в трёх
реализациях (`app/providers/internal/db_provider.py:37`,
`app/providers/internal/csv_provider.py:152`,
`app/providers/internal/composite.py:61`), но сравнивать ему не с чем — колонка
пуста у всех.

Отсюда единственный вывод, и других вариантов нет: **сценарий «ввёл номер —
увидел должника» закрывается только мостом «телефон → ФИО» из раздела 3.** Мост
переводит номер в ФИО, и уже этим ФИО поднимается строка из выгрузки заказчика.
Не будет моста — не будет и входа по номеру; всё остальное здесь — обход, а не
решение.

Что видит оператор, пока моста нет. Первый шаг карточки зовётся «✎ Номер или ФИО»
и просит «Отправьте номер телефона или фамилию с именем» (`ASK_TITLES`,
`ASK_PROMPT_NUMBER`, `app/bot/card_view.py:88`, `:113`) — экран, зовущий только
номер, скрывал бы единственный рабочий путь. Номер, по которому никого не нашли,
кончается одной строкой `По номеру не определилось. Введите фамилию.`
(`card_view.NAME_NOT_RESOLVED`, `:199`), и это штатный ход, а не сбой.

### 2.3. Что работает вместо номера сегодня: госномер

Госномер есть у 2008 из 2052 должников, и он такой же точный ключ, как телефон
(`_has_exact_key`, `app/bot/handlers/query_card.py:474`). Сценарий «одно сообщение
— отчёт» на нём закрывается целиком: присланный свободной строкой госномер
опознаёт должника и запускает проверку без единого вопроса — закреплено
`tests/test_review_fixes.py::test_an_exact_key_in_a_free_line_finds_the_debtor`.
Терять этот путь при правках первого шага нельзя: сегодня он единственный
работающий из коротких.

Точный ключ, поднявший из выгрузки нескольких разных людей, не отдаёт первого
попавшегося: `_narrow_by_person` (`app/services/search.py:665`) отсеивает строки,
противоречащие названному ФИО и дате, а если после фильтра не осталось никого —
возвращает исходный список, потому что расхождение выгрузки с тем, что оператор
набрал руками (девичья фамилия, опечатка в 1С), — это факт для отчёта, а не повод
выбросить единственную найденную строку. То же правило ждёт и номер, если он
когда-нибудь появится: семейный номер и номер поручителя — обычное дело.

### 2.4. Что происходит с номером, который прислал оператор

Номер из чата живёт своей жизнью и без колонки в выгрузке, поэтому три механизма
никуда не делись.

**Нормализация** — `normalize_phone` (`app/domain/identity.py:440`): из строки
берутся только цифры, 11 цифр с `7` или `8` и 10 цифр с `9` дают `+7XXXXXXXXXX`,
всё остальное — `None`. Почему `None`, а не «дотянуть до похожего»:
`+1 202 555 0143` и `+7 202 555 0143` не должны схлопнуться в одного человека
(`tests/test_phone_lookup.py:52`,
`test_number_that_is_not_russian_is_not_folded_into_a_neighbour`). Лучше не найти,
чем найти чужого — в этом продукте это правило, а не осторожность.

**Маска** — `mask_phone` (`app/utils/masking.py:50`): `+79990000001` →
`+7 (999) ***-**-01`. И текстовый отчёт, и веб-страница печатают
`record.phone_masked or mask_phone(record.phone)` (`app/services/reporting.py`,
`app/web/render.py:498`): полный номер в документ, который уходит в суд и в чат,
не попадает даже тогда, когда он есть в базе.

**Хэш** — `phone_hash` (`app/db/repository.py:907`),
`stable_hash("phone", normalize_phone(phone) or phone)`: он даёт поиск по номеру,
**не храня номер**. Нормализация живёт **внутри** хэша, а не у вызывающих — так
сделано после поломки, когда импорт хешировал приведённый номер, а поиск — то, что
набрал оператор, и `89263248600` не находил должника, записанного как
`+79263248600`. Не выносите её наружу. И держите в голове границу: хэш несолёный,
а пространство российских мобильных — порядка 10¹⁰, перебор занимает минуты
(`app/services/query_card.py:453`, докстринг `CardSecrets`). Приватность здесь
обеспечивают маска и `STORE_SENSITIVE_IDENTIFIERS`, а хэш — это поисковый индекс.

Одна разница между источником и чатом, которую надо знать: десять цифр с девятки,
присланные слитно и без кода страны, — это ещё и серия паспорта (90xx, 92xx),
поэтому бот сначала переспрашивает («паспорт или телефон?», `parse_query` →
`card.pending_ten`). Номер с `+7` или `8` доходит до поиска без вопросов.

### 2.5. Замечание на будущее: если телефоны начнут собирать

Отдельной работы это не потребует, и это единственное, что стоит сказать про
колонку. Если при эвакуации начнут записывать номер и он появится в выгрузке,
весь путь от файла до отчёта уже написан: схема (`Debtor.phone`, `phone_masked`,
`phone_hash` — `app/db/models.py:43-45`) и индекс `ix_debtors_phone_hash` лежат в
миграции `0001_initial_schema`, новой миграции не нужно; словарь заголовков
(`COLUMN_ALIASES`, `app/providers/internal/csv_schema.py:127-136`) понимает
`Телефон`, `Тел.`, `Phone`, `Номер телефона`, `НомерТелефона`, `Контактный
телефон`, `Мобильный телефон`, `Мобильный`, `Сотовый` и любую форму записи
приводит к одному виду, а непонятую колонку называет вслух отдельным разделом
экрана импорта (`ImportReport.unknown_columns`,
`app/services/import_service.py:193`); запись (`ImportService._to_model`,
`:352-354`), поиск и подстановка найденного в запрос (`_enrich_from_internal`,
`app/services/search.py:610`) работают сегодня, а повторный импорт **всей**
выгрузки допишет телефоны в уже загруженные записи (`DebtorRepository.upsert`,
`app/db/repository.py:80`) — сквозная проверка этого лежит в
`tests/test_phone_lookup.py`, ломать её нельзя. С того дня мост «телефон → ФИО»
станет не нужен: своя колонка даёт совпадение точное (равенство хэша,
`DebtorRepository.find_by_phone_hash`, `app/db/repository.py:154`), бесплатное и
ни от какого поставщика не зависящее, — и правильным действием станет просить
колонку, а не платить за перевод номера в имя. До того дня это замечание, а не
план работ.

## 3. Мост «телефон → ФИО»: контракт под любого поставщика

Это единственный способ закрыть вход по номеру телефона: телефона нет ни в
выгрузке, ни в самой 1С (раздел 2), и по номеру не ищет ни один реестр. Мост здесь
не запасной путь, а единственный. Если телефоны когда-нибудь начнут собирать при
эвакуации, он станет не нужен (2.5) — но не раньше.

Ниже описана **форма**, а не выбор. Поставщик не выбран и в коде не зашит: какому
сервису доверять — решение владельца. Мост спрашивает у поставщика ровно одно —
имя по номеру; контракт ниже описывает только это.

### 3.1. Что мост делает и чего он не делает

Заказчик формулирует сценарий одной фразой: «ввёл номер — увидел должника».
Колонки с телефоном в выгрузке нет, и взяться ей неоткуда — в 1С телефона нет
вовсе (2.1), — а ни один внешний реестр (ФССП, ЕФРСБ, ФНС) по номеру не ищет. Без
моста самый естественный для оператора ввод не находит никого.

Мост переводит номер в ФИО, и уже этим ФИО поднимается строка из выгрузки
заказчика.

**Найденное имя — ключ поиска, а не факт отчёта.** Это не стилистика, а свойство
продукта: отчёт несут в суд, и в нём имеют право быть только данные самого
взыскателя и ответы официальных реестров. Утверждение стороннего сервиса «этот
номер принадлежит такому-то» проверить нечем и предъявить нельзя. Поэтому в коде
мост устроен так (`app/providers/phone_bridge.py`):

* **записей не приносит** — `records=()` в обеих ветках `_read_rows`
  (`phone_bridge.py:200` и `:211`), всегда;
* **не входит в `configured_names`** (`app/providers/registry.py:113` — список
  строится только по `self._external`), а значит, не увеличивает
  `providers_per_debtor` в смете массового прогона
  (`app/services/batch.py:355`, `:368`);
* **не участвует в весах уверенности** — ключа `phone_bridge` нет в
  `PROVIDER_CONFIDENCE_WEIGHTS` (`app/domain/scoring.py:147`), поэтому он не
  влияет ни на `confidence`, ни на `scored_gap`.

Само имя при этом подставляется в субъект и вместе с ним сохраняется в
`search_requests.subject_json`: `redact_subject` (`app/services/search.py:791`)
снимает только паспорт и телефон. То есть в базе проекта остаётся имя, полученное
от стороннего сервиса, — это надо учитывать, выбирая поставщика. Тем же путём
приезжают ИНН и паспорт, если поставщик их отдаёт (3.3); про ИНН это важно
отдельно — `redact_subject` его не вырезает ни при каком флаге, и в истории
запросов он остаётся на `HISTORY_RETENTION_DAYS`.

Что мост **делает** видимым — строку в блоке ИСТОЧНИКИ. Проверено прогоном: отчёт
с одним результатом моста печатает `ИСТОЧНИКИ (ответили 1 из 1)`, а `coverage`
(`app/web/render.py:415`) даёт три значения, а не пару:
`(1, 8, ['Наши данные', 'ФССП', 'ЕФРСБ', 'ФНС', 'Залоги', 'Суды', 'Наследственные дела'])`
— семь молчавших источников плюс строка моста. Формулировка «мост не входит в
покрытие» из докстринга модуля точна только про `configured_names` и веса
уверенности; в счётчик «ответили N из M» он входит. Не считайте это багом и не
«чините»: у источника, который сделал всю проверку возможной, обязана быть
строка, иначе «спросили и не нашли» станет неотличимо от «не спрашивали».

Второе, чего мост не делает: **он не решает, звать ли себя**. Политика живёт в
`is_needed` (`phone_bridge.py:136`) — «имени нет, номер есть». Названное
оператором ФИО сильнее: он смотрит в документ, а мост — в чужую базу. `fetch()`
этой проверки не делает, её обязан делать вызывающий; оба вызывающих
(`app/services/search.py:274`, `app/bot/handlers/query_card.py:396`) её делают.

### 3.2. Контракт запроса

Собирается в `PhoneNameProvider._vendor_client` → `VendorJsonClient.fetch_records`
(`app/providers/vendor_http.py:112`).

| Что | Как |
|---|---|
| Адрес | `PHONE_BRIDGE_BASE_URL` + `PHONE_BRIDGE_PATH` |
| Метод | Только `GET`. `VendorConfig.method` существует, но мост его не передаёт и значение по умолчанию не переопределяет — настройки под POST нет |
| Формат номера | `+7XXXXXXXXXX`. Мост отправляет `subject.phone` **как есть**, не нормализуя; нормализацию делает `normalize_phone` (`app/domain/identity.py:440`) на входе бота (`app/bot/identifiers.py`) |
| Параметры | `{"phone": <номер>}` — один, имя ключа зашито в `_fetch` (`app/providers/phone_bridge.py:155`) |

**Подстановка `{phone}`.** Если в `PHONE_BRIDGE_PATH` есть `{phone}`, значение
уходит в путь и **исчезает из query**. Проверено на заглушке:

```
PHONE_BRIDGE_PATH=/lookup/{phone}  ->  GET /lookup/%2B79991234567          query: {}
PHONE_BRIDGE_PATH=/search          ->  GET /search?phone=%2B79991234567
```

Это чинилось коммитом `20ab40f` («Значение подставляется в путь источника, как и
было обещано»), и причину надо знать, чтобы не откатить. Это вторая из двух
поломок проекта, которые стоили молчаливого «ничего не нашли» (первая — секция
ответа моста к ФНС, 1.3): в обеих ошибка была на нашей стороне, а выглядела как
отсутствие данных у вендора. Раньше путь уезжал в
запрос как есть, httpx экранировал скобки, и на сервер уходило
`/lookup/%7Bphone%7D?phone=%2B7…`. Ответ — 404, а бот при этом говорил «имя по
номеру не определено»: адрес настроен, ключ верный, карта верная — и владелец
искал причину в источнике, которой там не было. Три решения в `_fill_path`
(`app/providers/vendor_http.py:51`) держатся на этом:

* подставленное **не дублируется** в query — иначе номер уходит дважды, и вендор
  со строгим разбором строки запроса отвечает ошибкой на верно настроенный мост;
* значение экранируется целиком, `safe=""` — `+7…` обязан стать `%2B7…`, а косая
  черта в любом значении `%2F`, а не новым сегментом пути;
* плейсхолдер, которому нечего подставить, — это
  `ProviderUnavailableError("bad_path_template")`, а не молчаливая пустая строка.
  Молчание дало бы тот же необъяснимый 404.

**Имя плейсхолдера — `{phone}` и только строчными буквами.** Плейсхолдер
опознаётся выражением `_PLACEHOLDER = re.compile(r"\{([a-z_][a-z0-9_]*)\}")`
(`app/providers/vendor_http.py:48`), а подставляются только ключи из `params`, где
ровно `phone`. Отсюда две разные судьбы у двух похожих опечаток, и разница между
ними стоит дня:

* `{msisdn}` — строчное, но неизвестное — даёт громкий `bad_path_template`;
* `{PHONE}`, `{Phone}`, `{phone-number}` под выражение не подходят и
  плейсхолдерами не считаются **вовсе**. Ошибки нет, скобки уезжают в адрес
  буквально. Проверено на заглушке: при `PHONE_BRIDGE_PATH=/lookup/{PHONE}` на
  сервер уходит `/lookup/%7BPHONE%7D?phone=%2B79991234567` — дословно тот запрос,
  который чинил коммит `20ab40f`. Живой вендор ответит 404, в отчёте будет
  `✗ ФИО по телефону — ошибка (http_error)`, а оператор увидит «По номеру не
  определилось». Имена переменных окружения пишутся заглавными, и рука тянется
  написать так же в пути — не поддавайтесь.

**Авторизация** (`VendorJsonClient._auth_headers` на `vendor_http.py:145`,
`_auth_query` на `:158`). Четыре рабочих варианта из пяти:

| `PHONE_BRIDGE_AUTH_STYLE` | Что уходит | Проверено |
|---|---|---|
| `bearer` | `Authorization: Bearer <PHONE_BRIDGE_API_KEY>`; `AUTH_NAME` игнорируется | да |
| `header` | `<PHONE_BRIDGE_AUTH_NAME>: <PHONE_BRIDGE_API_KEY>`; при пустом `AUTH_NAME` — `X-Api-Key` | да |
| `query` | `?<PHONE_BRIDGE_AUTH_NAME>=<PHONE_BRIDGE_API_KEY>`; при пустом `AUTH_NAME` — `key` | да |
| `none` | ничего | да |
| `basic` | **ничего.** `_auth_headers` требует `username` (`vendor_http.py:151`), а настроек `PHONE_BRIDGE_USERNAME`/`PASSWORD` не существует | да |

Две ловушки, обе воспроизведены на заглушке:

* `PHONE_BRIDGE_AUTH_STYLE=basic` не отвергается конфигом —
  `phone_bridge_configured` остаётся `True`, запрос уходит **без единого
  заголовка авторизации**, и живой вендор ответит 401. В отчёте это будет
  `✗ ФИО по телефону — ошибка (unauthorized)`, то есть похоже на «отвергли ключ»,
  а ключ не предъявлялся вовсе;
* умолчание `PHONE_BRIDGE_AUTH_NAME=X-Api-Key` при `AUTH_STYLE=query` даёт
  `?X-Api-Key=…` — заголовочное имя в строке запроса. Заглушка это и показала. Со
  стилем `query` имя надо задавать своё (`key`, `api_key`, `token`).

**Своих таймаутов и ретраев у моста нет, и это важно знать до правки.** Мост
читает общие `REQUEST_TIMEOUT_SECONDS`, `PROVIDER_MAX_RETRIES`,
`PROVIDER_RETRY_BACKOFF_SECONDS` (`phone_bridge.py:127-130`). Настроек
`PHONE_BRIDGE_TIMEOUT` и `PHONE_BRIDGE_MAX_RETRIES` **не существует**, а те же
две настройки читают ЕФРСБ (`fedresurs.py:102`, `:104`), ФНС (`fns.py:102`,
`:104`) и NewDB (`newdb.py:169`, `:177`). Совет «снизьте `PROVIDER_MAX_RETRIES`
под медленного вендора» одновременно урезает повторы у платного NewDB — это
отдельное решение, а не правка одной строки.

Повторяются только `timeout`, `connection_error`, `rate_limited`, `server_error`
(`app/providers/http.py:312`); 401 и битое тело не повторяются никогда — повтор
сжёг бы квоту на детерминированной ошибке.

**Мост не под бюджетом источника.** В отличие от моста «паспорт → ИНН»,
`_resolve_name_by_phone` зовёт `bridge.fetch(...)` напрямую
(`app/services/search.py:276`), минуя `_guarded_fetch` (`:402`), — значит, ни
`PROVIDER_BUDGET_SECONDS`, ни семафор `PROVIDER_CONCURRENCY` на него не
действуют. То же в боте: `query_card._resolve_name` (`:379`) тоже зовёт `fetch`
напрямую. Потолок ожидания =
`REQUEST_TIMEOUT_SECONDS × (PROVIDER_MAX_RETRIES + 1)` плюс бэкофф
(`0.5 + 1.0` с на умолчаниях). Измерено на висящей заглушке: при 2 с и двух
ретраях — 7,57 с (формула даёт 7,5). **На умолчаниях это 46,5 с молчания в чате
перед фразой «По номеру не определилось. Введите фамилию».**

### 3.3. Контракт ответа

JSON. Разбирает `FieldMap` (`app/providers/mapping.py`) по карте из
`PHONE_BRIDGE_FIELD_MAP`, затем `_read_rows`
(`app/providers/phone_bridge.py:173`).

**`records_path`** — точка до массива совпадений, считается от корня тела ответа
(вендорные адаптеры отдают карте весь ответ целиком). Поведение проверено
прогоном:

| Ответ и путь | Результат |
|---|---|
| `records_path` пустой, тело — объект | объект берётся как одна запись |
| `records_path` пустой, тело — массив | все элементы |
| путь ведёт на объект, а не на массив | объект берётся как одна запись |
| путь ведёт в никуда (опечатка) | `([], 0)` — **ноль записей и ноль потерь** |
| путь с индексом: `data.0.items` | работает, `dig` понимает индексы списка |

Последняя строка — главная диагностическая ловушка раздела. Опечатка в
`records_path` неотличима от честного «вендор не знает этого номера»: и то, и
другое даёт `NO_RESULTS` и строку «проверено, имя по этому номеру не определено».
Проверять карту надо на заглушке (3.6), а не на живом номере.

**Поля.** Ключи в `fields` — это имена, которые ищет `_read_rows`, а не имена
вендора; справа стоит точечный путь внутри одной записи.

| Ключ карты | Обязателен | Что делает |
|---|---|---|
| `fio` → `full_name` → `name` | один из трёх обязателен | ФИО одной строкой; берётся первое непустое в этом порядке |
| `birth_date` → `dob` | нет | дата рождения; первое непустое |
| `inn` → `innfiz` | нет | ИНН физлица; принимается **только двенадцатизначный** |
| `passport` → `passport_number` | нет, и не описывается | серия и номер паспорта, через `normalize_passport`. Код поле читает, но законного источника «паспорт по номеру телефона» не существует (8.2) |

**Готовый ИНН отменяет обращение к ФНС — но экономит меньше, чем кажется.**
Банкротство, статус ИП и арбитраж ищут физлицо только по ИНН физлица (1.1), и без
него бот идёт за ним в ФНС отдельным платным обращением. Готовый ИНН из ответа
поставщика это обращение отменяет: мост «паспорт → ИНН» проверяет `is_needed` и
не срабатывает вовсе — проверено прогоном, с ИНН `is_needed` даёт `False`, без
него `True`
(`tests/test_phone_bridge_identity.py::test_a_ready_inn_switches_the_fns_bridge_off`,
`:98`).

Считать эту экономию надо в обе стороны, иначе она превратится в довод за
подключение источника. Мост срабатывает только там, где `is_needed` истинно —
«имени нет, номер есть» (3.1), то есть при вводе номера оператором. В массовый
прогон он не входит вовсе: субъект приходит из выгрузки с разобранным ФИО, а
телефона нет ни у кого (2.1), и `BatchService._scan` считает только мост «паспорт
→ ИНН» (`app/services/batch.py:397`). Значит, расчёт всей базы из раздела 5
готовый ИНН не двигает ни на рубль. А в разовой проверке по номеру сам вызов
моста — тоже платное обращение, только к другому поставщику и по его цене: минус
2 ₽ у NewDB, плюс его тариф. Мост не окупается, и называть его владелице
экономией нельзя.

**Паспорт в этой карте — поле, которое нечем заполнить законно.** Код его читает
(`_read_rows`, `app/providers/phone_bridge.py:173`), нормализует и дописывает в
пустое поле субъекта, откуда его берёт мост «паспорт → ИНН». Учтите побочный
эффект: пришедший из источника паспорт ляжет в `search_requests.subject_json`, и
следом по нему уйдёт платный запрос в ФНС — даже если ИНН уже получен другим
путём. Поле описано здесь потому, что оно есть в коде; описывать его в карте
имеет смысл, только если ИНН источник не отдаёт.

**ИНН принимается только двенадцатизначный** (`_individual_inn`,
`app/providers/phone_bridge.py:159`). Десять цифр — идентификатор юрлица; `innfiz`
валидируется как двенадцать, десятизначное значение будет отклонено, а вызов всё
равно оплачен, и сразу у трёх источников. Не прошедшее проверку отбрасывается
молча: кривой ИНН отравляет три платных запроса и возвращает пустоту, неотличимую
от честного «не найдено». Ослаблять это до `normalize_inn` нельзя — он пропускает
и десятизначный, эту дыру нашёл собственный тест
(`::test_a_malformed_inn_is_dropped_not_passed_on`, `:117`).

**Ничего не перезаписывается поверх введённого оператором.** Дата рождения, ИНН и
паспорт дописываются только в пустое поле (`app/services/search.py:280-291`):
оператор смотрит в документ, поставщик — в чужую базу
(`::test_the_source_never_overwrites_what_the_operator_typed`, `:134`).

Пример карты (`config/field_maps/example_phone_bridge.json`) называет `fio`,
`birth_date`, `inn` и `passport`; остальные имена (`full_name`, `name`, `dob`,
`innfiz`, `passport_number`) в нём не названы, но код их читает. Ключи, которых
нет в этом списке, карта разберёт и положит в запись, а `_read_rows` их
проигнорирует.

**Разбор имени строгий.** `parse_fio` (`app/domain/identity.py:136`) требует
«Фамилия Имя [Отчество]» — от двух до трёх слов из алфавита имени (плюс частица
отчества вроде «оглы», которая склеивается с предыдущим словом). Одно слово
(«Иванов») или строка с цифрами — `NameParseError`, и запись **пропускается**, а
не собирается по кускам. Причина не в аккуратности: неверно разобранное имя
поднимет из выгрузки не того человека, и весь отчёт уедет про него — молча, без
единого признака ошибки.

Проверено на заглушке:

* запись с `fio: "Иванов"` (одно слово) → `NO_RESULTS`, `name=None`;
* записи с `fio` вовсе нет → `NO_RESULTS`;
* первая запись битая, вторая целая → берётся **вторая**, `SUCCESS`. Цикл идёт по
  всем записям до первого разобранного имени;
* элемент массива не объект, а строка (`{"matches": ["Иванов Иван Иванович"]}`) →
  `ProviderUnavailableError("unexpected_schema")`, «Карта полей не разобрала 1 из
  1 записей ответа источника». Это намеренно: молчаливый отброс таких элементов
  однажды превратил два найденных уведомления в «источник проверен, ничего нет».

**Дата рождения** проходит через `parse_date` (`app/utils/dates.py:30`):
`ДД.ММ.ГГГГ`, `ДД-ММ-ГГГГ`, `ДД/ММ/ГГГГ`, `ГГГГ-ММ-ДД`, восемь цифр подряд, ISO с
временем (`2015-01-29T16:40:08` → `2015-01-29`, проверено). Неправдоподобная дата
(до 1900 года, будущая, возраст больше 120) молча даёт `None` — имя при этом
остаётся. Дата необязательна, но резко полезна: она отсеивает однофамильцев в
выгрузке и открывает раздел исполнительных производств.

**Дата рождения не перетирает уже известную.** И `search.py`, и
`handlers/query_card.py` подставляют её только в пустое поле.

### 3.4. Настройки

Имена ровно как в `app/config.py:220-226`. В `.env` — те же в верхнем регистре
(`case_sensitive=False`).

| Настройка | Тип | Умолчание | Смысл |
|---|---|---|---|
| `PHONE_BRIDGE_ENABLED` | bool | `false` | Собирать ли провайдер вообще. `false` → `build_phone_bridge` возвращает `None` |
| `PHONE_BRIDGE_BASE_URL` | str | `""` | Схема и хост. Хвостовой `/` срезается валидатором `_strip_trailing_slash` (`app/config.py:323`) |
| `PHONE_BRIDGE_PATH` | str | `""` | Путь, можно с `{phone}` |
| `PHONE_BRIDGE_API_KEY` | str | `""` | Ключ |
| `PHONE_BRIDGE_AUTH_STYLE` | `AuthStyle` | `bearer` | `none` / `bearer` / `header` / `query` / `basic` (последний нерабочий, см. 3.2) |
| `PHONE_BRIDGE_AUTH_NAME` | str | `X-Api-Key` | Имя заголовка или query-параметра |
| `PHONE_BRIDGE_FIELD_MAP` | `Path \| None` | `None` | Путь к карте полей |

`phone_bridge_configured` (`app/config.py:488`) =
`enabled AND base_url AND path AND field_map is not None`. Карта обязательна
наравне с адресом: без неё ответ поставщика — произвольный JSON, из которого имя
пришлось бы угадывать.

Про пустое значение и несуществующий файл. Путь к **несуществующему** файлу
делает мост «настроенным», и падает он только в момент обращения:
`✗ ФИО по телефону — ошибка (invalid_field_map)`. Пустое `PHONE_BRIDGE_FIELD_MAP=`
на локальном интерпретаторе (3.14) отбрасывается валидатором
`_blank_means_unset` (`app/config.py:459`), поле берёт умолчание `None`, и мост
честно говорит «не подключено». Отбрасывание держится на том, что аннотация поля
имеет `__origin__`, а у `Path | None` это свойство зависит от версии Python; в
образе стоит 3.12 (`Dockerfile:3`, `:20`), и без карты
`TypeAdapter(Path | None).validate_python("")` даёт `PosixPath('.')`, то есть
«настроен» плюс `invalid_field_map`. **Не оставляйте настройку пустой —
удаляйте или комментируйте строку.**

**В `.env.example` блока `PHONE_BRIDGE_*` нет вовсе.** Проверено
`grep -i phone .env.example` — ни одного вхождения; там же нет `ROSREESTR_*`.
Разработчик, начавший с `cp .env.example .env`, о мосте не узнает и решит, что
ключей не существует. **Ключи добавляются в `.env` руками, имена берутся из
`app/config.py`.** Блок ниже стоит дописать в `.env.example` рядом с
`INN_BRIDGE_ENABLED` (`.env.example:159`):


### 3.5. Как мост обязан отказывать

Состояния источника называет **только** `app/services/reporting.py`
(`source_state` / `SourceStateCode` / `SourceState`, плюс `_bridge_source_line`
для мостов). Второй набор слов заводить нельзя: отчёт несут в суд, и «не
проверено», сказанное другими словами, однажды прочитается как «чисто». Ниже —
строки, снятые прогоном, а не переписанные из кода.

| Что случилось | Условие | Строка блока ИСТОЧНИКИ |
|---|---|---|
| Не спрашивали | `PHONE_BRIDGE_ENABLED=false` → `build_phone_bridge` даёт `None` | **строки нет вовсе** |
| Не спрашивали | ФИО уже названо оператором (`is_needed` = `False`) | **строки нет вовсе** |
| Не настроен | включён, но нет `BASE_URL`, `PATH` или `FIELD_MAP` | `○ ФИО по телефону — не подключено` |
| Нечего спросить | номера нет (`missing_input_for` → `MissingInput.PHONE`) | `○ ФИО по телефону — Нужен номер телефона` |
| Спросили, имени нет | пустой массив; нет поля `fio`; имя не разбирается; `records_path` мимо | `✓ ФИО по телефону — проверено, имя по этому номеру не определено` |
| Источник упал | таймаут, обрыв, 5xx, 429 | `✗ ФИО по телефону — недоступно (timeout \| connection_error \| server_error \| rate_limited)` |
| Ответ не той формы | элемент массива не объект | `✗ ФИО по телефону — недоступно (unexpected_schema)` |
| Ошибка настройки пути | `{что-то}` строчными и без значения | `✗ ФИО по телефону — недоступно (bad_path_template)` |
| Карта не читается | файла нет, битый JSON | `✗ ФИО по телефону — ошибка (invalid_field_map)` |
| Ключ отвергнут | 401 / 403 | `✗ ФИО по телефону — ошибка (unauthorized)` |
| Нет средств у вендора | 402 | `✗ ФИО по телефону — ошибка (payment_required)` |
| Прочий 4xx | 404 и т. п. | `✗ ФИО по телефону — ошибка (http_error)` |
| Ответ не JSON | HTML-страница ошибки на 200 (`Content-Type: text/html`, тело `<html>`) | `✗ ФИО по телефону — ошибка (malformed_json)` |

Последняя строка — первое, что видят при неверном `PHONE_BRIDGE_PATH` у вендоров,
отвечающих HTML на 200. Не ищите в ней проблему разбора карты: тела JSON не было
вовсе.

Отсутствие строки — это тоже осознанный ответ, а не потеря. `build_phone_bridge`
возвращает `None`, а не выключенный провайдер, чтобы незаполненный мост не
занимал строку в отчёте у тех, кто вводит ФИО и в переводе номера не нуждается:
для них перевода номера не существует как вопроса. Так же и второй случай:
`_resolve_name_by_phone` возвращает `None` вместо результата
(`app/services/search.py:275`), и в `provider_results` строка просто не
появляется.

**Оператору в чате состояния источника не показываются вообще.** Все исходы «имени
нет» — молчание вендора, незнание вендора, неподключённый мост — сводятся для него
в одну строку `card_view.NAME_NOT_RESOLVED` (`app/bot/card_view.py:199`):

> `По номеру не определилось. Введите фамилию.`

Ни имени сервиса, ни имён переменных окружения там нет и быть не должно: для
оператора все три случая — одно действие. Разница между ними живёт в отчёте,
который читает владелец. Отдельно от этого работает пара `card_view.NOT_IN_EXPORT`
(`:192`, шаблон «По {key} никого не нашёл.») и `NOT_IN_EXPORT_TRY` (`:195`,
«Попробуйте фамилию с именем или госномер.»); склеивает их `_missed`
(`app/bot/handlers/query_card.py:414`), а `{key}` подставляет `_searched_by`
(`:441`) — «номеру телефона», «госномеру», «VIN», «номеру договора» или их
перечисление. Это про поиск в выгрузке, а не про мост.

Успех моста в чате **молчалив**: подставленное ФИО видно в самой карточке, и
подписывать его отдельной фразой — лишний текст на экране, который читают каждый
день.

Две вещи, которые надо знать заранее, чтобы не искать их потом.

* **Строка `note=` в `_read_rows` никуда не попадает.** `PhoneNameResult`
  наследует `ProviderResult` (`app/domain/models.py`), у которого поля `note` нет
  (есть `notes: tuple[str, ...]`), а pydantic лишний аргумент молча игнорирует —
  проверено: `hasattr(result, "note") == False`, `error_message is None`. Значит,
  замаскированный номер («По номеру +7 (999) ***-**-67 имя не определено») в
  отчёт не едет, и ветка `NO_RESULTS` в `_bridge_source_line`, дописывающая
  `; {result.error_message}`, всегда дописывает пустоту. Не считайте это местом,
  где можно «вернуть подробность»: `_bridge_source_line` намеренно не печатает
  добытое значение ни в каком виде, включая маскированное, — восстановленный из
  кэша результат значения не несёт, и два показа одного отчёта разошлись бы.
* **Веб-страница и текстовый отчёт называют `NO_RESULTS` по-разному.**
  `app/web/render.py:461-462` подменяет подпись моста только для состояния
  `FOUND` («сработал»); при `NO_RESULTS` на странице стоит общий `EMPTY_LABEL` —
  «проверено, записей нет», тогда как в тексте — «проверено, имя по этому номеру
  не определено». Оба — из словаря `reporting.py` (`:156` и `:1044`), правило
  одного словаря не нарушено. Если будете это выравнивать, берите существующую
  формулировку из `_BRIDGE_WORDS` (`reporting.py:1037`); **новых слов не
  заводить**.

### 3.6. Чек-лист после подключения — на заглушке, не на живом источнике

Живой «пробив» стоит денег за обращение, а половина ошибок настройки (опечатка в
`records_path`, `basic` вместо `header`, `{PHONE}` вместо `{phone}`) на живом
источнике выглядит одинаково — «имя не определилось». Локальная заглушка на
`aiohttp` (он уже в окружении вместе с aiogram, версия 3.14.3) печатает то, чего
из бота не видно: полученный путь, параметры и заголовки. Именно так и был найден
баг с `{phone}` — см. хвост коммита `20ab40f`: «Найдено прогоном: мост подняли на
заглушке, и она напечатала полученный путь».

Заглушка (положить **вне репозитория**, например `/tmp/spec/stub.py`):

```python
import json
import sys

from aiohttp import web

MODE = sys.argv[1] if len(sys.argv) > 1 else "ok"
OK = {"matches": [{"who": {"fio": "Иванов Иван Иванович"}, "born": "01.02.1980"}]}
SKIP = {"host", "accept", "accept-encoding", "connection", "user-agent"}


async def handle(request: web.Request) -> web.Response:
    print(
        json.dumps(
            {
                "path": request.path,
                "raw_path": request.raw_path,
                "query": dict(request.query),
                # ВСЕ заголовки, а не один Authorization: при AUTH_STYLE=header
                # ключ уходит в своём заголовке, и по пустому Authorization
                # стили header, query, none и basic неразличимы.
                "headers": {
                    key: value
                    for key, value in request.headers.items()
                    if key.lower() not in SKIP
                },
            },
            ensure_ascii=False,
        ),
        flush=True,
    )
    if MODE == "empty":
        return web.json_response({"matches": []})
    if MODE == "500":
        return web.Response(status=500, text="boom")
    return web.json_response(OK)


app = web.Application()
app.router.add_route("*", "/{tail:.*}", handle)
web.run_app(app, host="127.0.0.1", port=8971)
```

**Чем звать мост.** Поднимать ради этого бота не нужно и токен не нужен:
`Settings` собирается прямо в коде, а `build_phone_bridge` отдаёт готовый
провайдер. Второй файл рядом с заглушкой (`/tmp/spec/call.py`):

```python
import asyncio
from pathlib import Path

from app.config import AuthStyle, Settings
from app.domain.enums import PROVIDER_TITLES, ProviderName
from app.domain.identity import SearchSubject
from app.providers.phone_bridge import build_phone_bridge
from app.services.reporting import _bridge_source_line

settings = Settings(
    phone_bridge_enabled=True,
    phone_bridge_base_url="http://127.0.0.1:8971",
    phone_bridge_path="/lookup/{phone}",
    phone_bridge_api_key="TEST-KEY",
    phone_bridge_auth_style=AuthStyle.BEARER,
    phone_bridge_field_map=Path("/tmp/spec/map.json"),
)
bridge = build_phone_bridge(settings)
result = asyncio.run(bridge.fetch(SearchSubject(search_type="person", phone="+79991234567")))
print("status:", result.status.value, "| code:", result.error_code)
print("name:", getattr(result, "name", None), "| birth:", getattr(result, "birth_date", None))
print("строка отчёта:", _bridge_source_line(result, PROVIDER_TITLES[ProviderName.PHONE_BRIDGE]))
```

Запускать из корня репозитория его же интерпретатором
(`.venv/bin/python /tmp/spec/call.py`), заглушка при этом уже поднята;
`/tmp/spec/map.json` — это карта из 3.4, положенная рядом с заглушкой. Вывод в
режиме `ok` такой — снят прогоном:

```text
status: success | code: None
name: last_name='Иванов' first_name='Иван' middle_name='Иванович' | birth: 1980-02-01
строка отчёта: ✓ ФИО по телефону — ФИО по номеру определено, должник найден по имени
```

а заглушка печатает полученный запрос:

```text
{"path": "/lookup/+79991234567", "raw_path": "/lookup/%2B79991234567", "query": {}, "headers": {"Authorization": "Bearer TEST-KEY"}}
```

Порядок проверки. Каждый пункт закрывается наблюдением, а не ощущением.

1. **Форма запроса.** Поднять заглушку в режиме `ok`, направить на неё
   `PHONE_BRIDGE_BASE_URL=http://127.0.0.1:8971` со своим `PHONE_BRIDGE_PATH`. В
   её выводе должно быть: номер там, где вы его ждёте (`raw_path` содержит
   `%2B7…`, либо `query` содержит `phone`), и **ровно один** экземпляр номера — в
   пути или в параметрах, но не в обоих. В `headers` должен лежать ровно тот
   ключ, которого ждёт ваш вендор: `Authorization: Bearer …` при `bearer`, ваш
   `AUTH_NAME` при `header`. Если в `headers` не осталось ничего, а
   `PHONE_BRIDGE_API_KEY` не пуст — у вас `AUTH_STYLE=basic`, и ключ не
   предъявляется вовсе. Смотреть надо все заголовки: по одному `Authorization`
   рабочий `header` неотличим от нерабочего `basic`.
2. **Плейсхолдер, если он есть.** В `raw_path` не должно остаться фигурных
   скобок. `%7B…%7D` означает, что имя написано не строчными (`{PHONE}`) или не
   по алфавиту `[a-z_][a-z0-9_]*`, — ошибки при этом нет, а живой вендор ответит
   404.
3. **Карта полей на настоящем образце.** Подмените в заглушке `OK` на **реальное
   тело ответа вашего вендора с обезличенными значениями** (вымышленное ФИО,
   вымышленная дата). Настоящие ФИО и номера в репозиторий и в фикстуры не
   попадают ни при каких условиях. Ожидаемое: `status = success`, `name`
   разобрано на три поля, `birth_date` не `None`.
4. **Пустой ответ.** Режим `empty`. Ожидаемое: `status = no_results` и строка
   `✓ ФИО по телефону — проверено, имя по этому номеру не определено`. Если вы
   вместо этого видите её же при непустом ответе из пункта 3 — ошибка в
   `records_path`, и никакого другого признака у неё нет.
5. **Падение.** Режим `500`. Ожидаемое:
   `✗ ФИО по телефону — недоступно (server_error)`, и это **другая** строка, чем
   в пункте 4. Различие этих двух строк — то, ради чего написан весь инструмент;
   если после ваших правок они совпали, правки надо откатывать.
6. **Через бота, а не через сервис.** Мост однажды уже был написан, покрыт
   тестами и недостижим из интерфейса, потому что тесты дёргали сервис напрямую.
   Прогоните
   `tests/test_review_fixes.py::test_a_phone_alone_produces_the_whole_report` и
   `::test_a_silent_bridge_asks_for_a_surname_in_one_line` — они идут через
   диспетчер aiogram (`dispatcher_for` / `feed`).
7. **Гейты.** Четыре команды из шапки документа, по коду возврата.
8. **Живой источник — один номер, один раз**, после того как семь пунктов выше
   зелёные. Смотреть надо на путь в логах вендора, а не на «получилось / не
   получилось».

### 3.7. Что стоит починить, если возьмётесь

Обе вещи проверены прогоном.

* **Неразрешившийся номер перезапрашивается на каждом следующем шаге карточки.**
  `_resolve_name` (`app/bot/handlers/query_card.py:379`) выходит рано только при
  уже заполненном `card.name`, а `card.name` требует и фамилии, и имени
  (`app/services/query_card.py:192`). `settle`
  (`app/bot/handlers/query_card.py:271`) вызывается на каждом принятом сообщении
  и доходит до `_resolve_name` (`:316`) всегда, кроме двух ранних выходов —
  незакрытый вопрос (`:301`) и свободная строка без точного ключа (`:306`).
  Считать цену повторов надо по сообщениям, дошедшим до `:316`, а не по всем
  подряд. Проверено прогоном через диспетчер: номер → фамилия → дата рождения
  дали **три** обращения к мосту, то есть три оплаченных вызова там, где нужен
  один. Косвенное подтверждение того, что это происходит на проде, — функция
  `_once` (`:356`), заведённая ровно затем, чтобы строка «По номеру не
  определилось» не висела над каждым следующим экраном.
* **`PhoneNameProvider.will_query` не вызывается ниоткуда.** `BatchService._scan`
  (`app/services/batch.py:429`) считает только `inn_bridge`; единственный другой
  вызов `will_query` — в `app/bot/report_actions.py:153`, и там аргумент
  типизирован как `InnBridgeProvider | None`. Обычно это безвредно — в массовом
  прогоне субъект приходит из выгрузки с ФИО, и `is_needed` ложно, — но не
  всегда: `_subject_for` (`app/services/batch.py:795`) отдаёт субъект с
  `name=None`, когда ФИО пустое или не разбирается, а номер договора есть, и
  подставляет туда `row.phone` (`:813`). Флаг `STORE_SENSITIVE_IDENTIFIERS` на
  проде поднят (`app/services/import_service.py:352` — только при нём в
  `Debtor.phone` вообще что-то ложится), так что удерживает это сегодня ровно
  одно обстоятельство: телефонов в выгрузке нет ни одного. Появятся — такая
  строка вызовет мост, и в смете этого обращения не будет.

## 4. ЕГРН «объект по адресу»: включён на проде

### 4.1. Что включено и как это видно

`ROSREESTR_ENABLED=true` (`app/config.py:157`), и `rosreestr_configured =
newdb_configured and rosreestr_enabled` (`app/config.py:448-455`) теперь `True`: в
строке `providers.ready` при старте (`app/providers/registry.py:224-228`) в списке
`configured` появился `property`, а на экране «Откуда данные» — строка
`✓ Объект по адресу (ЕГРН) — подключено`.

Второй флаг остался опущенным намеренно: `ROSREESTR_IN_BATCH=false`
(`app/config.py:160`). В массовом прогоне источник не вызывается даже при
включённом методе — прогон по всей базе означал бы полторы тысячи платных
обращений к ЕГРН одним нажатием (`_allowed_here`,
`app/providers/property.py:108`). Это правило «платит одна кнопка», применённое к
источнику, а не к экрану.

**Читать `_allowed_here` надо буквально, потому что «не в массовом прогоне» —
это шире, чем кажется.** Условие ровно одно: поиск по адресу проходит всегда,
включая массовый прогон; всё остальное проходит тогда, когда прогон **не**
массовый. То есть ЕГРН вызывается и в обычной одиночной проверке человека — по
номеру, по фамилии, по госномеру, — если в его карточке лежит адрес с квартирой.
Проверено вызовом `planned_calls` на субъекте `person` с адресом до квартиры:
`FetchContext(batch=False)` → `1`, `FetchContext(batch=True)` → `0`, адрес до
дома → `0` в обоих случаях. Считая деньги, помните: у 1512 должников из 2052
адрес для ЕГРН пригоден (4.3), и каждая одиночная проверка такого должника — это
плюс одно платное обращение (2 ₽) сверх строки из 5.2.

### 4.2. На какой вопрос он отвечает и на какой не отвечает

Отвечает: **что за объект по известному нам адресу.** Даёт кадастровый номер,
площадь, кадастровую стоимость, обременения и число долей
(`NewDBPropertyProvider`, `app/providers/property.py`). Кадастровый номер — то,
что физически вписывается в ходатайство приставу об обращении взыскания; ради
него источник и включён.

Не отвечает: **кому объект принадлежит.** Правообладателя ЕГРН не называет
никому, кроме самого лица, суда и пристава. В живом ответе — четыре записи о
правах (общая долевая собственность, доли 1/5, 2/5, 1/5, 1/5) и ни одного ФИО,
поэтому `PropertyRecord.owner_confirmed` этот провайдер **никогда** не выставляет
в `True` (`app/providers/property.py:169`), а раздела «Недвижимость должника» в
отчёте нет и не будет. Отсюда же имя источника в интерфейсе — «Объект по адресу
(ЕГРН)», а не «Недвижимость» (`app/domain/enums.py:89`): строка
«✓ Недвижимость — 1 зап.» прочиталась бы как «нашли имущество должника».

По ФИО он не ищет вовсе. Вход — адрес из нашей карточки или кадастровый номер
(`CADASTRAL_NUMBER`, `app/providers/property.py:47`).

### 4.3. Адрес обязан содержать номер квартиры

Адрес до дома живьём отвечает `500` с пустой `data` и не доходит до `complete`:
**вызов оплачен, результата нет.** Поэтому такой адрес провайдер не отправляет
вовсе — возвращается `HOUSE_LEVEL_REFUSAL` (`app/providers/property.py:55`, ветка
на `:89`) как `insufficient_query`, то есть «нам нечего было спросить», а не
«объект не найден». Это правило 1 на уровне одного поля, и трогать его нельзя:
разница между двумя ответами здесь стоит ровно два рубля за каждый ненайденный
дом.

Замер на проде: адрес есть у **2033** должников, из них с номером квартиры —
**1512**. То есть каждый четвёртый адрес выгрузки для ЕГРН непригоден, и починить
это может только заказчик в своей 1С, а не код. Пригодность считается по самому
адресу, поэтому пересчитать её можно в любой момент — тем же запросом к
`debtors`, что и в 1.4.

### 4.4. Текст границ пришлось переписать в тот же день

Экран «Откуда данные» состояние каждого источника берёт живым из реестра
провайдеров, но блок `LIMITS` (`app/bot/sources.py:134`) — статический текст,
который добавляется безусловно (`:159`). В нём стояло «не покажет имущество в
собственности: ЕГРН не подключён» — правда ровно до дня подключения, после
которого экран начинал спорить сам с собой: строкой выше `✓ Объект по адресу
(ЕГРН) — подключено`.

Сейчас там стоит граница, которая не зависит от настройки
(`app/bot/sources.py:137-138`):

```
• не покажет, что принадлежит должнику: правообладателя ЕГРН не называет
  никому, кроме него самого, суда и пристава;
```

Тест переписан вместе с текстом:
`tests/test_bot_face.py::test_sources_screen_states_the_limits` (`:259`) требует
подстроку «правообладателя ЕГРН не называет» и **запрещает** слово «не подключён»
внутри `LIMITS`. Правило общее и на будущее: если строка границы перестаёт быть
правдой в день подключения источника, она написана про настройку, а должна быть
написана про закон. Состояние источника рядом при этом честно говорит «подключено»
или «не подключено» — это про сегодняшнюю настройку, и там оно уместно.

### 4.5. Цена и оставшийся долг

По тарифу из раздела 5 обращение к ЕГРН стоит 2 ₽, а в массовый прогон источник не
входит, поэтому сумма — верхняя граница ручной работы оператора: 1512 пригодных
адресов × 2 ₽ = **3 024 ₽** за всю базу, если проверить каждый адрес по одному
разу.

**А вот в смете массового прогона ЕГРН теперь считается — и это дефект, который
принесло включение флага.** `providers_per_debtor` — это не «сколько спишется», а
`len(configured_names)` (`app/services/batch.py:355`, `:368`), то есть простой
счёт настроенных внешних источников. `property` в `configured_names` теперь
входит (`providers.ready` на проде: `['fssp', 'fedresurs', 'fns', 'pledge',
'court', 'property', 'inheritance']`), и смета берёт по нему обращение с каждого
должника, хотя `ROSREESTR_IN_BATCH=false` и в прогоне он не вызывается ни разу.
Там же и наследственные дела, которые бесплатны всегда (5.1), — смета считает их
обращением наравне с платными. То есть на сегодняшнем проде смета берёт по 7
обращений с каждого должника там, где платят пять (у должника с паспортом) или
два (у остальных, 5.2), и при внесённом тарифе назовёт владелице сумму заведомо
больше настоящей. Занижение моста (1.6) и это завышение друг друга не гасят: они
про разных должников и разные источники.

Строк `ROSREESTR_ENABLED` и `ROSREESTR_IN_BATCH` в `.env.example` нет — проверено
`grep -i rosreestr .env.example`, ноль вхождений; на сервере руками дописан только
`ROSREESTR_ENABLED=true`, `ROSREESTR_IN_BATCH` не задан вовсе и работает
умолчанием `false`. По правилу из раздела 9, пункт 8, обе строки надо дописать в
`.env.example` с объяснением, иначе следующий разработчик решит, что их не
существует.

## 5. Сколько это стоит

Раздела про деньги в первой редакции документа не было вовсе, и это был пробел:
подключение источника — не только код, но и счёт, который кто-то оплатит.

### 5.1. Тариф

Базовая единица тарификации NewDB — **один источник данных = 2 ₽**. Не отчёт, не
должник и не метод: обращение к одному источнику. Должник, по которому спросили
шесть источников, стоит шесть единиц.

* **100 обращений бесплатны** на время интеграции. Этого хватает на живую сверку
  каждого источника и на приёмку — если не жечь их прогоном по всей базе.
* **При объёме дают ниже 1 ₽** за обращение, по запросу на `access@newdb.net`.
* Источник сведений о тарифе — сам поставщик, <https://newdb.net/>.

Наследственные дела бесплатны всегда и ни в один расчёт ниже не входят: реестр
ФНП опрашивается напрямую через `notariat.ru`, без вендора и без ключа
(`NotariatInheritanceProvider`, `app/providers/inheritance.py`). Это единственный
бесплатный источник в проекте, и терять его при рефакторинге реестра нельзя.

### 5.2. Сколько обращений на одного должника

Считается по тому, что у должника есть; ничего другого сумму не двигает. Таблица
ниже — про **массовый прогон**: одиночная проверка того же человека стоит на одно
обращение дороже, если в его карточке есть адрес с квартирой, — в неё входит ещё
и ЕГРН (4.1).

| Кого проверяем | Кто отвечает | Обращений | Рублей |
|---|---|---|---|
| С паспортом (1300) | ФССП, мост «паспорт → ИНН», банкротство, статус ИП, арбитраж, залоги | 6 | 12 |
| Без паспорта (752) | ФССП, залоги | 2 | 4 |

Почему у второй строки всего два источника: банкротство, статус ИП и арбитраж
ищут физлицо только по ИНН физлица (1.1), ИНН нет ни у кого, а взять его без
паспорта неоткуда. У таких должников эти три раздела отчёта остаются «не
проверено» — и обращений не стоят.

Почему залоги — одно обращение, а не два: у источника две формы,
`pledge_person` по человеку и `pledge_vin` по машине
(`app/providers/pledge.py:59-60`), и вторая уходит только когда у субъекта есть
VIN (`:135-137`). **VIN нет ни у одного должника в выгрузке**, поэтому платится
ровно одна.

**Мост «телефон → ФИО» этот расчёт не двигает, и закладываться на него нельзя.**
Он срабатывает только там, где `is_needed` истинно — «имени нет, номер есть»
(3.1), то есть при вводе номера оператором. В массовом прогоне субъект приходит из
выгрузки с разобранным ФИО, телефона нет ни у кого (2.1), а `BatchService._scan`
считает только мост «паспорт → ИНН» (`app/services/batch.py:397`) — то есть по
всей базе мост по номеру не вызывается ни разу. И даже там, где он срабатывает,
готовый ИНН в его ответе не даёт чистой экономии: отменённое обращение к ФНС
(2 ₽) оплачено самим вызовом моста — к другому поставщику и по его цене (3.3).
Деление базы на 1300 и 752 снимает не мост, а паспорта: их 1304, и других
идентификаторов в выгрузке нет.

### 5.3. Вся база

```
с паспортом:  1300 × 12 ₽ = 15 600 ₽
без паспорта:  752 ×  4 ₽ =  3 008 ₽
                            ---------
                             18 608 ₽
```

18 608 ₽ — это **0,14 % от 13 679 650 ₽** долга, лежащего в выгрузке
(`docs/STATE.md:193`). Называть сумму владелице стоит именно так: не
«восемнадцать тысяч», а «доля процента от того, что взыскивается».

ЕГРН считается сверх этого и в массовый прогон не входит (4.1): 1512 адресов с
номером квартиры × 2 ₽ = **3 024 ₽**, если проверить каждый по одному разу.

Три поправки, которых расчёт не учитывает и которые надо знать до того, как
называть сумму окончательной.

* **Регионы ФССП.** Провайдер отправляет по одному набору параметров на регион
  (`_region_codes`, `app/providers/fssp.py:127-129`). У должника, которого ищут в
  двух регионах, строка «ФССП» удваивается.
* **Арбитраж компаний должника.** `arbitr_legal` — вторая фаза после ФНС: по
  одному обращению на каждую компанию, где должник руководитель или участник
  (`app/providers/arbitr_legal.py`). Сегодня он **не стоит ничего вовсе**:
  `arbitr_legal_configured = newdb_configured and arbitr_legal_enabled`
  (`app/config.py:514-515`), а `ARBITR_LEGAL_ENABLED` в прод-`.env` не дописан —
  умолчание `false` (`app/config.py:177`), и в `providers.ready` на проде
  `arbitr_legal` в списке `configured` отсутствует. Поправка станет поправкой в
  день включения флага; тогда же вспомните, что у большинства должников компаний
  нет, а кэш по ИНН компании (`:163`) не даёт двум должникам из одного холдинга
  заплатить за один ответ дважды.
* **Что считается обращением.** Всё выше посчитано из «одно обращение — один
  источник данных». Если поставщик тарифицирует набор параметров, а не метод,
  первая поправка перестаёт быть поправкой и становится множителем. Это
  единственное место расчёта, которое стоит подтвердить письмом поставщику до
  массового прогона.

Повторный вопрос про того же должника денег не стоит: ответ живёт в кэше
`CACHE_TTL_HOURS` (24 часа по умолчанию), а ключ кэша считается по вопросу
оператора, до обогащения (`build_query_hash`, `app/services/search.py:760`).

### 5.4. Смета молчит о рублях, пока не внесён тариф

`PROVIDER_REQUEST_COST` по умолчанию `0` (`app/config.py:288-293`), и это значит
«цена не задана», а не «бесплатно»: `BatchEstimate.cost` в этом случае возвращает
`None` (`app/services/batch.py:190-200`), и смета честно остаётся в обращениях.
Ноль рублей — это утверждение «бесплатно», сказанное ровно там, где оператор
решает, тратить ли деньги.

Считает смета так: `requests = to_query * providers_per_debtor + bridge_calls`
(`app/services/batch.py:188`). Мост отдельным термом, потому что стоит один вызов
на должника, а не один на источник. Чтобы владелица видела сумму до списания, в
`.env` вносится тариф её договора: сегодня это `2`, после скидки за объём — то,
что будет записано в договоре.

Прежде чем вносить тариф, закройте оба расхождения сметы с прогоном, иначе
названная владелице сумма будет неверна в обе стороны сразу. **Занижение:**
`_subject_for` не отдаёт паспорт, и вызовы моста не считаются — до 1300 обращений
(1.6). **Завышение:** `providers_per_debtor` — это `len(configured_names)`, а не
число тех, кто действительно ответит: туда входят и `property` (в прогоне не
вызывается, `ROSREESTR_IN_BATCH=false`), и бесплатные наследственные дела, и три
источника, которые без ИНН физлица возвращают `insufficient_query`, не сделав ни
одного обращения (4.5, 1.1).

## 6. Пять правил проекта и чем каждое куплено

Правила перечислены в `docs/STATE.md`, раздел «Правила, которые нельзя нарушать»
(строки 170–185). Они не стилистические. Ниже — дефект, который каждое оплатил, и
место, где правило удерживается кодом или тестом.

### Правило 1. Найденное не должно выглядеть ненайденным

Пустой раздел значит «не спрашивали» ИЛИ «спросили и пусто» — это разные строки,
всегда. Отчёт несут в суд.

Дефект, который его купил (`docs/STATE.md:68`, критическая находка «Оконченные
производства ФССП»): оконченные производства разбирались и терялись по дороге.
Раздел печатал «активных не найдено», список источников тут же писал «4 зап.», а
балл получал бонус за чистую ФССП. Три вывода об одном ответе противоречили друг
другу, и два из трёх были в пользу должника.

Второй набор примеров — `tests/test_newdb_live_answers.py`, шапка файла: шесть
подлогов, пойманных живыми ответами вендора, и все шесть одного вида — «НАЙДЕНО,
показанное как НЕ НАЙДЕНО». Самый дорогой: `pledge_person` нашёл тринадцать
уведомлений ФНП и не сопоставил ни одного — ноль записей читался как чистый
реестр и **приносил плюс к оценке взыскания**.

Где правило живёт:

* состояния источника называет только `app/services/reporting.py` —
  `SourceStateCode` (`:181`), `source_state()` (`:232`), `SourceState` (`:203`),
  `NO_SOURCE_STATE` (`:286`), `unanswered_line()` (`:289`). Второй набор слов
  заводить нельзя: чат, веб-страница, текстовый экспорт, карточка и экран «Откуда
  данные» берут подписи отсюда;
* `app/bot/sources.py` импортирует `CONNECTED_LABEL`, `NOT_CONFIGURED_LABEL`,
  `EMPTY_LABEL`, `NOT_CONFIGURED_REPORT_LINE` из `reporting` и не сочиняет своих
  (закреплено
  `tests/test_bot_face.py::test_sources_screen_separates_unchecked_from_clean`);
* провайдер, которому нечего было спросить, обязан вернуть
  `insufficient_query()`, а не `NO_RESULTS` (`app/providers/base.py:214`). Живой
  пример — `app/providers/property.py:89`: адрес до дома, без квартиры, в ЕГРН не
  отправляется вовсе, потому что это «не хватило данных», а не «объект не
  найден»;
* тот же принцип на уровне поля: `PropertyRecord.encumbrances_checked`
  (`app/providers/property.py:167`) отличает пустой массив обременений —
  проверенное отсутствие — от отсутствия массива, то есть непроверенного.

### Правило 2. Платит одна кнопка

Присланный текст дописывается в карточку и ничего не запускает.

Дефекты: двойной запуск прогона — второй тап по «Запустить» проходил сквозь
фильтр состояния, пока считалась смета, и оплачивал всю выгрузку второй раз
(`docs/STATE.md:43`). И кнопка «Обновить»: она идёт мимо кэша и висит под каждым
старым отчётом — четырёх случайных нажатий хватало, чтобы сжечь остаток у
поставщика (`docs/STATE.md:81`).

Исключение ровно одно и оно намеренное, `app/bot/handlers/query_card.py`: точный
ключ, опознавший в выгрузке ровно одного человека, запускает проверку сразу.
Точный ключ — это телефон, госномер, VIN или номер договора (`_has_exact_key`,
`:474`); ФИО и дата рождения в список не входят, потому что по ним выгрузка
отвечает похожими, а не теми же.

Границу держит `settle()` (`:271`), и читать её надо буквально:

* свободная строка **без** точного ключа до выгрузки не доходит вовсе (`:306`) —
  догадка не платит и карточку из выгрузки не переписывает;
* с точным ключом выгрузка спрашивается (это бесплатно, файл свой), и если она
  опознала **ровно одного** (`found.only`), управление уходит в `recognised()`
  (`:319-329`);
* `recognised()` (`:506`) при `autorun` и разошедшемся `run_hash` идёт прямо в
  `run_card` (`:547-551`) — платный прогон без единого нажатия. Так и задумано:
  это дословное требование владелицы «ввёл номер — сразу отчёт», закреплённое
  `tests/test_review_fixes.py::test_an_exact_key_in_a_free_line_finds_the_debtor`
  (свободной строкой шлётся госномер, в ответе ожидается готовый отчёт).

**Ловушка для правящего.** Автопрогон случается в обоих сценариях — и в ведомом,
и по свободной строке; отсекается только догадка. Параметр `autorun` у
`recognised()` есть, но `False` его сегодня не передаёт никто: вызов у функции
ровно один. Докстринг `recognised()` в части «только в ведомом сценарии» устарел
— не чините код по нему, сломаете главный сценарий заказчицы.

### Правило 3. Подпись нижней кнопки живёт вечно

Нижняя клавиатура принадлежит чату и обновляется только со следующим `/start`. У
всех, кто его ещё не нажал, остаются прежние кнопки — и приходят они обычным
текстом.

Дефект: нажатие «Главное меню» отвечало вопросом «это другой человек или
исправление?» — подпись доезжала до карточки и разбиралась как фамилия должника.
Отсюда `LEGACY_BUTTON_*` в `app/bot/keyboards.py:92-96` и обработчики под каждую
снятую подпись в `app/bot/handlers/buttons.py` — каждая нынешняя подпись стоит в
одном `F.text.in_({...})` со своей снятой. Тест перебирает весь `REPLY_BUTTONS` —
и нынешние подписи, и снятые — и требует от каждой осмысленного ответа:
`tests/test_review_fixes.py::test_every_bottom_label_reaches_a_handler`.

Смежное требование оттуда же —
`tests/test_bot_keyboard.py::test_every_label_is_a_phrase_nobody_enters_as_data`:
подпись — не меньше двух слов. От эмодзи в начале отказались, и различение
«нажатие или ввод» держится теперь только на том, что «Проверить человека» не
бывает ни фамилией, ни номером договора. Однословная «История» столкнулась бы с
номером договора и украла бы ввод.

### Правило 4. В текстах для оператора нет имён источников и переменных окружения

Причины нехватки — есть: они про то, что оператор может исправить.

Дефекты (`docs/STATE.md`, HIGH, `:101-107`): имена переменных окружения стояли в
смете прогона и в подсказке про паспорт; тест, закреплявший
`PROVIDER_REQUEST_COST` в тексте, пришлось переписать на обратное утверждение
(`tests/test_batch_flow.py`). И второй: источники перечислялись поимённо в
карточке и в истории, хотя правило владелицы «не надо про это рассказывать всем»
до этого действовало только для отчёта. Теперь — числами: «Сейчас спрошу: 6
источников из 6» (`app/bot/card_view.py:612`, `_coverage_lines`, вызов на `:451`;
числа считает `app.services.coverage`, а не захардкоженный список).

Граница правила: название закона — не имя источника, а основание, и оно как раз
обязано стоять. Держат её два теста в `tests/test_report_source_states.py`:
`test_bank_section_names_no_source_and_no_setting` (`:412`) запрещает в разделе о
счетах слова «ЕГРН», «Федресурс», «ЕФРСБ», «Росреестр», «ФНП», «NewDB» и
подстроку «ENABLED», а `test_bank_section_says_where_the_data_can_actually_be_obtained`
(`:399`) требует «суде», «пристава», «ст. 26» и «ст. 69 ФЗ-229».

### Правило 5. Персональные данные третьих лиц в репозиторий не попадают

Ни в фикстуры, ни в тесты, ни в примеры.

Как это сделано, чтобы фикстуры при этом оставались настоящими: файлы
`tests/data/newdb_live_*.json` — дословные конверты живых ответов, ни один ключ не
переименован и ни одно значение не выброшено; заменены только персональные данные
и только «значение на значение той же формы» — ФИО на ФИО, двенадцать цифр на
двенадцать цифр, GUID на GUID. Нарезаны скриптом `scripts/make_live_fixtures.py`,
а не набраны руками: набранная руками фикстура согласуется с тем, что код уже
делает, и потому ничего не ловит. Исходные захваты лежат вне репозитория и туда
не попадают — это записано в шапке скрипта.

Смежные барьеры, которые нельзя снимать:

* `redact_sensitive_json()` (`app/utils/masking.py:132`) вырезает
  `SENSITIVE_RAW_KEYS` (`:37`) из тела вендора **до** сохранения и не спрятан за
  `STORE_SENSITIVE_IDENTIFIERS`: тот флаг про идентификаторы наших должников,
  которые ввёл оператор, а эти данные не вводил никто и не читает ничто. Важно
  знать границу: вызывается он сегодня только на пути NewDB
  (`app/providers/newdb.py:918`, `raw_for`) и ФССП (`app/providers/fssp.py:165`).
  Обобщённые адаптеры сохраняют тело без вычистки
  (`app/providers/fedresurs.py:139`, `app/providers/fns.py:135`) — **новый
  адаптер, списанный с них, унаследует эту дыру, и вычистку в него надо ставить
  руками**;
* реестр наследственных дел ФНП не сохраняет сырое тело вообще
  (`tests/test_inheritance.py::test_raw_response_is_never_stored`): в ответе —
  персональные данные тысячи посторонних людей, а нужных ключей в списке
  редактирования нет;
* веб-CSV очереди отдавал всю базу с ФИО, датой рождения и госномером рядом с
  намеренно маскированной страницей — починено `queue_to_csv(mask_personal=True)`
  (`app/services/export.py:41`).

## 7. Состояния источника: восемь вычисляемых и одно назначаемое

`SourceStateCode` (`app/services/reporting.py:181`) — единственное место, где
состояния источника называются словами. Восемь из девяти кодов выдаёт
`source_state()` (`:232`) по `ProviderResult`; девятый назначается разделом
напрямую.

| Код | Подпись (`label`) | Знак | `answered` | Когда |
|---|---|---|---|---|
| `FOUND` | `N зап.` | `✓` | да | `ProviderStatus.SUCCESS` |
| `EMPTY` | `проверено, записей нет` | `—` | да | `ProviderStatus.NO_RESULTS` — спросили, ответ пустой |
| `PARTIAL` | `ответ неполный, N зап.` | `⚠` | да | источник ответил и сам сказал, что прислал не всё (`result.is_partial and result.is_answered`) |
| `NOT_CONFIGURED` | `не подключено` | `○` | нет | `ProviderStatus.NOT_CONFIGURED` — гейт провайдера закрыт, запрос не уходил |
| `INSUFFICIENT` | `недостаточно данных` | `?` | нет | `error_code == "insufficient_query"` — нам нечего было спросить |
| `UNAVAILABLE` | `недоступно (код)`, а для двух кодов — словами | `!` | нет | `ProviderStatus.UNAVAILABLE` — источник не ответил |
| `ERROR` | `ошибка (код)` | `✗` | нет | всё остальное |
| `NOT_QUERIED` | `не опрашивался` | `○` | нет | `result is None` — результата нет вовсе |
| `NO_SOURCE` | `источника нет` | `∅` | нет | назначается разделом; `source_state()` его не выдаёт |

Порядок веток в `source_state()` — часть контракта, а не оформление.
`insufficient_query` проверяется до `UNAVAILABLE`, иначе «нам нечего было
спросить» превратится в «источник лежал». `is_partial` — до
`SUCCESS`/`NO_RESULTS`, иначе источник, честно сказавший о неполноте, получит
подпись «проверено, записей нет».

Знак (`mark`) — не украшение. В чате, в чёрно-белой распечатке и для дальтоника
он единственный носитель смысла, цвет — только усиление. Отчёт печатают и несут в
суд.

`answered=False` означает «утверждать об этом источнике нечего»: такие состояния
не идут в счётчик «ответили N из M» и не дают оценке ни плюса, ни минуса.

### Два кода, которые звучат словами

Латинский код в скобках — нормальная подпись: он короткий, и его можно поискать.
Два кода из этого правила выведены, потому что по ним читатель отчёта принимает
решение не о технике, а о деньгах (`_SPOKEN_CODES`,
`app/services/reporting.py:219-229`, ветка на `:258`):

| Код | Что печатается вместо него |
|---|---|
| `unauthorized` | `не проверено — у поставщика данных нет доступа или средств` |
| `poll_timeout` | `не проверено — поставщик не успел ответить, стоит повторить` |

Куплено это прогоном на проде: у поставщика кончился баланс, всё ответило
«недоступно (unauthorized)», и отчёт стал неотличим от честного «ничего не
нашли». Это худший вид молчания — оплаченный: владелец видит пустые разделы и
делает вывод о должнике, хотя вывод надо делать о своём счёте. `poll_timeout`
отделён по той же причине с другой стороны: «не успел ответить» чинится повтором
через несколько минут, «ответил, ничего нет» не чинится ничем, и слить их значит
предлагать платить за повтор там, где повторять нечего.

Код состояния при этом остался прежним — `UNAVAILABLE`, девятого не появилось;
изменилась только подпись. Правило 4 соблюдено: ни имени поставщика, ни ключа, ни
адреса поддержки в строке нет, это проверяется
`tests/test_report_source_states.py::test_a_provider_out_of_money_says_so_in_words`
(`:524`) и `::test_a_slow_provider_is_told_apart_from_an_empty_one` (`:555`).

Расширять словарь по вкусу нельзя: он существует ровно для тех кодов, по которым
читатель делает другое действие. Всё остальное — латиницей в скобках.

### Почему девятое состояние — почти всегда ошибка

Состояние читают минимум четыре потребителя, и у каждого есть ветка «всё
остальное», в которую новый код попадёт молча:

* `unanswered_line()` (`reporting.py:289`) — `case _` печатает «Не проверено:
  ошибка обращения к источнику (unknown)»;
* `state_tag()` (`app/web/render.py:290`) через `_unchecked_tone()` выдаст класс
  `unchecked` — штрихованный чип, который означает «мы сюда ещё не сходили», то
  есть обещание сходить;
* `app/bot/view.py` печатает строку факта только для `FOUND` и `EMPTY`, остальное
  молчит;
* CSS: класс чипа обязан существовать и в экранном, и в печатном блоке стилей,
  иначе различие умрёт на листе.

То есть новый код по умолчанию не «неизвестен», а **ложно распознан**: он либо
назовётся ошибкой обращения, либо оденется в чужую подпись. Прежде чем заводить
девятый, проверьте, не сводится ли случай к одному из восьми — почти всегда
сводится.

### Почему `NO_SOURCE` всё-таки завели

Единственный случай, который не свёлся: счета в банках. Ближайший по смыслу
`NOT_CONFIGURED` значит противоположное — экран «Откуда данные» определяет его
дословно: «записи там могут быть, мы просто не смотрели», то есть обещает
подключение когда-нибудь. Со счетами подключать нечего и ждать нечего, и это
разные ответы взыскателю.

`ProviderResult` здесь взяться неоткуда — спрашивать некого. Поэтому состояние
заведено константой `NO_SOURCE_STATE` (`:286`) и ставится разделом напрямую, а не
строкой в разметке: слова о состоянии источника называет только `reporting`.

Псевдо-провайдер под этот раздел заводить нельзя, и не из брезгливости:
`ProviderResult` попал бы в счётчик «ответили N из M», в строку «Не проверено: …»
на первом экране и в карточку чата репликой «проверено не всё» — то есть трижды
позвал бы оператора чинить нечинимое.

Инварианты закреплены тестами в `tests/test_report_source_states.py`:

* `test_no_provider_result_can_ever_claim_this_state` (`:387`) — `source_state()`
  перебором всех `ProviderStatus` и `None` никогда не возвращает `NO_SOURCE`;
* `test_the_state_of_a_source_that_cannot_exist_stands_apart` (`:363`) — подпись
  и знак не совпадают ни с одним из восьми, чип получает свой класс
  `tag nosource`, и класс присутствует в CSS **дважды**: в экранном блоке и
  внутри `@media print{`.

## 8. Чего не существует и почему

### 8.1. Счета в банках — источника нет и не будет

В ТЗ счета названы прямым текстом, раздела в отчёте не было вовсе, и читающий не
мог отличить «забыли» от «не бывает». Отличать это обязан отчёт, а не переписка с
автором.

Основание: сведения о счетах и остатках — банковская тайна, ст. 26 ФЗ «О банках и
банковской деятельности». Ни один агрегатор их легально не отдаёт. Получают двумя
путями: ходатайством об истребовании доказательств в суде или через пристава в
возбуждённом исполнительном производстве (ст. 69 ФЗ-229).

Реализация:

* тексты — `app/services/reporting.py:132`, `:140`, `:144`: `BANK_TITLE`,
  `BANK_NO_SOURCE_LINE`, `BANK_ACCESS_LINE`. Строк две, и вторая важнее первой:
  «данных нет» — это не ответ, ответ — куда идти;
* чат: `_bank_block()` (`:916`) — единственный раздел без аргумента `report`,
  потому что состояние не вычисляется из ответа, а известно заранее и навсегда.
  Стоит сразу за имуществом, а не в конце: читающий ищет, с чего взыскивать, и
  счета — соседний вопрос, а не примечание;
* веб: `bank_section()` (`app/web/render.py:1041`) собирает те же две строки и
  вешает `state=NO_SOURCE_STATE`; в `build_blocks()` (`:1267`) блок `"bank"`

Ограничения раздела, закреплённые тестами

### 8.2. Имущество должника по ФИО — ЕГРН на этот вопрос не отвечает

Различайте два разных вопроса. «Что за объект по известному нам адресу» — на него
источник отвечает, он включён, и ему посвящён раздел 4. «Что принадлежит
должнику» — на него ЕГРН не ответит никому, кроме самого лица, суда и пристава, и
подключение метода этого не изменило: правообладателя в ответе нет, поэтому
`PropertyRecord.owner_confirmed` не выставляется в `True` никогда
(`app/providers/property.py:169`), а раздела «Недвижимость должника» в отчёте нет
и не будет.

Чтобы получить настоящую проверку имущества должника, нужен официальный платный
запрос в Росреестр с идентификатором лица — СНИЛС или паспорт. Это отдельный
продукт, а не ещё один адаптер.

### 8.3. БКИ — не подключено, и это не вопрос кода

Нужны, по `docs/STATE.md` (раздел «По ТЗ не закрыто», `:241`): договор с бюро
кредитных историй, УКЭП, статус пользователя кредитной истории и согласие субъекта
в шаблоне договора займа. Последнее означает правку документооборота заказчицы, а
не репозитория: без согласия, полученного в момент подписания договора, запрос в
БКИ невозможен независимо от того, написан адаптер или нет.

По БКИ ответ разведки окончательный: без письменного согласия субъекта нельзя
ничем — перечень получателей кредитного отчёта в ФЗ-218 закрытый, и адвокатский
запрос в него не попадает. Обходных поставщиков здесь не бывает: тот, кто обещает
кредитную историю без согласия субъекта, законным путём её не получил.
Подробности — `docs/VENDORS.md`.

### 8.4. Владелец по госномеру и VIN — интерфейс есть, провайдера нет

`UnconfiguredVehicleProvider` (`app/providers/vehicle.py:34`) всегда отвечает
`NOT_CONFIGURED` — правдивый ответ, в отличие от `NO_RESULTS`, который
подразумевал бы, что мы смотрели. Законного стабильного API для «госномер →
владелец» у проекта нет. Валидация номера и VIN при этом настоящая и полезная: она
ловит опечатки до платного прогона и работает против нашей же базы, куда номера
попали из договоров заказчицы.

Заготовки под неподключённые источники живут в `app/providers/future.py` — стабы
`StubProvider` (`app/providers/base.py:237`), всегда `NOT_CONFIGURED`, ровно чтобы
каждый отчёт называл пробел вслух. Стаб обязан уступить место настоящему
провайдеру при регистрации (`build_future_providers(exclude=...)`, вызов —
`app/providers/registry.py:179`): отчёт адресуется по имени провайдера, и две
записи под одним именем молча потеряют одну.

### 8.5. Устаревшая запись в `docs/STATE.md`

`docs/STATE.md:215-219` называет мост «телефон → ФИО» префиксом `PHONE_LOOKUP_*`
и «заготовкой у владелицы вне репозитория». Это неправда с тех пор, как мост
написан: в `app/config.py:220-226` и `app/providers/phone_bridge.py` он
`PHONE_BRIDGE_*`. Не грепайте несуществующий префикс.

Вторая ловушка того же рода — в самом мосте: докстринг
`app/providers/phone_bridge.py:43` упоминает настройку `PHONE_BRIDGE_QUERY`,
которой в `Settings` не существует (`grep` по `app/config.py` — ноль совпадений).
Реальный набор — семь полей `phone_bridge_enabled / base_url / path / api_key /
auth_style / auth_name / field_map`.

## 9. Точки, которые трогает любой новый источник

Чтобы «регистрация, а не редизайн» не осталась обещанием без адреса, вот полный
список мест:

1. **Адаптер** — `app/providers/<имя>.py`. Если вендор отдаёт JSON по HTTP с
   ключом — берите `VendorJsonClient` (`app/providers/vendor_http.py`), не пишите
   свой HTTP. Форму ответа снимайте живым вызовом, а не со страницы документации:
   она уже расходилась с API и стоила молчаливой поломки (1.3).
2. **Регистрация и вытеснение стаба** — `app/providers/registry.py:179`
   (`build_future_providers(exclude=...)`). Две записи под одним именем молча
   потеряют одну.
3. **Подпись в интерфейсе** — `PROVIDER_TITLES` (`app/domain/enums.py:80-94`).
   Название обязано говорить, на какой вопрос источник отвечает, а не как он
   называется внутри (см. «Объект по адресу (ЕГРН)»).
4. **Счёт покрытия** — `app/services/coverage.py`.
5. **Состояние — только через `app/services/reporting.py`.** Своих слов о том,
   спросили или нет, адаптер не заводит никогда. Код ошибки, по которому владелец
   принимает решение о деньгах, а не о технике, добавляется в `_SPOKEN_CODES`
   (раздел 7), а не новым состоянием.
6. **Вычистка сырого тела.** Сохраняешь `raw_response` — прогоняй его через
   `redact_sensitive_json()` (`app/utils/masking.py:132`). Сегодня это делают
   только NewDB (`newdb.py:918`) и ФССП (`fssp.py:165`); `fedresurs.py:139` и
   `fns.py:135` сохраняют тело как есть, и адаптер, скопированный с них,
   унаследует дыру.
7. **Гейт настройки.** Незаполненный источник обязан отвечать `NOT_CONFIGURED` и
   не делать ни одного обращения (`app/providers/base.py:155`). Нечего
   спросить — `insufficient_query()` (`:214`), а не `NO_RESULTS`.
8. **`.env.example`.** Если завели настройку — допишите её туда с объяснением,
   иначе следующий разработчик решит, что её не существует.

## 10. Выкатка на сервер

Три правила. Все три куплены реальными потерями времени, описанными в
`docs/STATE.md` (`:270`, `:297`).

**На сервере только `git pull`. Руками туда не копировать ничего.** До 07.09.2026
прод жил без гита: клон стоял на давно заброшенной ветке, а весь последующий код
туда копировали руками. `git pull` там поэтому ничего не менял, и месяцами
крутилась старая версия при свежем репозитории. Сейчас каталог
`/opt/collector-bot` пересоздан чистым клоном `main`; старый лежит рядом как
`collector-bot-old-<дата>`.

**`--build` обязателен.** Образ собирается из исходников (`build: .`,
`docker-compose.prod.yml:15`), и без него `up -d` поднимет ровно тот же старый
образ: контейнер перезапустится, а код останется прежним. Ровно так однажды и
вышло — аватар в боте был уже новый, а интерфейс предыдущей версии.

```bash
cd /opt/collector-bot
git pull origin main
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml logs -f bot   # убедиться, что поднялся
```

**Перед тем как искать дефект в коде — сверить, что выложено.** Две строки:

```bash
cd /opt/collector-bot && git rev-parse --short HEAD   # что выложено
git ls-remote origin -h refs/heads/main               # что в main
```

Разошлись — значит дефект уже починен, просто не доехал. Это не гипотеза: бот
показывал заказчице интерфейс месячной давности при свежем репозитории, и полдня
ушло на поиск того, чего в коде уже не было.

**После выкладки нажать `/start`.** Нижняя клавиатура принадлежит чату и живёт на
стороне Telegram: пока `/start` не нажат, у всех прежних пользователей остаются
старые кнопки. Обработчики снятых подписей на этот случай сохранены
(`LEGACY_BUTTON_*`, правило 3), поэтому старая кнопка не сломается — но новых не
появится.

Автодеплоя нет: `.github/workflows/check.yml` только гоняет проверки
(`make install`, `make check`, `make demo`) на каждый push и pull request.
