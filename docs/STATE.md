## Что закрыто

### Критические (4 из 5)

**Двойной запуск прогона.** Второй тап по «Запустить» проходил сквозь фильтр
состояния, пока считалась смета, и оплачивал всю выгрузку второй раз; второй
владелец обходил хендлерную защиту вовсе. Замок на двух уровнях: состояние и
клавиатура сметы снимаются до первого `await` (`app/bot/handlers/batch.py`), а
`BatchService.run` проверяет активный прогон и в памяти, и в базе
(`BatchAlreadyRunningError`). Ответ второму — отказ со ссылкой на идущую
очередь: замок, который ждёт своей очереди, молча начал бы второй прогон за те
же деньги. Строка `running` старше 30 минут считается мёртвой, иначе упавший
процесс запрещал бы прогоны навсегда.

**Второй должник подряд.** `Card.blank` ложно после любой проверки, поэтому
«Проверить человека» открывало карточку предыдущего: новый телефон ложился к
чужой фамилии, и отчёт выходил про прошлого человека — с его долгом и его
пошлиной. Проверенная карточка чистится у всех дверей (`start_person_card`), а
телефон, присланный после законченной проверки, начинает нового должника
(`_starts_new_person`). Остальные поля по-прежнему дописываются в ту же карточку:
«дошлите ИНН — перепроверю того же».

**Один телефон на нескольких людей.** Точное попадание по телефону возвращало
все строки, и дата рождения, сумма долга и пошлина брались у первой попавшейся.
`_narrow_by_person` в `app/services/search.py` фильтрует по уже введённым ФИО и
дате. Фильтр односторонний: если после него не осталось никого, отдаётся
исходный список — расхождение выгрузки с документом оператора это факт, а не
повод выбросить единственную найденную строку.

**Оконченные производства ФССП.** Разбирались и терялись: раздел печатал
«активных не найдено», список источников тут же писал «4 зап.», а балл получал
бонус за чистую ФССП. Теперь `DebtorReport.closed_proceedings` печатается
отдельным списком в тексте и в вебе словами источника; бонус `no_enforcement` не
начисляется при оконченных, а ст. 46 ч. 1 п. 3/п. 4 даёт отрицательный фактор
(`WRITTEN_OFF_ENFORCEMENT_PENALTY`): пристав уже искал должника и его имущество
и не нашёл. Ложная нота «слабое совпадение либо непрочитанный статус» исправлена.

### Пятая критическая — сознательно отложена

Открытый доступ (`ALLOWED_TELEGRAM_USER_IDS=*`). Решение владелицы: доступы
настраиваются при передаче бота заказчику, когда он сам начнёт их раздавать.
Механизм готов и выключен: `DAILY_SEARCH_QUOTA=0` (владелец без лимита всегда).
Отдельно сделано подтверждение перед платным повтором — «Обновить» идёт мимо
кэша и висит под каждым старым отчётом, четырёх случайных нажатий хватало,
чтобы сжечь остаток.

- **Имена переменных окружения в текстах для оператора.** Убраны из сметы и из

### Интерфейс — переделан по боту-образцу

Ориентир: скриншоты бота, который владелица показала как образец, и её слова —
«нравится анимация, простота, одна фраза при старте, две кнопки внизу».

- Нижняя клавиатура: **ровно две кнопки в один ряд** — «Главное меню» и
  «Проверить человека». Все прежние подписи сохранены с обработчиками
  (`LEGACY_BUTTON_*`): клавиатура живёт на стороне Telegram и обновляется только
  со следующим `/start`.
- `/start` — **одно сообщение**: фраза и меню под ним. Нижняя клавиатура
  приезжает носителем, который тут же удаляется (`install_reply_keyboard`).
- Главное меню — 5–6 кнопок в столбик, первой то, что нажимают каждый день.
  Справка и история переехали в него из подменю.
- Карточка — сетка полей три в ряд, `✅` у заполненного, «Проверить» отдельной
  строкой, «В меню» под ним. Экран вопроса — `✎ Фамилия`, одна строка что
  сделать, пример.
- Под отчётом первой ссылка с числом записей, дальше выгрузка, платный повтор,
  «Новая проверка» и «В меню». История — одно сообщение с «В меню» и «Обновить».
- Тупиков нет ни на одном экране; `/cancel` снимает заданный карточкой вопрос.

## Правила, которые нельзя нарушать

Они не стилистические. Каждое куплено дефектом.

1. **Найденное не должно выглядеть ненайденным.** Пустой раздел значит «не
   спрашивали» ИЛИ «спросили и пусто» — и это разные строки, всегда. Отчёт несут
   в суд.
2. **Платит одна кнопка.** Присланный текст дописывается в карточку и ничего не
   запускает. Любая новая кнопка, тратящая деньги, обязана спрашивать.
3. **Подпись нижней кнопки, которая когда-либо существовала, обязана иметь
   обработчик навсегда.** Иначе она уходит в разбор свободного текста и
   становится фамилией должника. Проверяется тестом по всему `REPLY_BUTTONS`.
4. **Имён источников и переменных окружения в текстах для оператора нет.**
   Причины нехватки — есть.
5. **Персональные данные третьих лиц в репозиторий не попадают** — ни в
   фикстуры, ни в примеры, ни в тесты.

## Что дальше, по убыванию важности

### 1. Боевая версия и живая выгрузка

Заказчик прислал CSV с настоящими должниками. Он ни разу не проходил импорт.

- Проверить импорт на нём **не коммитя файл**: положить вне репозитория,
  `ImportService.import_file`, прочитать отчёт импорта.
- Известный дефект ревью, который тут вылезет первым: широкий CSV с
  разделителем `;` отвергается — сэмпл для `csv.Sniffer` режется посреди строки
  (`app/providers/internal/csv_schema.py`, `read_table`). Порог ниже, чем
  кажется: сниффер требует ≥10 полных строк в 4096 символах, то есть ломается
  уже на ~20 колонках. Починка: резать сэмпл по последнему переводу строки, а
  при `csv.Error` выбирать разделитель по числу вхождений в строке шапки.
  Сниффить «только шапку» рискованно — запятые внутри названий колонок.
- После импорта прогнать массовую проверку и посмотреть очередь.

### 2. Оставшиеся HIGH из ревью

- **#7** Смета обещает «из кэша, бесплатно» строки, которые кэш не отдаст:
  `_scan` считает кэшированным любой запрос в TTL, а `_has_unsettled_source`
  отчёт с неответившим источником переспрашивает. Для остановленного прогона
  ложь гарантирована.
- **#11** Кэш выбрасывает весь отчёт, если одному источнику «не хватило данных»,
  и повторный запрос заново оплачивает ответившие.
- **#18** Вердикты «Подавать иск»/«Судебный приказ» несут только положительные
  причины: завершённое банкротство, производства, залоги и иски до карточки,
  очереди и CSV не доходят.
- **#13** Очередь подписывает «Проверено полностью — ответили все источники» по
  порогу уверенности 90%, хотя источники молчали.
- **#22** Прогон нельзя остановить: под прогрессом только ссылка.

## Как запустить

```
make install          # venv и зависимости
cp .env.example .env  # заполнить TELEGRAM_BOT_TOKEN и ALLOWED_TELEGRAM_USER_IDS
make demo             # весь пайплайн в терминале, без единого ключа
make run              # бот
```

`APP_MODE=demo` не ходит во внешние источники и не тратит баланс — на нём
проверяется весь интерфейс. Живые реестры включает `APP_MODE=live` и ключ
агрегатора; остаток у поставщика небольшой, полная проверка одного должника —
пять платных обращений.

## Как выкатить на сервер

Автодеплоя нет: `.github/workflows/check.yml` только гоняет проверки. Выкладка
руками, на сервере:

```
cd <каталог с репозиторием>
git pull origin main
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml logs -f bot   # убедиться, что поднялся
```

`--build` обязателен. Образ собирается из исходников (`build: .`), и без него
`up -d` поднимет ровно тот же старый образ — контейнер перезапустится, а код
останется прежним. Ровно так однажды и вышло: аватар в боте был уже новый, а
интерфейс — предыдущей версии.

**После выкладки нажать `/start`.** Нижняя клавиатура принадлежит чату и живёт
на стороне Telegram: пока не будет `/start`, у всех, кто уже пользовался ботом,
останутся прежние кнопки. Обработчики снятых подписей на этот случай сохранены
(`LEGACY_BUTTON_*`), поэтому старая кнопка не сломается, но новых двух не
появится.
